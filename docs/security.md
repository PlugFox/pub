# Security Requirements

Corporate-grade posture. Self-assessment framework: **OWASP ASVS L2**; authenticator policy aligned with **NIST SP 800-63B rev4**; OAuth per **RFC 9700** (OAuth 2.0 Security BCP). This document is normative for implementation and review; requirement IDs (S-xx) are referenced from tests.

## 1. Authentication

**S-01 OIDC** (Google preset or any configured issuer; confidential client, code exchange server-side only): `state` ≥128-bit single-use, bound to the initiating browser via a short-lived `__Host-` pre-auth cookie (the redirect traverses full-page navigation; this cookie is a flow binder, never an API credential); PKCE S256; `nonce` verified in `id_token`; exact-match redirect URI; `id_token` validation — signature against Google JWKS by `kid` (alg pinned to RS256), `iss`/`aud`/`exp`/`iat` with small skew. Identity key is `(iss, sub)`, never email. Trust email only when `email_verified=true`.

> **S-01.a — how the flow binder and the alg pin are actually implemented** (added 2026-08-07 with the OIDC slice).
>
> - **Flow binder**: the API is deliberately cookieless (decision 03), so the "pre-auth cookie" role is played by an opaque 128-bit **`flow_id`**: `start` persists `{state, nonce, pkce_verifier}` server-side in KV under it (10-min TTL) and the initiating page holds the id (e.g. sessionStorage); `callback` requires `flow_id` + `code` + `state` in one JSON POST. The binding is equivalent — `state` alone redeems nothing, the record is **deleted on first presentation regardless of outcome** (success, mismatch, or expiry all burn it), `state` is compared constant-time, and expiry is decided by the record's own `created_at`, not the KV TTL.
> - **Alg pin, multi-provider**: with arbitrary issuers allowed (decision 12), the accepted signature algorithms are the discovery-advertised set **intersected with `{RS256, ES256}`** — `none` and the HMAC family are structurally outside the set, so key-confusion forgeries never reach key material. Keys resolve strictly by `kid` from the provider's JWKS (no trial verification); an unknown `kid` triggers **exactly one** JWKS refetch (key rotation) before the token is rejected. On multi-audience tokens `azp` must equal the client id. The token-exchange response body is never logged (attacker-influenced).
> - `start`/`callback` ride the S-24 "login 10/min/IP" bucket — unthrottled starts would mint unbounded KV flow records.

**S-02 Account linking**: auto-link OIDC identity to an existing account only if both sides have verified the same email; an unverified identity can never claim an existing account; linking writes an audit event and notifies the user by email.

> **S-02.a — the policy for identities we have never seen** (added 2026-08-07). A *known* `(iss, sub)` signs in on the credential alone — the email claim is display data. A *new* identity requires a **verified** email from the IdP to do anything at all: link (only when a *verified* local holder of the same address exists — an unverified local claimant can neither be linked to nor displaced, the attempt fails uniformly), or register (behind `allow_registration`, S-31-gated). No verified email → uniform refusal. The S-31 domain gate is evaluated at **every** OIDC sign-in against the account's email, not only at registration — consistent with the OTP path.

**S-03 Email OTP** (primary single factor — it is *not* MFA and is never presented as such): 8-digit CSPRNG code; stored as HMAC-SHA-256 with server pepper; expiry 10 min; single-use; invalidated by successful use *and* by issuing a replacement; ≤5 wrong attempts per code then the code dies (never the account); resend ≥60 s apart, ≤5/hour per email, per-IP caps; verification bound to the server-side pending-auth record created at request time (opaque one-time id held by the client), so a phished code cannot be redeemed from elsewhere.

> **S-03.a — the attempt budget must be spent atomically** (added 2026-08-06 after the auth-slice security review). "≤5 wrong attempts" is only a bound if concurrent verifications cannot share an increment. The counter therefore lives in its own KV key under an **atomic** increment (`Kv::incr`), never as a field inside the pending-auth record read-modify-written by the verify handler, and the attempt is **spent before the code is compared**. A get-then-set counter lets an attacker fire N guesses in parallel for the price of one attempt, converting a 5-guess budget into an arbitrarily large one. Expiry is likewise decided by the record's own `created_at`, not by the KV TTL, so a lagging or misconfigured eviction policy cannot extend a code's life.

**S-04 Anti-enumeration** (login, OTP request, signup, invitations, password-reset-like flows): uniform responses and near-identical timing whether or not the account exists. On the pub protocol the ladder is visibility-first: any package the principal cannot read (another org's private, unknown name) returns **404 — for anonymous and authenticated principals alike**; a 403-vs-404 differential would let account holders enumerate private names. 401/403 semantics per S-14; the full normative ladder incl. `require_auth_for_read` mode lives in [decision 05](decisions.md#05--anonymous-read-configurable-default-allowed).

> **S-04.b — what the registry ladder does *not* hide** (added 2026-08-07 after the registry conformance review). Two residues are real, understood, and accepted; both are recorded here so a future change is measured against a known baseline rather than an assumption.
>
> - **Org slugs are not secret.** Decision 01 step 2 resolves *any* instance-public package inside *any* org base, so a prober who knows one public package name can tell `/o/acme/pub` (200) from `/o/nosuchorg/pub` (404) without credentials. The publish ladder's 403-for-a-foreign-org-token adds nothing an anonymous caller could not already learn. Package *names* — the thing S-04 protects — stay uniform: private and unknown answer identical bytes on every read route, asserted by `private_and_unknown_names_answer_identical_bytes`. If org-slug secrecy is ever required it needs a different mechanism (unguessable base paths), not a status-code change.
> - **A restricted name costs one query, an unknown name costs two.** `resolve_in_base` looks up the package row and, only when there is none, the name claim — so "claimed but unreadable" and "never claimed" differ by one indexed SELECT (tens of microseconds) behind identical responses. Making it constant-work means a second query on every hot-path resolve, which is the endpoint the pub client re-fetches before *every* command. **Accepted**: the signal is far below network jitter and the responses are byte-identical. Revisit if the proxy slice ever makes the unclaimed branch expensive enough to be timeable — an upstream fetch on a cache miss is a *visible* delay, and that one must be made uniform (serve the miss from a bounded-latency path) rather than accepted.
>
> **S-04.c — the proxy made that branch timeable; the residue is now a network round trip, and it is accepted with its number written down** (added 2026-08-07 after the proxy adversarial review; this is S-04.b's own revisit condition firing).
>
> Measured against the live instance with the real pub.dev upstream, 15 samples each, both answers **byte-identical** `404 {"error":{"code":"not_found","message":"package …"}}`:
>
> | Probe | Work done | Median |
> |-------|-----------|--------|
> | a name **claimed on this instance** but unreadable from this base | two indexed SELECTs | **0.34 ms** |
> | a name claimed **nowhere**, absent upstream | the above + one upstream listing fetch | **219 ms** |
>
> So an *unauthenticated* prober can decide "is this name claimed on this instance?" — for any org's private packages — by response time alone, at 640× separation. That is the enumeration S-04 exists to prevent, and it is not fixable by making the statuses match, because they already do.
>
> **Accepted, with the mitigation named rather than implied.** The three alternatives are all worse than the leak: padding every unclaimed-name 404 up to an upstream round trip puts ~200 ms on the hot path of every legitimate cold resolve; skipping the upstream fetch and warming asynchronously makes the *first* `pub get` of any new package fail; and asking upstream about claimed names too would tell pub.dev the instance's private package names, which is a strictly larger leak to a strictly worse audience. What closes it is **`registry.require_auth_for_read = true`** ([decision 05](decisions.md#05--anonymous-read-configurable-default-allowed)): with nothing anonymous-readable there is no anonymous prober, and the differential is then only visible to principals who already hold a credential on the instance. Deployments whose private *names* are sensitive must set it; this is the concrete reason the flag exists, and it belongs in the deployment runbook. A **blocked** org (`upstream_policy = block`) has no expensive branch at all and is uniform at 0.6–0.7 ms across claimed, unknown, and upstream-only names — measured in the same session.
>
> **S-04.d — the app read model has more surfaces than the protocol, and every one of them is the same predicate** (added 2026-08-07 with the search backend and the public read model, [decision 11](decisions.md#11--search-behind-a-trait)).
>
> The pub protocol leaks a name through exactly one shape: a status code on a by-name route. The web read model adds five more, and four of them are not statuses at all — a search result, a facet bucket, an instance counter, an org profile's package list, and a reverse-dependency edge. A count is as much a disclosure as a name: "2 packages" versus "3 packages" on the same org, seen by two principals, is the existence of a private package.
>
> **The rule.** Every read in `PackageSearch` — listing, text query, facet aggregate, instance counters — applies one mandatory predicate, `visibility = 'public' OR org_id ∈ SearchView`, emitted by the backend before anything the query grammar can reach. The view is *computed by calling `authorize(actor, ReadPackages, org)`*, not by a second implementation of the ladder, so search visibility cannot drift from resolution visibility. Consequences that are asserted rather than assumed (`search_visibility` in the contract suite, on both backends; `s04_private_packages_are_invisible_on_every_read_route` over the HTTP surface):
>
> - An `is:private` / `is:unlisted` / `org:` filter **narrows** the visible set and can never widen it — asking for the hidden rows explicitly returns nothing.
> - Facet totals and `/api/v1/home` counters equal the number of rows the same principal's listing would return.
> - A **reverse dependency query is gated on the subject**: "who depends on `acme_secret`" is refused unless the caller can read `acme_secret`, or the dependents list would confirm the name to somebody who cannot.
> - Every by-name route (`/packages/{name}`, its versions, one version, its dependents) answers the same `404 not_found` for private-and-unreadable as for never-existed. The message quotes the name the *caller* supplied — which they already know — and nothing derived from our state.
> - `unlisted` is a discovery flag, not an access-control one: it is hidden from search, facets, counters, and the org profile for everyone outside the owning org, while the package page and `resolve` still serve it by name. Hiding it from the page too would break the "share a direct link" workflow the flag exists for.
>
> One deliberate non-secret, for symmetry with S-04.b: the **publishing account** on a version row is withheld outside the owning org, but the owning *organization* is public everywhere. Orgs are this registry's publishers; the individual who ran `dart pub publish` is not part of that contract.

> **S-04.a — uniform work, and the one accepted timing residue** (amended 2026-08-06 after the auth-slice security review). "Near-identical timing" is implemented as *identical server-side work*: `request_otp` runs the rate-limit checks, generates the code, computes the HMAC, writes the pending record, performs the account lookup, and renders the email template for **every** address — known, unknown, or policy-rejected. Branching on the outcome anywhere earlier turns response latency into an existence oracle, so no early `return` may be introduced above the mail hand-off.
>
> **The asymmetry is closed** (amended 2026-08-07 with [decision 26](decisions.md#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path); this is the "planned mitigation" clause below firing). The SMTP hand-off used to happen only for addresses that may actually receive a code — a blocked address must never be sent a redeemable code, so the transport could not be made unconditional, and the residue was one delivery round trip. Delivery now happens on the jobs queue, so **both branches perform one identical enqueue** and differ only in the row's state: `pending` for an address that may receive a code, `suppressed` — never claimable, carrying no deliverable payload — for one that may not. The response no longer waits on anything that branches, so the residue is gone rather than bounded.
>
> Two properties this must keep, or it regresses: the suppressed row exists **only** to make the two branches cost the same (it tells a database reader nothing the audit log did not already record about the rejection, and it must never become a deliverable message), and no early `return` may reappear above the enqueue — every line of uniform work above it stands unchanged. A further consequence worth stating positively: because the mail hand-off can no longer fail the request, an SMTP outage no longer answers **500** for a deliverable address and **200** for a blocked one, which was the same oracle reachable by taking the relay down.
>
> The historical bound, kept for context: the leak was limited by the per-email (5/h) and per-IP (20/h) caps, and revealed only "this address would receive mail", never whether an account exists — an unknown address on an allowed domain is mailed too whenever registration is open.

> **S-04.d — `Server-Timing` is opt-in, and the authentication family never carries it** (added 2026-08-14, *before* the header was implemented — see [decision 28](decisions.md#28--the-observability-plane-its-own-listener-bounded-labels-and-timing-that-stays-opt-in)).
>
> S-04.a constrains server-side *work* and says nothing about response *headers*, and three separate documents instructed an implementer to emit `Server-Timing` without qualifying it. A duration header is not a smaller version of a timing side channel — it is the same channel with the network noise removed, delivered by the server, per request, for free. Two rules, both normative:
>
> - **The header is off by default** (`telemetry.server_timing = false`). An operator who turns it on is choosing a diagnostic aid over a measurement surface, on an instance they control.
> - **It is never emitted on `/api/v1/auth/*`, whatever the flag says** — `otp/request`, `otp/verify`, `refresh`, `logout`, `totp/*`, `step-up` and every OIDC `start`/`callback`. These are the routes whose entire defence is that two outcomes cost the same; publishing the cost of each one is the oracle S-04.a exists to remove.
>
> The two surfaces the flag *does* expose when enabled — the app read model and the pub protocol — carry their own visibility differentials (404 for unreadable names per S-04, the one-query-versus-two residue of S-04.b, the upstream round trip of S-04.c). Enabling it hands a prober exact numbers for those. That is the operator's call to make, which is what "opt-in, default off, documented" means; it is not a call an implementer gets to make silently by adding a header layer.

**S-05 TOTP second factor**: RFC 6238, 160-bit seed, ±1 step skew, last-accepted-counter stored to reject replays; seed encrypted at rest (AES-GCM with env KEK); 8–10 single-use recovery codes hashed with argon2id, shown once. ≤5 failed TOTP/recovery-code/step-up verifications per pending attempt, then exponential backoff on the MFA step only — audit-logged as throttle trips (see S-24).

> **S-05.a — implementation notes** (added 2026-08-07 with the TOTP slice).
>
> - **Enrollment** touches the database only once proven: `enroll` parks the KEK-sealed seed in a 15-min KV record; `confirm` verifies a live code against it and only then writes the credential — with the confirmation step as the initial replay floor, so the code the user typed at confirm can never be replayed at login. Ten recovery codes are issued exactly once at confirm (`XXXXX-XXXXX`, look-alike-free alphabet; entry forgives case and separators).
> - **Replay rejection is layered**: verification only considers steps strictly above the stored floor, and the floor advance itself is a single-statement compare-and-set in the repository (`… WHERE totp_last_step < ?`), so two concurrent verifications of one step cannot both win. Sealing is AES-256-GCM under the boot KEK (`auth.kek`, base64 32 bytes, production-required per S-25), stored `nonce ‖ ciphertext‖tag` in `credentials.secret_enc`.
> - **The failure budget** is an atomic KV counter per MFA scope — the pending-login handle, the session (step-up), or the user (enrollment confirm). After the 5th failure the scope enters exponential backoff (2 s doubling per further failure, capped at 10 min, `429 + Retry-After`), decided **before** any verification work; throttle trips are audit-logged. The budget never locks the account — only the scope waits.
> - A first factor that passes for a TOTP-enrolled account yields **no tokens**: only an opaque single-use pending-MFA handle (5-min TTL, expiry decided by the record's own timestamp), redeemed with a TOTP or recovery code. This applies to OTP and OIDC first factors alike.

**S-06 Step-up ("sudo mode")**: fresh second-factor (or re-auth) within a short window required for: disabling 2FA, changing email, creating `publish`/`admin` tokens, sending invitations, granting or changing member roles at Write level or above, version retraction, hard delete, org deletion, transferring ownership. (Without gating invitations/role grants, a stolen admin session could invite an attacker account and escalate around the CLI-token publish boundary.) Invitations default to the `Read` role — least privilege.

> **S-06.a — what "fresh" means, and the list as implemented today** (added 2026-08-07 with the TOTP slice).
>
> - A session is **step-up-fresh** when either (a) it was *created* within the step-up window — a login already ran the strongest factor chain the account has, TOTP included — or (b) `POST /api/v1/auth/step-up` verified a live TOTP/recovery code within the window. The window is `auth.step_up_minutes` (default 15); the mark lives in KV keyed by `sid` and its expiry is decided by the stored timestamp. Stale sessions get the distinct `step_up_required` **403** so the UI can prompt instead of dead-ending.
> - Accounts **without** an enrolled second factor cannot call the step-up endpoint (nothing to verify); their re-auth path is a fresh login, which satisfies (a). This is the "or re-auth" arm of S-06 — a stolen stale session still cannot perform gated actions without redoing the email-OTP loop.
> - **Gated today** (updated 2026-08-07 with the management surface — the placeholder list below is now empty except for the email change, whose endpoint still does not exist): `DELETE /api/v1/auth/totp` (disabling 2FA), minting CLI tokens with `publish`/`admin` scopes, `POST /api/v1/sessions/revoke-all`, `POST /api/v1/orgs/{slug}/invitations` and its revocation, member add/role-change **at Write level or above**, `POST …/versions/{version}/retract` and `…/unretract`, `DELETE …/versions/{version}` (hard delete), `POST /api/v1/packages/{name}/transfer`, and `DELETE /api/v1/orgs/{slug}`. Each takes the `StepUp` extractor, or calls `require_step_up` where the gate depends on the parsed body (the role being granted). **Still a placeholder**: email change.
>
> **S-06.b — three refinements the gate list needed once it met real endpoints** (added 2026-08-07).
>
> - **The role gate is symmetric.** "Granting or changing member roles at Write level or above" is read as *either side* being Write+: promoting a Read member to Write is gated, and so is demoting an Admin to Read. Taking somebody's publish rights away is exactly as consequential as granting them, and an ungated demotion would let a stolen stale admin session lock the real owners out. The check is `role.satisfies(WRITE)` on the old **and** the new level, so a future intermediate role above Write inherits the gate instead of slipping under an enumeration.
> - **A Read-level grant is not gated**, deliberately. S-06's list is about escalation, and prompting for a second factor to add a read-only teammate is how a prompt becomes noise that people click through. Invitations *are* gated unconditionally, because an invitation reaches an address that may not have an account yet — which is the escalation route S-06's parenthetical names.
> - **Dangerous actions carry a confirmation field on top of the gate**, not instead of it: `{confirm: "{name}@{version}"}` for a hard delete, `{confirm: "<slug>"}` for an org deletion, `{confirm: "<name>"}` for a transfer. A fresh second factor proves *who* is asking; the confirmation proves *what* they meant. Neither substitutes for the other.

> **S-06.c — bulk export is gated, which is the one exception to "the list is about escalation"** (added 2026-08-14 with [decision 30](decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature)).
>
> The audit export (`GET /api/v1/admin/audit/export`, [S-23](#5-audit--abuse)) grants no privilege and changes no state, so S-06.b's reasoning would leave it ungated. It is gated anyway: one request hands the caller every actor id, IP address and user agent the instance has ever recorded, which is the highest-value single read on the surface and exactly what a stolen stale admin session is for. Reading the audit *viewer* stays ungated — it is paginated and filtered, and gating it would gate ordinary operations work. The line is bulk, not sensitivity.

> **S-06.d — a credential with no expiry is gated by its lifetime, not by its scope** (added 2026-08-15 with [decision 33](decisions.md#33--reaching-the-mechanisms-that-already-exist-the-token-model-on-the-wire-an-operator-surface-for-the-supply-chain-registers-and-errors-that-say-what-the-server-said)).
>
> The list gates minting `publish`/`admin` tokens and leaves `read` mints ungated, which was right while every token expired: a stolen stale session could produce a read credential that died in 90 days. [S-13.c](#3-cliapi-tokens) makes "never" expressible, and a non-expiring token is the longest-lived object the token plane can produce — revocable, but only by somebody who knows it exists. So the gate follows the lifetime: **`expires_days: null` demands a fresh factor at every scope**, including `read`. The scope gate is unchanged and independent; a non-expiring `publish` mint is refused outright by S-13.c before either gate is reached.
>
> This also makes the S-13.c wire change loud rather than silent: a client that omits `expires_days` because it expected the old 90-day default now meets `step_up_required` (or a 400 if it asked for a write scope), instead of receiving an eternal credential nobody chose.

## 2. Sessions & web plane

**S-07** Access JWT: TTL ≤15 min; Ed25519 with `kid`; claims limited to `sub`, `sid`, org role levels, timestamps. No other PII in claims. Verification pins the algorithm to EdDSA, resolves keys strictly by `kid` from the boot keyring, rejects `none`/unknown algorithms and retired kids, and enforces `exp`/`iat` with small skew.
**S-08** Refresh token: opaque ≥128-bit CSPRNG, stored hashed (SHA-256), rotated on every refresh; reuse of a rotated-out token revokes the session family. The refresh endpoint validates the durable session row in the DB on **every** call: not revoked (`revoked_at`), within idle timeout (default 30 d sliding) and absolute cap (default 90 d). Client-side the refresh token lives in localStorage; its theft-bound is rotation + reuse detection + these caps (decision 03 consequences).
> **S-08.a — what the loser of a rotation race is told** (added 2026-08-16 with [decision 35](decisions.md#35--backend-legs-that-fail-when-the-backend-is-absent-and-a-harness-that-admits-a-race), after the new test stand found the answer was a 500).
>
> Two refreshes of one token can be in flight at once, and this is ordinary rather than exotic: two
> browser tabs, a client retrying a slow request, or a stolen token presented beside its owner's. The
> requirement "exactly one may win" was already implied by rotation; what was never written down is
> that **the loser must be told it lost**. A rotation refused by the store — a lock conflict, a
> serialization failure — is indistinguishable from the store being down: the auth layer cannot revoke
> the family, cannot clear the client's session, and answers 5xx on the endpoint every signed-in
> browser calls, so the client retries into the same race.
>
> Normative: a rotation that loses the race answers as **reuse** (`RefreshReused`, which revokes the
> family) or as **unknown** (`NotFound`), never as a store error, and the decision is made by the write
> itself rather than by a read the write then trusts — SQLite makes the swap one conditional statement,
> Postgres holds the row with `SELECT … FOR UPDATE`. Both dialects are held to
> `session_rotation_is_single_winner` in the shared contract suite, which races 25 barrier-released
> rounds; a single attempt does not reliably overlap, and a pool with one connection cannot overlap at
> all, which is why this requirement was satisfiable and unsatisfied for as long as it was.

**S-09** Revocation: durable truth is `sessions.revoked_at` in the DB. The revoked-`sid` set (TTL = access TTL) in KV is only the fast path for access-JWT checks on every authenticated request; its keyspace must not evict early (`noeviction` or a dedicated non-evicting store), and when the KV check is unavailable it **fails closed** (reject or force refresh, which hits the DB). Logout revokes the current session (`sid`); the explicit revoke-all action and **any permission or role change** revoke all the user's sessions. Multi-instance coherence is guaranteed by the Redis requirement ([decision 03](decisions.md#03--sessions-jwt-access--refresh-sessions-kv-backed-revocation)); with the in-memory KV a restart clears the blocklist for up to one access TTL — accepted, documented single-node risk.
> **S-09.a — which changes revoke, and where the rule lives** (added 2026-08-07 with the management surface).
>
> "Any permission or role change revokes all the user's sessions" is implemented as a
> classification made in exactly one place — `AuthorityChange` in `pub_admin::orgs` — and every
> membership mutation is routed through it. `OrgRepo`'s membership mutators are called from that
> module and nowhere else, so "no route can forget" is structural rather than a review item.
>
> | Change | Revokes sessions | Sweeps CLI tokens | Why |
> |--------|---------|---------|-----|
> | Role change **down** | **yes** | **yes** (S-13.a) | An access token minted a minute ago carries the *old* level; a still-live CLI token could still mint above the new role. Both are the window this rule closes. |
> | Role change **up** | **yes** | **no** | Sessions revoke either direction for simplicity; a *raise* strands no over-scoped token (the new level is higher), so the token sweep is a no-op. |
> | Membership removal | **yes** | **yes**, all of this org's | Old level was "anything at all"; every one of the member's tokens for this org is now over-scoped. |
> | Org archived (forced deletion) | **yes**, per removed member | **yes**, in one bulk repo `UPDATE` *before* the per-member loop, so the sweep finds nothing left to do and does not double-audit. | Every membership is deleted, so every one is a withdrawal. |
> | Account suspended | **yes** | **gated, not swept** | Authority went to zero *reversibly*; sessions are revoked and the credential plane is gated at `find_active_by_hash` (S-13.a), so unsuspension restores the tokens rather than forcing a re-mint. |
> | Membership **created** (add member, invitation accepted) | **no** | **no** | Nothing stale can spend authority the grant just created: a token issued before it carries no claim for the org and fails closed. Logging somebody out the instant they accept an invitation is a cost with no security benefit — and it would make accept hand back a session it had just destroyed. |
>
> Session revocation goes through `AuthService::revoke_sessions_after_authority_change`, so it is the
> same durable-then-KV-blocklist path logout uses, with the **system** as the audit actor (the
> person losing their sessions is not the person who acted) and a `reason` naming the change; the
> token sweep (S-13.a) runs **after** it, best-effort, and never blocks it.
> Asserted end to end against live tokens by
> `manage.rs::s09_a_role_change_revokes_every_session_of_the_affected_member` and
> `s09_removal_revokes_sessions_but_a_grant_leaves_them_alone`.
>
> **Accepted edge (2026-08-07):** accepting an invitation that *raises* an existing member's role is classified `Granted`, so it revokes no sessions — a deviation from the "either direction" row above, kept because a raise strands nothing stale (the old level is lower) and reclassifying it would need an extra membership read on the accept path for no security gain. A raise, however reached, is the one direction where not revoking is safe.

**S-10** Session hygiene: session list UI (created, last-seen throttled, IP, coarse UA, current flag, revoke one/all); idle timeout and absolute cap configurable per instance.
**S-11** XSS compensation for localStorage tokens: strict CSP (`script-src 'self'` + nonce for the single inline theme script, no `unsafe-inline`), backend-sanitized README HTML (ammonia whitelist; links `rel="nofollow ugc noopener"`; `img-src` restricted), publishing rights reserved to CLI tokens so a stolen web session cannot publish.
**S-12** CORS locked to the instance origin; state-changing JSON endpoints require a custom header and reject non-JSON content types; `Origin`/`Sec-Fetch-Site` verified server-side.

> **S-12.a — the three checks are independent layers** (clarified 2026-08-06 after the auth-slice security review). The custom header (`X-Pub-Request: 1`) forces a CORS preflight, but its enforcement lives in the browser. The server-side comparison is the layer that does not delegate: when `Sec-Fetch-Site` is present it must be `same-origin`/`same-site`/`none`, and when `Origin` is present its scheme+host+port must equal the instance's configured `server.public_url` origin (parsed, not string-prefixed — `https://pub.corp.com.evil.example` and a scheme downgrade must both fail; `null` never matches). **Absence of both headers is allowed**: CLI, CI, and `curl` clients never send them, and absence is not evidence of a cross-site request — a foreign *value* is.

## 3. CLI/API tokens

**S-13** Format `<prefix>_<base62×30><crc32-base62×6>` (default prefix `pub_`, instance-configurable per decision 17); SHA-256 at rest + first-8 display hint; show-once. Scopes `read`/`publish`/`retract`/`admin`, org-bound, optional package patterns; default expiry 90 days (unlimited allowed only for `read`); last-used/last-IP write-throttled tracking; revocation effective within ≤60 s (no server-side token caching beyond that); per-token rate limits.
> **S-13.a — a token no longer outlives the authority it was minted under** (added 2026-08-07, closes roadmap D37). "Revocation effective within ≤60 s" used to mean only the explicit revoke action; a demotion or a suspension left the credential itself untouched, because the token plane re-derives the *role* per request but never re-examines the *token*. Two rules close that, and both are asserted against live tokens.
>
> - **A lowered role sweeps the tokens the new role could no longer mint.** When a member's role is redefined *downward* or their membership is withdrawn, their org-bound tokens whose scopes exceed the new level are revoked (a withdrawal → level `NONE` → all of them; a raise → none). "What a scope is worth" has one source — the same scope→action→level map the mint gate uses (`read`→50, `publish`/`retract`→100, `admin`→200), evaluated in Rust so it is never duplicated into per-dialect SQL — and the comparison is against the *token's* scopes, not the holder's, so a Read-scoped token survives a demotion to Read. An empty scope set fails **closed** (revoked). The sweep runs *after* the S-09 session revocation, cannot block it, and revokes best-effort with a logged warning on any per-token failure; it appends one `token.revoked` audit row (system actor, `{reason, count}`) only when it revoked something. Asserted by `manage.rs::s13_a_demotion_revokes_the_org_tokens_the_new_role_could_no_longer_mint` and `s13_a_raise_revokes_no_tokens_and_a_removal_sweeps_only_this_orgs_tokens`.
> - **Suspension gates the credential plane at the repository.** `TokenRepo::find_active_by_hash` (both dialects, an `EXISTS status = 'active'` predicate — which also excludes `deleted`) returns nothing for a token whose owner is not active, so a suspended account's CLI tokens stop authenticating within the ≤60 s bound and resume on unsuspension — reversible, exactly like suspension. On the wire the token is indistinguishable from a revoked or unknown one (uniform 401 per S-14.a; the pub client drops its stored copy, costing one `dart pub token add` after reinstatement), and the failure still spends the S-24 budget. This is what makes the S-27 break-glass answer real: suspending a compromised account now neutralizes both its web sessions *and* its CLI tokens. Asserted by `admin.rs::s13_suspension_revokes_sessions_blocks_sign_in_and_gates_cli_tokens` and the `db-tests` token-repo contract walk on both backends.
>
> **S-13.b — "per-token rate limits" means the token is a rate-limit identity** (added 2026-08-14, closes the last unimplemented clause of S-13 — see [decision 27](decisions.md#27--rate-limit-identity-what-a-bucket-is-keyed-on-and-what-happens-when-the-kv-is-down)). Until now every bucket on the token plane was keyed on the client IP, which meant the sentence above described nothing that existed.
>
> - **A presented CLI token is bucketed as itself**, under `rl:read:tok:{sha256(secret)[..16]}` — sixteen hex characters of the same hash the database stores, never the secret and never the whole hash. A collision merges two tokens' budgets, which can only refuse more.
> - **Identity is decided by the offline gate, not by a lookup.** `token::validate` (prefix, length, charset, CRC32) is the same check `authenticate_cli_token` runs before it touches the database, so the middleware adds no query to the hot path. The consequence is explicit: an attacker can mint unlimited CRC32-valid strings and therefore unlimited buckets. That is bounded, on the only plane where it is reachable, by `token_auth_fail_per_ip_minute` (30/min/IP, S-14.a) — a request carrying an unknown token fails authentication and spends it. **A plane that ever accepts CLI tokens without spending that budget re-opens this**, and is the reason the coupling is written down here rather than left in a comment.
> - **The budget is `read_per_identity_minute`** and it fails **open** (S-24.f): a token's read quota is a quota, not the credential check. The credential check is S-13.a's, and it fails closed.

> **S-13.c — the two optional clauses of this requirement become reachable, and "default expiry 90 days" stops being a server default** (added 2026-08-15 with [decision 33](decisions.md#33--reaching-the-mechanisms-that-already-exist-the-token-model-on-the-wire-an-operator-surface-for-the-supply-chain-registers-and-errors-that-say-what-the-server-said); closes roadmap D19).
>
> `patterns_allow` narrows publish at finalize and narrows reads of private packages on the pub plane, and `expires_at IS NULL` has always meant non-expiring — but `mint_token` wrote an empty pattern list and an expiry unconditionally, so **neither clause described anything a caller could ask for**. What changes:
>
> - **`expires_days` is explicit on the wire**: an integer in `1..=3650` is a lifetime in days, `null` is non-expiring, and `0` is refused. The 90-day default is now the value the UI pre-fills and sends, not a server fallback for an absent field — before this, `null` meant 90 days, which is why "unlimited allowed only for `read`" had no spelling. This is a **change of meaning for a shipped field** and is recorded as such in [decision 13](decisions.md#13--cliapi-token-format).
> - **"Unlimited allowed only for `read`" is enforced at the mint**: `null` together with `publish`, `retract` or `admin` is a permanent 400 (`invalid_argument`). A non-expiring token carries the `read` scope and nothing else.
> - **A non-expiring mint is step-up gated at every scope** ([S-06.d](#1-authentication)). The two guards exist together so an old client that omits the field meets a 400 or a 403 instead of quietly receiving an eternal credential; the only request whose meaning changes silently is a step-up-fresh, read-only mint, which is a thing a caller can reach only by asking for it.
> - **Patterns are validated against the matcher that enforces them.** One trailing `*` (prefix match) or an exact name; refused: a leading or interior `*`, more than one `*`, a bare `*` (an empty list already means "no narrowing"), an empty pattern, anything over 64 characters, any character outside `[a-z0-9_]` after the trailing `*` is stripped, and more than 32 patterns. Deduplicated, order preserved. The reason to refuse rather than store is that a pattern the matcher cannot satisfy is not a narrower token but a token that authorizes **nothing**, discovered by its owner at the first CI publish. The grammar is checked; the intent is not — `acme_x*` for packages named `acme_y*` mints happily, which is why `TokenDto` now carries `package_patterns` and the token list renders them.

**S-14** 401 vs 403 discipline on pub routes: **both** statuses carry `WWW-Authenticate: Bearer realm="pub", message="<actionable text>"` — the client surfaces the message in the CLI on 401 *and* 403, and it is our only messaging channel there (how to get a token / how to request access). 401 **only** for absent/invalid tokens (the client deletes its stored token on 401); 403 only for valid-but-insufficient scope/role on a resource the principal can see; unreadable resources are 404 per S-04.

> **S-14.a — the ladder as implemented, and the two things that must not be forgotten** (added 2026-08-07 with the pub protocol surface). The mapping lives in exactly one place (`api/src/protocol/error.rs`); handlers pick a constructor, never a status code.
>
> - **The challenge is built, not concatenated.** `message` is assembled from package names, org slugs, and backend text, so it is sanitized into a header value: quotes and backslashes replaced, control and non-ASCII characters dropped, truncated to 1024 characters. If the result still cannot become a header value the bare `Bearer realm="pub"` is sent — the challenge is never omitted, because a 401 without it leaves the CLI with a deleted token and no explanation. A **404 never carries a challenge**: hinting that a credential would help is the same enumeration leak the 404 exists to prevent.
> - **Permanent failures are 4xx by construction, `Conflict` included.** The pub client retries 408, 429, and every ≥500 up to seven times, so a doomed request answered with 5xx is hammered six more times for nothing. `Conflict` maps to **400**, not 409, because the finalize step's whole contract is `200 {"success":…}` or `400 {"error":…}`; a unit test walks every permanent variant and asserts none reaches 5xx.
> - **Failed token authentications spend an S-24 budget** (30/min/IP, `auth.rate_limit.token_auth_fail_per_ip_minute`), after which the answer becomes **429 + `Retry-After`** rather than another 401. That is not only abuse control: an attacker spraying an IP would otherwise be able to make a legitimate co-located client delete its stored token on every request it makes.
> - Success is unthrottled by that bucket. The pub client sends its credential on *every* resolve and *every* download, so counting successes would rate-limit ordinary `pub get` traffic.
> - **A 401 must never be an authorization outcome.** Because the CLI deletes the credential, every denial that is *not* about the credential itself — missing scope, wrong org, insufficient role, a name held elsewhere, an unreadable package — is 403 or 404. `protocol.rs::a_valid_credential_is_never_answered_with_401` walks that matrix. Confirmed against the real client: a 401 prints `Invalid token for … deleted.`, while a 403 prints our message and leaves the token configured. For the same reason the `Bearer` scheme is matched **case-insensitively** (RFC 9110 §11.1) — header casing must not cost a developer their credential.
>
> **S-24.c — the publish budget** (added 2026-08-07 with the registry conformance review; S-24's "publish 30/h/org" was previously unimplemented). The budget is `registry.rate_limit.publish_per_hour_org` (default 30) and is spent by the **upload** step, not by step 1 or finalize: the upload is the step that costs storage, it is reachable directly (its URL is a fixed path, not a capability), and charging step 1 would bound nothing while charging finalize would bound it too late. Trips are `429 + Retry-After` — a status the pub client retries, which is the correct behavior for a window that will reopen — and are audit-logged as `package.publish.throttled` with the org and the token that spent it (S-22). A KV outage **fails open** with a loud log line: this bucket rides an already-authenticated, already-authorized write, so an outage that lifted a quota is a smaller failure than one that closed publishing instance-wide. That is the opposite stance from the auth-abuse buckets, where failing open would grant access rather than lift a quota.
**S-15** Secret-scanning support: published token regex + checksum algorithm in docs; gitleaks rule shipped; GitHub Secret Scanning partner registration later.

## 4. Supply chain & registry integrity

**S-16** Deterministic resolution: local (claimed) names always win over upstream; resolution never chooses by version across sources; per-org upstream policy (`allow` now, `delay`/`allowlist` later).

> **S-16.a — "local always wins" has exactly one door, and the policy is a column** (added 2026-08-07 with the read-through proxy).
>
> - The proxy is reachable from **one** expression in the codebase: the `Resolution::Unclaimed` arm of `resolve_target` in `api/src/protocol/pub_v2.rs`. `Unclaimed` itself is produced on one path (after `lookup_claim` returned `None` — S-16 addendum to decision 01), and the arm *carries* the `UpstreamService` reference, so a handler that wanted to proxy a claimed name would have to obtain the service some other way and there is none. A claim with no published package is still local and is never proxied — otherwise a reserved name could be handed to whoever registered it publicly.
> - **Versions are never merged across sources.** A proxied listing is upstream's version set, a local listing is ours, and no code path produces a union. `proxy.rs::s16_a_locally_claimed_name_never_falls_through_to_upstream` publishes `acme_core 1.0.0` locally while upstream advertises `acme_core 9.9.9` and asserts the listing contains exactly `1.0.0` **and that upstream was never contacted at all** (the mock's call count is 0) — the version-based race this requirement forbids cannot even be attempted.
> - Per-org policy is `orgs.upstream_policy` (`allow` | `block`, migration 0005), enforced in `upstream_for()` alongside the instance-level `[upstream].enabled`. A blocked org answers 404 for an unclaimed name, identical to an unknown one (S-04).
>
> **S-16.b — `block` is a property of the base, not of the principal** (added 2026-08-07 after the proxy adversarial review). `upstream_for()` reads the policy of the org whose *URL* the request arrived on. The public root has no org and therefore follows the instance switch alone ([decision 01](decisions.md#01--per-org-virtual-registry-urls)), so a developer in a blocked org who points `PUB_HOSTED_URL` at `https://host/pub` instead of `https://host/o/acme/pub` resolves upstream packages normally — verified live: the same name answers 404 under `/o/acme/pub` and 200 under `/pub` for the same token. This is coherent (the base *is* the namespace, decision 01) but it is not what "per-org upstream policy" sounds like, so it is written down: `block` is a **default for the org's registry URL**, not a control that prevents the org's members from consuming upstream packages. The only setting that does the latter is instance-wide `[upstream].enabled = false`. If per-principal enforcement is ever required it needs the policy evaluated against the *token's* org rather than the base's — a different rule, with its own consequence that one `pubspec.lock` would then resolve differently per developer, which decision 01 rejects.
**S-17** Shadowing alarm: if a locally-claimed name appears upstream, keep serving local and alert org admins + audit.

> **S-17.a — the two arrival orders, and why one of them needs the mirror** (added 2026-08-07 with the mirror worker).
>
> - **Detection has exactly one implementation and two callers** (`registry/src/shadow.rs`). The condition — a name claimed here that also exists upstream — arrives in two orders, and each is visible in exactly one place. A **publish** claiming a name the proxy already caches is seen in the publish pipeline, on the first publish of that name, as one indexed read. Upstream **starting** to carry a name we already claim is seen only by the mirror sweep, because the read path structurally never asks upstream about a claimed name (S-16) — there is no request whose answer could reveal it. That is why `full` mode re-enumerates on `resweep_after` instead of sweeping once: a mirror that enumerated only at startup would go permanently blind to this half.
> - **Serving does not change, before or after.** The alarm is a notification register (`shadowing_alarms`, one row per shadowed name), not a policy switch: the local package won by decision 01 before the alarm existed and keeps winning after it, and acknowledging an alarm is bookkeeping. Anything else would make an admin click a button to keep serving their own package. `proxy.rs::s17_claiming_a_proxied_name_alarms_and_the_local_package_still_wins` asserts the listing is unchanged across the whole cycle, acknowledgement included.
> - **An alarm is raised once per incident, then counted.** `record_shadowing` reports whether this observation *raised* the alarm — a first sighting, or the first after an acknowledgement — and only a raise writes the `upstream.shadowing` audit event and emits the domain event. Without that, an hourly sweep would re-page the same admins for as long as the condition holds, which is how an alarm channel stops being read. A sighting after an acknowledgement is a **new incident**: it raises again and resets `first_seen_at`, so an admin who cleared it hears about it coming back.
> - **The audience is the claim holder.** `DomainEvent::PackageShadowed` carries the claiming org (unlike the S-19 alarms, which are instance-scoped) and the `security` notification category, because only that org can judge whether the upstream namesake is a squat, a coincidence, or their own open-source release. A name **claimed but never published** shadows too — it is precisely the name somebody is holding *for* a release.
> - **A shadowed name is never mirrored.** The sweep observes it and skips it: caching a package resolution can never serve is storage spent on a supply-chain hazard.

> **S-17.b — the register an operator can page through, and the one write it has** (added 2026-08-15 with [decision 33](decisions.md#33--reaching-the-mechanisms-that-already-exist-the-token-model-on-the-wire-an-operator-surface-for-the-supply-chain-registers-and-errors-that-say-what-the-server-said); closes roadmap D26 together with [S-19.b](#4-supply-chain--registry-integrity)).
>
> "Alert org admins + audit" was implemented; *reading the register afterwards* was not. The admin dashboard showed the newest twenty rows inside `/admin/stats` and offered no way past them, no active-only filter, and no way to acknowledge — which meant `acknowledge_shadowing`, implemented in both dialects and contract-tested, was reachable from tests alone.
>
> - **`GET /api/v1/admin/shadowing`** is instance-admin and keyset-paginated over `(last_seen_at, format, name)`, newest sighting first, with an optional `active` filter. The cursor carries the whole primary key on purpose: one mirror sweep stamps every alarm it raises with the same instant, so a cursor of `last_seen_at` alone would skip or repeat rows exactly when a sweep raises several at once.
> - **`POST /api/v1/admin/shadowing/{format}/{name}/acknowledge`** is instance-admin and audited as `upstream.shadowing.acknowledged` **with the acting administrator, their IP and their user agent**. The service's existing audit helper hard-codes `AuditActor::System` and `AuditResult::Failure` — correct for the integrity events it was written for, wrong for a person's action — so the operator path takes an actor-carrying variant. Acknowledging an already-acknowledged alarm answers 200 with `acknowledged: false` and writes no row.
> - **It is not step-up gated** (S-06.b's rule: the list is about escalation). It grants nothing, deletes nothing and changes no resolution, and the next upstream sighting raises the alarm again as a new incident.

**S-18** Immutability: versions immutable, numbers never reused (tombstones survive hard delete); archives byte-stable forever; blob store is content-addressed by sha256.

> **S-18.a — serving the bytes: a presigned URL is a bearer capability, and the integrity claim is not the transport** (added 2026-08-16 with [decision 34](decisions.md#34--presigned-downloads-the-redirect-branch-becomes-reachable-off-by-default-and-honest-about-the-address-a-client-can-dial); closes roadmap D11).
>
> - **The S3 backend MAY answer an archive request with `307` to a presigned URL**, and does so only when `blob.presign` is explicitly on. The URL is signed for the request's own method — SigV4 covers the method, so a `GET`-signed URL refuses the `HEAD` the pub client sends before every archive fetch — and for `blob.presign_ttl_secs`, bounded to `1500..=604800`: the floor is [sharp edge 4](protocol.md#sharp-edges-violate--break-clients)'s ≥25 minutes for retries and clock drift, the ceiling is SigV4's own limit.
> - **A signed URL is a bearer capability for those seconds.** Anyone holding it reads that archive, with no token, no session and no visibility check — the authorization decision was made once, when the redirect was issued. Two consequences are normative rather than incidental: the redirect response carries `Cache-Control: no-store` so no shared cache retains the capability, and the S-24.f read bucket is spent at the redirect, so the bytes themselves leave outside our rate limit. An instance that cannot accept the second property leaves `blob.presign` off, which is the default.
> - **No `Authorization` may reach the object store.** The client keeps its bearer token across a *same-origin* redirect (`dart:io`, verified on Dart 3.12.2) and S3 refuses a request carrying both a header credential and a query signature. The signing origin therefore MUST differ from `server.public_url`'s origin, and boot refuses the combination rather than warning about it.
> - **A signed URL outlives revocation, and this is the requirement it bends.** [S-13](#3-cliapi-tokens) promises token revocation is effective within 60 seconds, and it still is for every request that reaches this instance — but a URL already handed out is answered by the object store, which has never heard of our tokens. Revoking a token, suspending a user or making a package private therefore does **not** reach a redirect issued before the change; those bytes stay fetchable for up to `blob.presign_ttl_secs`. The floor of 1500 s means the shortest achievable window is 25 minutes, so this is a property of presigning and not a number an operator can tune away. An instance whose threat model needs revocation to reach the bytes leaves `blob.presign` off, which is the default.
> - **The URL carries the access key id, which our own config types as a secret.** SigV4 query signing puts `X-Amz-Credential=<access-key-id>/<date>/<region>/s3/aws4_request` in every URL, so `blob.access_key` — masked in the startup summary under [S-25](#6-secrets--configuration) — is published to every client that downloads an archive. That is by AWS's design and is not an exposure of `blob.secret_key`, which never leaves the process, but it means the key id must be treated as public once presigning is on: it must not double as an identifier anywhere else, and it is one more thing a KEK/credential rotation has to reach.
> - **The integrity claim is unchanged and lives in the listing, not in the transport.** `archive_sha256` is what the client verifies and what lands in `pubspec.lock` (S-18, [sharp edge 3](protocol.md#sharp-edges-violate--break-clients)); S-19's serve-time re-verification stays structural because the blob key *is* the content hash, so a redirect can only ever point at the bytes that hash to the number already published. What the redirect gives up is observation, not verification: the app no longer sees the bytes leave, so a missing object is the store's own 404 at the client rather than ours.

**S-19** Proxy integrity: verify upstream `archive_sha256` at ingest; re-verify from own store on serve; upstream byte-drift for a known version ⇒ serve cached, alert, quarantine the discrepancy.

> **S-19.a — the proxy's integrity rules as implemented, and the two accepted residues** (added 2026-08-07 with the read-through proxy).
>
> - **Hash before store.** The sha256 is computed over the fetched bytes and compared with the value upstream advertised in its listing *before* anything reaches the blob store. A mismatch is a **quarantine**: never stored, never served, audited as `upstream.quarantine` with both hashes, emitted as an instance-scoped domain event, and answered to the client as a 404 (a permanent 4xx — sharp edge 2). The version stays uncached, so a later honest answer can still be ingested. Since 2026-08-07 it is also **listable**: the refusal is recorded in `upstream_quarantine`, one row per `(format, name, version)` with an occurrence counter, because a package under active tampering is fetched by every developer on the team and a row per attempt would bury the signal. The register is evidence, never enforcement — the bytes were refused before it is written, so a failure to record loses the trail and never the containment.
> - **Byte-drift freezes, it does not overwrite.** Once a version is `cached`, its `archive_sha256` — and the `archive_size` measured while caching — are immutable. A later listing advertising a different hash is audited as `upstream.drift`, alarmed, and *discarded*; the cached bytes keep being served, because somebody's `pubspec.lock` pins that hash. This is enforced twice on purpose: the service computes the preserved value, and the repositories' upsert independently keeps it (`CASE WHEN cached THEN … END` in both dialects), so a future caller cannot reintroduce the overwrite. A version we have **not** cached has nothing pinned to it, so a changed hash there is upstream correcting itself, not drift.
> - **A listing is validated with the publish-path validator.** Each version's pubspec goes through `Pubspec::from_json` — the same name, version, and depth rules a local upload clears (S-20) — and must agree with its own entry on both name and version; `archive_sha256` must be 64 lowercase hex or the version is dropped; a listing that names a package other than the one requested is refused outright, because an upstream able to answer `foo` with `bar`'s versions substitutes a dependency wholesale and the hash check would confirm bar's own bytes quite happily. Listing bodies are capped (`upstream.max_listing_bytes`) while they arrive.
> - **Fetching a URL upstream chose is SSRF surface.** `archive_url` and every redirect are checked with S-33's ruleset: https only (plain http is dev-mode only, and the config validator refuses a plaintext upstream in production because the listing carries the hash we verify against), no user-info, and no loopback/private/link-local/unique-local/CGNAT destination — `169.254.169.254` included. The *configured* upstream host is exempt, because a corporate mirror on a private address is a legitimate deployment and the rule exists to constrain hosts **upstream** picks. Redirects are capped at 5, and a configured bearer token never follows a cross-host hop. Address literals are covered in every notation, because WHATWG host parsing normalizes `2130706433`, `0x7f000001`, and `127.1` to `127.0.0.1` before the guard runs — a property of the `url` crate, and therefore pinned by a test rather than assumed.
> - **Special-use *names* are refused, not only special-use addresses** (added 2026-08-07 after the proxy adversarial review; the previous rule missed them). The guard runs before DNS, so blocking `127.0.0.1` and `169.254.169.254` while allowing `localhost` and `metadata.google.internal` left the same destinations reachable by name — one `archive_url` away from the GCP metadata server. Names reserved by standard or convention for loopback and private use are now refused for hosts **upstream** picks: `localhost` and `*.localhost` (RFC 6761), `*.local` (RFC 6762 mDNS), `*.internal` (ICANN's 2024 private-use delegation, where GCP's metadata server lives) and `metadata.goog`, and `home.arpa` (RFC 8375). The configured host is exempt before this is reached, so `https://packages.corp.internal` remains a supported mirror.
> - **Only *reachability* failures reach the circuit breaker** (added 2026-08-07 after the proxy adversarial review). The breaker is instance-wide: whatever opens it degrades every package to stale-or-404 for the whole window. It previously counted every non-404 failure, so a listing our own validator refuses, or one past `max_listing_bytes`, was treated as an upstream outage — and the pub client re-fetches a listing before *every* resolve, so a single CI job depending on a single such package would open the circuit for the whole instance, repeatedly. Upstream answering promptly and in full with a document we cannot use is a fact about **that package**, exactly like a 404, and is now counted as a fetch outcome (`upstream_fetch_total{outcome="unusable"}`) and nothing more. Symmetrically, the archive path — which holds a concurrency permit longest — now *does* feed the breaker on transport failures; with a warm listing cache and a dead archive host, nothing else reached upstream at all, so no circuit could ever open and every download paid its full retry budget and timeout.
> - **A body that stops short of its own `Content-Length` is a transport failure, and is named as one** (added 2026-08-07 after the proxy adversarial review). Hash-before-store already made a truncated download harmless — short bytes hash to something else, so they are never stored — but reaching that conclusion through the hash check filed a dropped connection in the quarantine register as tampering and emitted a `security`-category alarm for a network hiccup. The length is now compared explicitly and a short body is `Unavailable`, which also makes the containment a property of this pipeline rather than of the HTTP client underneath it. The version stays ingestible, so the next honest answer caches normally.
> - **`Content-Length` is upstream's claim, and is not allowed to become an allocation** (added 2026-08-07 after the proxy adversarial review). The archive buffer was pre-sized from the advertised length, so an upstream announcing `max_archive_bytes` and then sending nothing cost a full archive cap of resident memory per in-flight fetch — 100 MB × `max_concurrent_fetches` by default, held for as long as the archive timeout allows. The hint is clamped to 1 MiB; `Vec`'s amortized growth pays for genuinely large archives. Slow-loris bodies themselves are bounded by the whole-request timeout, which `reqwest` applies to the streamed body and not only to the response head (verified in 0.12.28).
>
> Two residues are accepted and recorded here so a future change is measured against a known baseline:
>
> - **"Re-verify from own store on serve" is satisfied structurally, not by re-hashing.** Blobs are content-addressed: the serve path can only express "give me the bytes stored under this sha256", so returning wrong bytes would require the blob store to answer a key with content that is not its own hash. Re-hashing every archive on every download would put a full SHA-256 pass on the hottest byte path in the system for a threat the key already excludes. **Planned**: an explicit rehash sweep rides the unreferenced-blob GC job, where it is amortized rather than per-request.
> - **Upstream archives are size-capped and hash-verified, but not structurally validated.** The S-20 tar/gzip validator is *not* run over proxied bytes. They are stored and served verbatim, and pub.dev's 60 000 packages were produced by many tar writers over a decade; rejecting the ones our stricter rules dislike (duplicate entries, trailing data) would make the proxy unusable while protecting nothing — we never extract an archive, and proxied packages take no README-rendering path. What *is* enforced is `upstream.max_archive_bytes`, checked against the advertised `Content-Length` and again while streaming. **Revisit** if proxied archives ever gain a server-side consumer that reads inside them.

> **S-19.b — the quarantine register becomes readable past its newest twenty rows** (added 2026-08-15 with [decision 33](decisions.md#33--reaching-the-mechanisms-that-already-exist-the-token-model-on-the-wire-an-operator-surface-for-the-supply-chain-registers-and-errors-that-say-what-the-server-said); closes roadmap D26 together with [S-17.b](#4-supply-chain--registry-integrity)).
>
> **`GET /api/v1/admin/quarantine`** is instance-admin and keyset-paginated over `(last_seen_at, format, name, version)`, newest observation first. The whole primary key is in the cursor for the same reason as S-17.b's and a sharper one: a tampering incident across a package's versions writes a block of rows inside one fetch loop, so ties on `last_seen_at` are the *normal* shape here, not the edge case. The register stays evidence and never enforcement — it is written after the bytes were already refused — so nothing in this surface can change what the proxy serves. There is no acknowledge and no delete: an operator's remedy for a quarantined package is upstream's problem or a local publish of the name, and a row that could be cleared from the UI would be a row an attacker with an admin session could clear.

**S-20** Ingest hardening: archive size cap (100 MB default, configurable), safe tar extraction (reject path escapes, duplicate entries; skip external symlink/hardlink targets), pubspec must parse and match name/version; configurable per-org storage quota enforced at publish.

> **S-20.a — the ingest limits as implemented, and the amplification vectors they close** (added 2026-08-07 with the registry slice). "Safe extraction" understates it: the archive is **never extracted**, to disk or otherwise. It is streamed gzip → byte counter → tar reader, and only four small files are lifted out (`pubspec.yaml`, `README`, `CHANGELOG`, the example document); every other entry is walked past with its bytes counted and its content dropped.
>
> - **Enforced while decompressing, not after**: compressed size (`registry.max_archive_bytes`, default 100 MB, checked before any CPU is spent), total decompressed size (`max_uncompressed_bytes`, default 256 MB), entry count (`max_entries`, default 10 000), expansion ratio (`max_compression_ratio`, default 100×, applied above a 1 MiB floor so ordinary small packages are not mistaken for bombs), and per-captured-file size (`max_captured_file_bytes`, default 4 MiB). A bomb dies mid-stream, at the limit, never at the allocation.
> - **Rejected outright**: `..` in any path component, absolute paths (POSIX and `C:/`), backslash separators, NUL bytes, non-UTF-8 paths, duplicate entries after normalization (`./x` and `x` are the same entry), symlinks/hardlinks whose target escapes the archive, and a missing or non-root `pubspec.yaml`. Internal links are allowed — they are ordinary package content. `./`-prefixed paths normalize rather than fail (GNU tar writes them). Attacker-controlled paths are clipped before they enter an error message.
> - **The bytes we validate are all the bytes we store** (added 2026-08-07 after the registry conformance review; the previous implementation failed this). A tar reader stops at the end-of-archive marker and a single-member gzip reader stops at the end of member one — so an archive could carry a second concatenated gzip member (which `tar -xzf` happily decodes) or a payload past the zero blocks (which `tar --ignore-zeros` walks into), and the validator would have inspected a *prefix* of what we then stored and served forever. Both are closed by one rule: the stream is decoded **multi-member** and **drained to EOF**, and every byte after the marker must be NUL padding, or the publish is rejected (`TrailingData`). Honest padding passes — `package:tar` writes 1 KiB of zeros, GNU/bsdtar up to a 10 KiB blocking factor; verified against archives produced by the real `dart pub publish` (465 bytes of zero padding). The drain reads through the same limiting reader, so a bomb parked in the tail trips the size and ratio caps instead of being a free decompression budget.
> - **The YAML parser is part of the attack surface.** A pubspec is untrusted input, so it is parsed with `yaml-rust2` (pure safe Rust, no `unsafe-libyaml` lineage) at the **event level**: an `Alias` event is rejected instead of expanded. Every DOM/serde YAML loader materializes aliases by copying, which turns a few KiB of nested anchors ("billion laughs") into gigabytes — the same amplification class the archive limits close one layer down. Mapping depth is capped at 32.
> - **Every rejection is a permanent 4xx** carrying a typed reason, never a 5xx: the pub client retries 5xx up to 7 times ([protocol.md sharp edge 2](protocol.md#sharp-edges-violate--break-clients)), so a doomed upload must not look retryable.
> - **The per-org storage quota named above is implemented** as of 2026-08-14 — see [S-20.b](#4-supply-chain--registry-integrity). Until it landed, the *only* bound on what an org could park in storage was the S-24 publish budget below plus the archive cap (30 × 100 MB/h by default).
> - **The abandoned-upload sweep runs on a default install** (landed 2026-08-07 inside the blob-GC job; moved to its own job and switched on by default 2026-08-14, [decision 31](decisions.md#31--blob-lifecycle-staged-uploads-swept-by-default-and-an-archive-gc-that-streams-batches-and-resumes)). Staged bytes under `uploads/<format>/<session>.tar.gz` outlive their KV record, which expires after an hour; `staging-sweep` collects them by **age alone** — once the record is gone, `newUploadFinish` answers "expired or already finalized", so a staged object older than the grace period (default 2 h, validated to exceed the 1 h TTL) can no longer be finalized by anybody. Deliberately not by consulting the KV record: that would couple the job to a key format owned by the protocol module, and age is the stronger test anyway. Only `uploads/<format>/<32 lowercase hex>.tar.gz` is recognized as sweepable; anything else under that prefix is reported and left alone. Until 2026-08-14 this rode the unreferenced-archive collector, which ships disabled and dry-run (decision 06 addendum) — so on a default install these bytes were never collected at all ([D22](roadmap.md)), and the only bound on the pile was the S-24 publish budget times the archive cap.
> **S-20.b — the per-org storage quota: what it counts, where it refuses, and how loose it is** (added 2026-08-14 — [decision 32](decisions.md#32--quotas-and-limits-what-an-org-may-store-what-a-caller-may-write-and-one-identity-per-request), closes roadmap D21).
>
> - **What counts**: the sum of `archive_size` over the org's **live** version rows (`tombstone = 0`). Retracted versions count — they are still downloadable, so their bytes are still stored. Tombstoned versions do not; a hard delete is how an org frees space. Proxied upstream archives never count, because `upstream_versions` has no org and one org's fetch caches for the whole instance. Staged uploads do not count either — they are swept, and a quota that flapped with in-flight publishes would refuse the retry of the upload that caused it.
> - **Deduplicated bytes are over-counted deliberately.** Blobs are content-addressed, so two orgs publishing identical bytes share one object and are each charged for it. The alternative makes one org's quota depend on another org's behaviour. This is the stance `RegistryStats::archive_bytes` already takes for the instance-wide number.
> - **Three checkpoints, none redundant** (amended 2026-08-14 — the requirement first named two, and this wave's review found package **transfer** moving storage between orgs with no check at all: bytes are attributed by the package's current org, so a transfer re-attributes every version at once, unbounded and repeatable. A transfer the receiving org has no room for is now the same permanent 400). The authoritative refusal is at **finalize, immediately before the blob write**. A second check at **upload, before the staged write** bounds what finalize structurally cannot: staged bytes survive the two-hour staging grace, so an org already over quota would otherwise park `publish_per_hour_org × max_archive_bytes` per hour in the store.
> - **The refusal is a permanent 400** (`invalid_argument`), never 429: per [sharp edge 2](protocol.md#sharp-edges-violate--break-clients) a retryable status is a lie the pub client acts on seven times, and no amount of waiting frees space.
> - **The bound is loose by a stated amount.** The publish lock is per package name, not per org, so N concurrent publishes of different names each read the same usage; the reachable overshoot in **stored** bytes is `quota + (concurrent publishes × max_archive_bytes)`. Staged bytes are a separate and larger term (amended 2026-08-14): an org *under* its quota passes the upload guard every time, so it can hold `publish_per_hour_org × max_archive_bytes` per staging grace period on top — 30 × 100 MB × 2 h on defaults, from a single-threaded client that never finalizes. Those bytes are swept and deliberately uncounted; an operator sizing a volume needs both terms. Closing it needs a maintained counter inside the version-creating transaction in both dialects, which trades a stated overshoot for undetectable drift.
> - **Configuration**: `registry.storage_quota_bytes`, default `0` = unlimited, runtime-changeable; `orgs.storage_quota_bytes` is a nullable per-org override, and the effective limit is the override or the instance default. `NULL` follows the instance default, `0` is unlimited for that org whatever the instance default is, and nothing expresses "may store nothing" — that is what archiving an org is for. **Only an instance admin may set the override** (`PATCH /api/v1/admin/orgs/{id}`) — a quota an org can raise for itself is not a quota.
> - **Crossing 80 % of the effective quota emits one event, on the edge**, not on every publish above the line; the audience is the org.

**S-21** Provenance-lite: record publisher identity, token id, and CI metadata per version; surfaced in UI and audit. (Sigstore/SLSA attestations: later.)

## 5. Audit & abuse

**S-22** Append-only audit log: INSERT-only DB role; events — auth success/failure per method, MFA enroll/disable, throttle trips (incl. invitation throttles), session/token lifecycle, publish/retract/hard-delete, package settings, org/membership/invitation changes, admin settings changes, proxy policy changes, shadowing alarms, data-export requests, account-deletion requests/completions. Record: ULID, ts, actor (user|token|system), IP, UA, org, dot-namespaced action, target, result, metadata (before/after). Never log secrets, full tokens, or OTP codes.
> **S-22.a — the INSERT-only role keeps no DELETE, and retention still runs automatically** (added 2026-08-14 with [decision 30](decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature)).
>
> S-23's retention needs a delete on the one table this requirement forbids deleting from, and the naive resolutions both lose something real: granting the app role `DELETE ON audit_log` hands a code regression or an injection exactly the recent rows an attacker wants gone, and moving retention out of process means a default install grows forever. Neither is necessary. On Postgres the app role's `REVOKE UPDATE, DELETE, TRUNCATE ON audit_log` **stands unchanged**; retention calls `pub_audit_prune(cutoff, batch)`, a `SECURITY DEFINER` function owned by the migration role, on which the app role holds only `EXECUTE`. The application refuses any cutoff newer than **30 days** and the config validator refuses a retention window below that, so the reachable capability is "delete audit rows older than a month in bounded batches" and nothing wider. The DB-level property this requirement asserts therefore narrows precisely: no `UPDATE`, no `TRUNCATE`, and no deletion of anything recent. SQLite has no roles, so there the `AuditRepo` surface — one batched `prune_before` and no update — remains the whole enforcement, as it always has been.
>
> Three properties of that function are load-bearing and are asserted by a Postgres test that provisions a role from the 0002 template and connects as it:
>
> - **`search_path` is pinned with `pg_temp` demoted, and every table reference is schema-qualified.** The pin alone is not enough — Postgres searches an implicit `pg_temp` first for relation names — so a caller could shadow `audit_log` with a temp table and turn the prune into a silent no-op that still reports a row count. That direction preserves evidence rather than destroying it and is not an escalation path (the app role holds `USAGE`, not `CREATE`, so it has nowhere to put a trigger function, and rule actions are checked against the rule's owner), but a retention job that reports success while deleting nothing defeats the point of the signal.
> - **The function's own floor is 29 days, one day looser than the application's 30.** A backstop set to the same instant as the primary is a defect: `INTERVAL '30 days'` is calendar arithmetic while the application's window is exactly 720 h, so a DST transition or ordinary clock skew between hosts makes a legal configuration fail every pass.
> - **`EXECUTE` is revoked from `PUBLIC`.** Otherwise every role that can reach the database holds the prune capability over this instance's audit log — moot on a single-tenant deployment, a real widening on a shared cluster.
>
> A refused `EXECUTE` (the expected state on a hardened Postgres until the grant is added) disables audit retention with a named log line, a gauge and a durable job-state failure — never a silent skip, and never a tick that stops purging the other tables.

**S-23** Retention: **one uniform window per table**, in days, `0` meaning keep forever — audit log 730 d (≈24 months) by default, sessions 30 d, invitations 30 d, notifications 180 d, the work queue per its own per-state windows. Version tombstones and daily download rows are excluded by design (a tombstone is what keeps a hard-deleted version number unpublishable per S-18; download rows are chart data whose bound is a roll-up, not a purge). Every retention delete is batched and converges across passes; one leader-locked lifecycle job owns all of them. Export: `GET /api/v1/admin/audit/export` streams NDJSON over a keyset walk, resumable by cursor, terminated by an explicit `{"done":true,"count":N}` line so a truncated export is detectable; instance-admin, step-up gated (S-06.c), audited as `audit.export`, and bounded by a budget of its own (12/hour/administrator) rather than by the S-24.f read bucket — 3000 reads a minute is the right number for `dart pub get` and the wrong one for a statement that walks the whole table.

> **S-23.a — why the audit window is one number and not three** (added 2026-08-14 with [decision 30](decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature); supersedes this requirement's original "auth 12 mo, admin/role 24 mo, publish = package lifetime").
>
> Three windows over one table mean one viewer whose history depth silently depends on which action you filtered for, and three numbers to configure for one feature. The uniform 730-day window is safe because **provenance is not in the audit log**: `versions.published_by`, `published_by_token` and `published_at` are columns on the version row (S-21), so purging a two-year-old `package.publish` event drops the access record and never the provenance — the claim "publish events = package lifetime" was protecting data that lives somewhere else. An operator with a longer statutory obligation raises the one number, or exports.

> **S-23.b — the two supply-chain registers come under retention, and the windows are not load-bearing** (added 2026-08-15 with [decision 33](decisions.md#33--reaching-the-mechanisms-that-already-exist-the-token-model-on-the-wire-an-operator-surface-for-the-supply-chain-registers-and-errors-that-say-what-the-server-said)).
>
> `upstream_quarantine` and `shadowing_alarms` were the last two tables in the instance that grew without a bound. Both now carry a window, `retain_quarantine_days` and `retain_shadowing_days`, defaulting to **730** — the audit log's number, because these rows are evidence of the same class, and evidence of an attack is recent. Deletion is batched, looped and budgeted like every other retention delete, and both tables are reported by the same pass.
>
> What makes a badly set window harmless is **what the rows age from**, not the number:
>
> - a **quarantine** row ages from `last_seen_at`, so a mismatch still being observed is outside every window at every setting; only a register entry nobody has re-triggered for the whole window can be deleted;
> - a **shadowing** alarm ages from `acknowledged_at`, and an **active alarm is undeletable at every setting** — the same shape as a pending invitation under [decision 30](decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature). Deleting an active alarm would be worse than losing a row: the mirror sweep re-raises it on the next pass with a fresh `first_seen_at` ([S-17.a](#4-supply-chain--registry-integrity)), so retention would silently rewrite the incident's start date and tell an admin the shadowing began this morning.
>
> `download_stats` remains the one window shipped disabled, for the reason S-23 already gives.
**S-24** Rate limiting (KV-backed, per-IP / per-account / per-token / per-org): OTP request 5/h/email + 20/h/IP; OTP verify 5/code; TOTP/recovery/step-up verify ≤5 failures then exponential backoff (per S-05); login 10/min/IP; token-auth failures 30/min/IP then tarpit; publish 30/h/org; invitations ≤20/day/org with per-actor caps; 429 + `Retry-After`; health checks exempt. KV-outage semantics: auth-abuse limiting fails **closed** via a per-instance in-process fallback; read-path limiting fails **open**. Anti-lockout: exponential backoff + device-cookie style trust, never account hard-lock from IP-driven failures; notify users on failure bursts.

> **S-24.a — trusted-proxy stance: the client IP is not a header** (added 2026-08-06 after the auth-slice security review; the previous behaviour was unspecified). Every per-IP limit is only as strong as the identity it is keyed on, and `X-Forwarded-For` is attacker-controlled unless something trustworthy wrote it.
>
> - The instance setting `server.trust_proxy_headers` defaults to **false**. In that mode forwarding headers are ignored entirely and the **socket peer address** is the client identity (the server is started with connect-info so the peer is available). A caller cannot mint fresh rate-limit buckets by rotating the header, and cannot spend another address's budget or poison its audit trail by claiming to be it.
> - Set it to **true** only when exactly one reverse proxy you control sits in front of the listener. The server then reads the **rightmost** `X-Forwarded-For` entry — the address the trusted proxy itself observed (`proxy_add_x_forwarded_for` *appends* the peer, so everything to the left is client-supplied). Reading the leftmost entry, the common default, is equivalent to trusting the client outright.
> - The counters are keyed on **normalized** identities: emails are lower-cased before the bucket key is built, so casing variants share one budget. `Retry-After` is the real remainder of the fixed window, not a constant.
> - Credential redemption (`otp/verify`, `refresh`) carries the "login 10/min/IP" bucket. Without it the per-code ≤5 budget bounds nothing, since an attacker simply requests fresh codes.

**S-24.b** Deployments that terminate TLS at a proxy MUST set `server.trust_proxy_headers = true` **and** ensure the proxy overwrites (or appends to) `X-Forwarded-For`; a proxy that passes the client's header through unchanged makes the trusted mode strictly worse than the untrusted one. Documented in the deployment runbook.

> **S-24.d — every window is spent atomically, and the window lives in the key** (added 2026-08-07, closing D3; the general form of [S-03.a](#1-authentication)).
>
> S-03.a fixed the OTP attempt budget and nothing else. Every *other* bucket in this requirement — OTP per email and per IP, login per IP, token-auth failures, the publish budget — was still a `get` → decide → `set` round trip, which bounds nothing: N concurrent requests read the same count, all decide *allowed*, and a burst of size N spends one unit. The in-memory backend does not rescue it; one process is not one task.
>
> - **The counter is incremented with an atomic `Kv::incr`, and the increment happens before the decision**, which is read from the returned value and never from a re-read. Atomicity is a stated contract of the `Kv` trait in both backends, asserted by a test rather than assumed from the implementation.
> - **The window is part of the key** (`{prefix}:{floor(now / window)}`), not part of the value and not the KV TTL. Both backends re-arm a key's TTL on every increment, so a TTL-shaped window under sustained traffic would never reset; and the KV expires on real time while every rate-limit decision is made against the injected clock the rest of the auth stack is tested with. The TTL is retained purely as garbage collection.
> - **Windows are aligned and tumbling.** `Retry-After` is the time to the next boundary — still the true remainder of the window that is actually refusing the request, which is what S-24.a requires. The accepted cost is the fixed-window edge: up to 2× the limit may pass across a boundary. Accepted and written down; the exit path, if it is ever observed to matter, is a two-window weighted estimate over the same keys.
> - **Per-bucket outage stances are unchanged** by this: auth-abuse buckets fail closed, token-auth failures degrade to a plain 401, the publish budget fails open per S-24.c. The limiter propagates its error and each call site decides — a uniform stance would be a normative violation in one direction or the other.

> **S-24.e — the in-process fallback exists; a KV outage degrades sign-in instead of closing it** (recorded 2026-08-07 as the honest record that it did *not* exist, **rewritten 2026-08-14 when it was built** — [decision 27](decisions.md#27--rate-limit-identity-what-a-bucket-is-keyed-on-and-what-happens-when-the-kv-is-down), closes roadmap D41).
>
> *Historical, kept because the roadmap and two reviews cite it:* between 2026-08-07 and 2026-08-14 this requirement's "per-instance in-process fallback" was unimplemented — a KV error made the auth guard answer **503**, taking sign-in down instance-wide for the duration of the outage. Fail-closed in the sense that matters most, but not what the requirement says.
>
> As implemented:
>
> - **A KV error on an auth-abuse bucket falls back to a per-instance limiter and the request continues.** Same limit, same window arithmetic, same aligned/tumbling semantics as S-24.d — the only difference is where the count lives. `Retry-After` on a fallback refusal is still the time to the next boundary.
> - **The fallback's memory is bounded by construction, not by an eviction policy.** Bucket keys are attacker-chosen (`rl:otp:email:{address}` carries a submitted address), so an unbounded map would turn a KV outage into a memory-exhaustion primitive. The fallback is a fixed-size table of atomic slots and the key is hashed into one. **Slot collisions merge two buckets' counts**, which can only refuse *more* than the true count — the safe direction for a fail-closed bucket, and the reason no eviction is needed.
> - **The aggregate budget during an outage is up to N × the limit on N replicas**, because each instance counts alone. This is the cost of the requirement as written and it is stated rather than left to be discovered: a limiter N times looser for the minutes an outage lasts is a smaller failure than sign-in being unavailable for the same minutes. An operator who cannot accept it should treat the KV as a sign-in dependency and alert on it, which the shipped rules do.
> - **The stance is per bucket, unchanged.** The fallback covers the auth-abuse buckets (OTP per email and per IP, login per IP). Token-auth failures still degrade to a plain 401 (the request has already failed authentication, so open and closed coincide there); the publish budget still fails open per S-24.c; read-path buckets fail open per S-24.f.

> **S-24.f — read-path buckets, and the identity a bucket is keyed on** (added 2026-08-14, closes roadmap D14 — [decision 27](decisions.md#27--rate-limit-identity-what-a-bucket-is-keyed-on-and-what-happens-when-the-kv-is-down)).
>
> This requirement has always listed "per-IP / per-account / per-token / per-org" and "read-path limiting fails open"; until now the read path had no bucket on either plane and per-token meant nothing (S-13.b).
>
> - **Every `GET`/`HEAD` on the app API and on the pub protocol spends one read bucket**, keyed on the request's identity: `tok:` for a syntactically valid CLI token, `usr:` for a *verified* access JWT, `ip:` otherwise. A JWT's `sub` is used only after signature verification — trusting a decoded one would let anyone drain a chosen victim's budget.
> - **Two numbers, both runtime-changeable**: `read_per_ip_minute` (default 600) for `ip:` identities, `read_per_identity_minute` (default 3000) for `tok:`/`usr:`. One number cannot serve both — a CI fleet behind one NAT is one IP and many tokens, a scraper is one IP and no credential.
> - **It fails open.** A KV error allows the request and logs; this is a quota, not an access gate, and closing it would let a KV outage take package resolution down for every client of the instance.
> - **`/healthz` is exempt** (this requirement's own "health checks exempt") **and its cost is now bounded anyway**: the three backend probes are memoized for one second, so an unauthenticated probe loop can no longer be used as a three-backend amplifier. **The SSE stream is exempt** because it is one request per session rather than a rate; its bound is the S-32 heartbeat.
> - **Trips answer `429 + Retry-After` and are audited once per bucket per window**, under the action `read.throttled` — deliberately *not* `auth.throttled`. A read trip is a quota event; keeping it out of the credential-abuse action is what stops a scraper from drowning the signal an operator filters that action for. Volume lives in `rate_limit_trips_total`, not in row count: one row per refused request would let the refused traffic choose how many rows land in a table that has no retention yet ([D12](roadmap.md)). The same rule was applied to the pre-existing auth and publish buckets.

> **S-24.g — write-path buckets: the mutations this requirement never bounded** (added 2026-08-14, closes roadmap D57 — [decision 32](decisions.md#32--quotas-and-limits-what-an-org-may-store-what-a-caller-may-write-and-one-identity-per-request)).
>
> S-24 bounds sign-in, token authentication, publishing and — since S-24.f — reading. Everything else that *writes* passed with no bucket at all: org and membership mutations, token minting, notification marking, admin settings, the SMTP test that sends real mail. The only bound was the D8 concurrency shed, which limits concurrency and not rate, so an authenticated account could write as fast as the instance answered.
>
> - **Every app-API mutation spends one write bucket**, keyed on the identity classes of S-24.f — but **`tok:` is a pub-plane identity only** (amended 2026-08-14): a CLI token never authenticates on the app API, so it charges no `token_auth_fail_per_ip_minute` there, and treating it as an identity let a caller rotate offline-valid fake tokens for a fresh bucket per request and make the per-IP cap unenforceable. On the app plane a token-shaped credential is an anonymous caller and shares the address's bucket; this is [decision 27](decisions.md#27--rate-limit-identity-what-a-bucket-is-keyed-on-and-what-happens-when-the-kv-is-down)'s own re-check clause being pulled, and it closes the same hole on the read path. Two runtime-changeable numbers: `write_per_ip_minute` (default 60) and `write_per_identity_minute` (default 300). The identity is resolved **once per request** and shared with the read bucket and the authentication extractor, so a write verifies its JWT once rather than three times.
> - **The pub protocol plane is excluded.** Its one write already spends S-24.c's per-org publish budget; a second bucket would answer 429 for two unrelated reasons with two different `Retry-After` values.
> - **The six credential endpoints are excluded**, not charged twice. They spend their own buckets, which fail **closed** onto S-24.e's in-process table; adding an open bucket beside a closed one on the same request only makes the closed one harder to reason about.
> - **It fails open**, for S-24.f's reason: a quota on cost, not an access gate.
> - **It is enforced inside the S-12 custom-header guard**, so a cross-origin request the guard refuses spends nothing. The other order lets a page a user merely visits drain that user's own `ip:` write budget — and, on the refusal, plant an audit row carrying that visitor's IP and User-Agent. **Both layers read one predicate** (amended 2026-08-14): they were written with two spellings of "the app-API plane" that agreed everywhere except the bare path `/api`, which sat outside the guard and inside the bucket, making exactly this attack reachable.
> - **Trips answer `429 + Retry-After`, audited once per bucket per window as `write.throttled`** and counted in `rate_limit_trips_total`. A third action name rather than a reused one, for S-24.f's reason: an operator filtering for refused credentials must not have to read past refused writes.

> **S-24.h — the invitation caps, and why they are not a KV bucket** (added 2026-08-14 — [decision 32](decisions.md#32--quotas-and-limits-what-an-org-may-store-what-a-caller-may-write-and-one-identity-per-request); this requirement's "invitations ≤20/day/org with per-actor caps" was half implemented and undocumented).
>
> - **The per-org cap existed before this amendment** and is unchanged in mechanism: a rolling 24-hour `COUNT(*)` over `invitations`, index-backed, refusing with `429 + Retry-After`. **The per-actor cap is new**: `invitations_per_day_actor` (default 10) bounds one actor's invitations *within one org*, so a single member cannot spend the whole org's budget.
> - **Both numbers are runtime-changeable.** They were compile-time constants, so an instance being spammed could not respond without a rebuild.
> - **It stays a database count rather than moving onto the limiter.** The count is exact, its window genuinely rolls rather than tumbling, and it survives a KV outage — three properties the KV buckets do not have, on the one mutation whose cost is mail delivered to a third party.
> - **A refusal is audited once per (org, actor) per window**, like every other throttle (amended 2026-08-14; this requirement first said *every* refusal writes a row). The argument for keeping every row was that the actor is authenticated, step-up gated, org-scoped and "bounded by S-24.g's write bucket" — true about requests, false about rows, and rows were the point: every other site dedupes, so their ceiling is one row per window, while this one's was one per **request**, 300 a minute at the default identity budget and 432 000 a day per account under S-23's 730-day retention. One row per window still names the actor, the org and the cap that was hit, which is the evidence S-22 requires. **Enforcement is unaffected** — the cap is still the exact rolling count, so a KV outage degrades the audit trail and never the limit. The action is `org.invitation.throttled`, not `auth.throttled`.

## 6. Secrets & configuration

**S-25** Boot-only via env/CLI/mounted files (never DB, never admin-editable): DB URL, blob credentials, Redis URL, JWT signing keyring, OTP/HMAC pepper, KEK, OIDC client secret, public base URL. `_FILE`-suffixed env supported; secrets masked in the startup config summary and never logged.

> **S-25.a — "never logged" is a type, not a habit** (added 2026-08-06 after the auth-slice security review). Masking the startup summary covers the *intended* output path only; a derived `Debug` reachable from a config struct, a flow policy, or a login result is how a pepper or refresh token actually reaches a log line — via `tracing` fields, `#[instrument]`, `unwrap()` panics, or error formatting. Therefore:
> - Configured secrets are carried by a `Secret` newtype with a redacting `Debug` and **no** `Display`; reading requires an explicit `.expose()`, which is the review checkpoint.
> - Connection URLs (`database.url`, `kv.url`) are secrets in disguise; their `Debug` masks the password component.
> - Any in-memory struct holding live credential material — OTP pepper, minted token secret, access/refresh pair, SMTP password — hand-writes `Debug` to redact those fields.
> - Failure messages name the offending **field**, never its value ("`auth.jwt.signing_key` is not valid base64", never the seed).
>
> `_FILE`-suffixed variables are read at startup with trailing newlines trimmed (a pepper with a stray `\n` silently invalidates every outstanding code); an unreadable path and the ambiguous "both `X` and `X_FILE` set" case are startup errors, never silent fallbacks.
**S-26** Runtime settings in DB with sensitive values (SMTP password) envelope-encrypted with the env KEK.

> **S-26.a — write-only is a type, not a filter** (added 2026-08-07 with the admin settings surface).
>
> The SMTP password is the one credential [decision 09](decisions.md#09--always-compiled-backends-runtime-config-selection) moves out of boot config, and three things keep it from coming back out:
>
> - **Sealed before storage.** `pub_auth::secretbox` (AES-256-GCM, fresh nonce per seal, `nonce ‖ ciphertext‖tag`) under the boot KEK — the same construction the S-05 TOTP seed uses, factored into one module so the two cannot drift into different nonce policies. The stored settings row contains base64 of the sealed blob and never the plaintext.
> - **Absent from the read type.** `SettingsView`/`SmtpSettingsDto` carry `password_set: bool` and have **no field** the value could occupy — a distinct type rather than a filtered serialization of the storage struct, so a future `#[derive(Serialize)]` on the latter cannot leak it. Omitting the field on a write keeps whatever is stored, which is what makes a read-modify-write round trip of the returned document safe; an explicit `""` clears it.
> - **Absent from the audit trail and from `Debug`.** The `admin.settings` audit event records the section *keys* and the new version, never a value (S-22). `SmtpPatch` and its DTO hand-write `Debug` to redact the field (S-25.a), because the patch holds the plaintext for the length of one request and a derived `Debug` is how it would reach an `#[instrument]` field or a panic message.
> **S-26.b — the KEK now also seals data in flight, not only settings at rest** (added 2026-08-07 with [decision 26](decisions.md#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path)).
>
> Moving outbound mail onto a durable queue puts a **rendered OTP body — a live, redeemable credential — into a database table** for as long as it takes a worker to claim it. That is a new class of value for this requirement: S-26 was written about a configuration secret at rest, and the queue introduces a secret in flight through storage. Same mechanism, no second construction: the payload is sealed with `pub_auth::secretbox` under the boot KEK before the row is written and unsealed by the worker on claim, so a database dump, a replica, or a backup never contains a usable code. The queued payload type hand-writes `Debug` for the same reason `SmtpPatch` does ([S-25.a](#6-secrets--configuration)).
>
> **The subject is part of the payload** (added 2026-08-07 by the wave's adversarial review, which caught the first implementation leaking exactly this). Sealing the body is not sealing the message: the sign-in template rendered its subject as `"{code} is your sign-in code"`, so every queued row carried the redeemable code in the clear next to the address it belonged to — in the table, in a dump, in a replica, and in the type's hand-written `Debug` — while the sealed body sat next to it proving the intent. **No credential may appear in a queued subject.** The subject stays cleartext by design (the dead-letter admin surface has to be readable without a KEK), which is precisely why the rule has to be stated: a subject is an unsealed field, so nothing secret goes in one. The regression test builds its payload from the production renderer rather than a hand-written literal — the original test suite hard-coded a benign subject at all seven construction sites and was therefore structurally blind to the leak.
>
> Two further consequences recorded rather than discovered later: under the **ephemeral development KEK** a restart makes queued rows unopenable, which costs at most an undelivered sign-in code because these rows live for minutes — but it means the dev-KEK warning now has a second effect, not just one. And this makes the queue a **second reader of the KEK**, so it joins the TOTP seed and the SMTP password on the list of things [S-27](#6-secrets--configuration) KEK rotation must rewrap — which is still structurally impossible (D27), now with one more dependent.

**S-27** Rotation: signing keyring rotates via `kid` overlap; KEK rotation = DEK rewrap; documented rotation runbook; admin break-glass "revoke all tokens/sessions for user/org".

## 7. Platform

**S-28** Transport & headers: HSTS, strict CSP, `X-Content-Type-Options`, frame-ancestors none (except docs if embedded), cookieless API responses marked no-store where sensitive.
**S-29** Compliance surface: account deletion erases profile, keeps anonymized publish-history tombstone (supply-chain integrity, same stance as npm/crates.io); data export endpoint; `/.well-known/security.txt` + disclosure page.
**S-30** Dependencies: `cargo audit` in CI with documented ignore justifications; `default-features = false` discipline with inline rationale (foxic convention); frontend lockfile audit.
**S-31** Sign-in domain policy: an instance-level allowlist of email domains (e.g. `corp.com`) enforced uniformly across every auth path — OIDC (verified email), email OTP, invitations — evaluated server-side at sign-in, registration, and invite time; changes are admin-only and audited; rejection responses stay anti-enumeration-uniform (S-04).

> **S-31.a — the allowlist and the registration mode are runtime settings now** (added 2026-08-07; they were boot-only TODOs).
>
> Both live in the `registration` settings section ([decision 09](decisions.md#09--always-compiled-backends-runtime-config-selection)) and are read per request from the `ArcSwap` cache, so tightening either takes effect on the next sign-in rather than on the next restart. Four properties:
>
> - **The domain gate is evaluated at every sign-in**, not only at registration — an existing account whose domain has left the allowlist can no longer authenticate, which is what makes the setting a *policy* rather than an onboarding filter.
> - **Entries are normalized and validated on the way in**: trimmed, `@`-stripped, lower-cased, de-duplicated, and refused outright if they are not domains (an address, whitespace, or a dotless label). A typo here is a silent instance-wide lockout, and it is admin-only and audited, so failing the write is strictly better than storing it.
> - **Registration has three modes**: `open`, `invite` (registration requires a live, unexpired, unrevoked invitation for that exact address — the org invitation flow is what creates it), and `closed`. A mode an older build does not recognize resolves to the most restrictive behaviour, so a rolling upgrade can never widen registration by accident.
> - **Rejections stay uniform** (S-04/S-04.a): the response shape and the server-side work are identical for allowed, blocked, and unknown addresses; only the SMTP hand-off is conditional, because a blocked address must never receive a redeemable code. The registration probe itself runs for every address, so an invite-only instance and an open one do the same work per request.
**S-32** SSE event stream: authenticated with the same access-JWT validation as REST (including the revoked-`sid` fast path); streams re-check revocation on heartbeat and terminate within one access TTL of session revocation; per-user concurrent-connection cap; events are authorization-filtered — a principal receives only events for orgs/resources they can read.

> **S-32.a — the four clauses as implemented, and what enforces each** (added 2026-08-07 with the realtime layer).
>
> - **Authentication is the same extractor.** `GET /api/v1/events` takes `AuthContext`, so the keyring verification (S-07) and the revoked-`sid` fast path (S-09) that gate every REST route gate the stream too. There is no stream-specific credential path to drift.
> - **"Within one access TTL" is enforced at startup, not by hope.** The heartbeat is where the stream re-asks the KV blocklist *and* re-reads the account row, and the config validator **refuses** `realtime.heartbeat_secs >= auth.access_ttl_minutes`. A KV failure during that re-check closes the stream (fail closed, like the request path), and the stream additionally ends at the token's own `exp`, so a connection cannot outlive the credential that opened it. Asserted end to end by `realtime.rs::s32_a_revoked_session_stream_dies_on_the_next_heartbeat`, which logs out and watches the socket close.
> - **The connection cap is RAII, not bookkeeping.** A slot is released when the writer task's guard drops, which happens on every exit path — client disconnect, revocation, expiry, abort. An explicit release call would leak a slot on the one path somebody forgot, and a few reconnects later the cap becomes a permanent lockout. Over budget answers `429 + Retry-After`, not a bare denial: the condition clears by itself.
> - **The filter reads one thing.** `DomainEvent::audience()` — `Org` | `Instance` | `User` — is checked through the `authorize()` chokepoint (decision 19) and nothing else. An org-scoped event needs `ReadPackages` in that org, an instance-scoped one needs the durable `is_instance_admin` flag (re-read on every heartbeat, so a demotion narrows a *live* stream), and a user-scoped one matches exactly one `sub` — not even an instance administrator reads somebody else's notifications. **Replay applies the identical filter**, so reconnecting with a `Last-Event-ID` cannot widen what a principal sees.
>
> Two residues, accepted and written down:
>
> - **The org roles the filter uses come from the access token**, like every other read path. They cannot be stale-*high*, because any role change or removal revokes the session (S-09.a) and the next heartbeat kills the stream; they can be stale-*low* until the client refreshes, which fails closed.
> - **A slot is held until the writer notices the client is gone**, which is at most one heartbeat. A client that reconnects in a tight loop can therefore hold up to `max_connections_per_user` stale slots for one heartbeat interval — bounded, self-clearing, and cheaper than a per-write liveness probe.
**S-33** Outbound webhooks: URLs validated against SSRF — public DNS/IP only (block loopback, RFC-1918, link-local, cloud-metadata ranges), re-checked after DNS resolution at delivery time; HTTPS required by default; payloads signed HMAC-SHA256 with a per-endpoint secret (encrypted at rest with the env KEK, shown once) and carry event data only, never credentials; capped exponential-backoff retries with a dead-letter state; delivery attempts logged (endpoint, status, duration) without response bodies.
