## 01 — Per-org virtual registry URLs

**Context.** Pub has no npm-style scopes; package names are flat. The registry both hosts private/public packages and proxies pub.dev. Dependency confusion (private name shadowed by a public upstream package) is the primary attack class against this architecture, and the URL/namespace model cannot be changed cheaply later.

**Decision.** Each organization gets a virtual registry endpoint: `PUB_HOSTED_URL = https://<host>/o/<org>/pub`. The trailing `/pub` is the **format segment** — it reserves sibling URL space for future artifact formats (`/o/<org>/npm`, `/o/<org>/cargo`; decision 21) and cannot be retrofitted cheaply, so it exists from day one. That endpoint resolves, in deterministic priority order:

1. Packages owned by the org (private or public).
2. Public packages owned by other orgs on this instance.
3. pub.dev via the proxy pipeline — only if the name is not claimed on the instance (**local always wins**, never version-based races).

Package names are **globally unique per instance per format**: a name is claimed for an org at first publish and recorded in a claim table keyed by `(format, name)`. If a claimed name later appears upstream, the local package keeps winning and org admins are alerted (shadowing alarm). A public root endpoint per format (`https://<host>/pub`) serves only public + proxied packages for anonymous/simple use.

**Consequences.** One URL per org covers private deps, instance-public deps, and pub.dev simultaneously — no `hosted:` boilerplate per dependency. Resolution policy is enforceable per org: upstream `allow` (default) now, `delay` quarantine and `allowlist` later. Cross-org name contention exists by design (flat pub ecosystem semantics); squatting inside an instance is an admin-policy matter, with org name-prefix reservations (e.g. `acme_*` reserved at claim time, never proxied) as the planned enforcement mechanism (later tier).

**Implementation addendum (2026-08-07, pub protocol HTTP surface).** Three things the "resolution order" sentence left implicit, decided while wiring it:

- **The base is the namespace, not the principal.** Inside `/o/{org}/pub` a package owned by *another* org resolves only if it is **public** — another org's private package stays invisible **even to a principal who is a member of that other org**. Without this rule the same `PUB_HOSTED_URL` would mean a different package set per user, and a `pubspec.lock` written by one developer would stop resolving for their colleague. The public root `/pub` likewise resolves nothing private, not even the caller's own. The rule lives in `PackageRepo::resolve_in_base` (a *provided* method, like `resolve` — one policy above two SQL dialects) and is asserted by a contract function on both backends.
- **"Local always wins" is structural.** `Resolution::Unclaimed` is the only value that may ever authorize an upstream lookup, and it is produced on exactly one code path: after `lookup_claim` returned `None`. A locally claimed name therefore cannot reach the proxy no matter what a caller does with the result, and the pub-protocol handlers never call `get_by_name` on a read path at all.
- **Publishing a name another org holds answers 403, not 404** — a narrow, deliberate exception to the visibility-first ladder ([decision 05](#05--anonymous-read-configurable-default-allowed)), scoped to the *publish* verb. The caller has already proven publish authority in its own org, cross-org name contention is accepted by this decision as a design property, and the alternative — "package not found" in response to an attempt to *create* one — is actively misleading on the CLI's one messaging channel. The message names the package (which the caller supplied) and never the holding org. **Ownership is decided before existence** (corrected 2026-08-07 during the conformance review): the publish pipeline checks the claim before the duplicate-version pre-check, because answering "version 1.0.0 already exists" to a caller who does not hold the name is a version-existence oracle for somebody else's private package, spendable one publish attempt at a time. Both routes to the denial emit the same sentence, so an existing version is indistinguishable from a new one.

Publishing is refused at the public root with a 403 pointing at the org URL: a publish needs an owning org, and the root has none.

**Implementation addendum (2026-08-07, per-org upstream policy).** The policy named in "Consequences" is now a column: `orgs.upstream_policy`, `allow` (default) | `block`, migration 0005. `delay` and `allowlist` are additional variants of the same enum rather than a different mechanism, which is why the field and its enforcement point land with the read-through proxy instead of with the later modes — retrofitting a resolution policy onto orgs once the proxy is serving traffic is a migration *plus* a behaviour change on a live path. Three properties:

- **Blocked is indistinguishable from unknown.** An unclaimed name inside a `block`ed org's base answers the same **404** as a name nobody has ever heard of. A distinct status would tell any member that the name exists upstream, which is the enumeration leak the 404 ladder exists to prevent ([S-04](security.md#1-authentication)).
- **The policy is about *upstream*, not about reads.** A blocked org's own packages and instance-public packages resolve exactly as before; only step 3 of the resolution order is removed.
- **The public root has no org**, so it follows the instance-level switch (`[upstream].enabled`) alone. Two gates, not one: the operator's and the org's.

## 02 — sqlx repository traits with per-backend implementation crates

**Context.** SQLite and PostgreSQL must both be first-class (config-driven). sqlx `Any` driver loses compile-time checking and native type mapping. SeaORM 2.0 (kellnr's route) offers one migration set but is days old and takes SQL control away; the owner explicitly chose sqlx.

**Decision.** Domain repository traits (`PackageRepo`, `UserRepo`, `TokenRepo`, `SessionRepo`, `AuditRepo`, `SettingsRepo`, …) live in the `core` crate. Two implementation crates — `db-postgres` and `db-sqlite` — each with their own `migrations/` and their own SQL, compile-time checked via sqlx 0.9 (`sqlx.toml` multi-database prepare, committed `.sqlx/` for offline builds). Each backend uses its idioms: advisory locks vs single-writer locking, tsvector vs FTS5, `TIMESTAMPTZ`/`INET`/partial indexes vs SQLite equivalents. (Cross-instance signaling deliberately lives in the KV broker, not PG LISTEN/NOTIFY — see decision 03.)

**Consequences.** Some SQL is written twice; in exchange both backends are checked at compile time and free to be idiomatic. The API layer never sees sqlx types — only `core` traits and domain structs.

## 03 — Sessions: JWT access + refresh sessions, KV-backed revocation

**Context.** Web UI needs multi-instance-correct sessions. foxic's per-process moka blocklist leaks revoked sessions across instances.

**Decision.**

- **Access token**: short-lived JWT (default 10–15 min, configurable) stored in `localStorage`. Claims: `sub` (user id), `sid` (session id), org memberships as **role levels** per org (decision 19), `iat`/`exp`. Signed with **Ed25519**, keys carry `kid` for rotation.
- **Refresh token = server-side session**: opaque token, hash at rest, rotated on every refresh with **reuse detection** (presenting a rotated-out token revokes the whole session); the sessions table powers the device/session management UI. Client-side the refresh token lives in `localStorage` next to the access token. Defaults: idle timeout 30 days (sliding), absolute cap 90 days — both instance-configurable.
- **Revocation**: durable truth is `sessions.revoked_at` in the DB — the refresh endpoint always validates the session row (not revoked, within idle/absolute limits). The revoked-`sid` set with TTL (= access TTL) in the KV layer is the fast path checked on every authenticated request; its keyspace must not evict early and the check fails closed (S-09). Logout revokes the current session; the explicit revoke-all action and **any permission/role change revoke all of the user's sessions**, so stale role claims can never outlive the access TTL.
- **Scaling gate**: a Redis-compatible store **and broker** (pub/sub) is mandatory for more than one instance. With the in-memory KV backend the config validator refuses `instances > 1`. This one rule also carries rate-limit counters, publish locks, and runtime-settings invalidation — no PG LISTEN/NOTIFY needed.
- CLI/API tokens are a fully separate credential plane (see 13); cookies are not used for API auth, browser tokens are never accepted on pub endpoints.

**Alternatives considered.** The research baseline (IETF BFF guidance, OWASP) recommends server-side cookie sessions for the browser. The JWT+localStorage model was chosen deliberately by the owner: a uniform token plane across SPA/PWA, offline-friendly interceptor architecture (proven in foxic), and future split/CDN static serving without cookie-domain coupling. The rejected concerns are compensated explicitly here and in [security.md §2](security.md#2-sessions--web-plane).

**Consequences.** localStorage is XSS-readable — including the refresh token, whose theft-bound is rotation + reuse detection + idle/absolute caps rather than the 15-minute access TTL. Compensations: strict CSP (nonce for the single inline theme script, no `unsafe-inline`), backend-sanitized README HTML, and publish/retract/role-grant/token-mint actions reserved to CLI tokens or gated by step-up (S-06), so a stolen web session alone can neither publish nor silently escalate. With the in-memory KV backend (single instance) a process restart clears the blocklist for up to one access TTL — an accepted, documented single-node risk. Revocation is instance-coherent by construction otherwise.

## 04 — Single binary now, optional split later

**Decision.** The Astro build output (pre-compressed `.br`/`.gz`) and the service worker are embedded into the Rust binary (`rust-embed`); cache tiers/CSP/security headers are tower layers. `docker run` one container with SQLite + filesystem storage is a supported production minimum. The Docker image is a thin wrapper around the same binary. A split mode (static assets served by CDN/nginx separately) is planned later for large deployments; route layout must keep static assets under a clean prefix so the split stays mechanical.

## 05 — Anonymous read configurable, default allowed

**Decision.** Public and proxied packages are readable without authentication by default (pub.dev-like DX, public-instance showcase possible). An instance-level `require_auth_for_read` flag flips everything to token-only for strict corporate policies.

Status-code ladder (normative; mirrored in [S-04/S-14](security.md#1-authentication)):

1. **Visibility first**: any package the principal cannot read — another org's private package or an unknown name — returns **404, for anonymous and authenticated principals alike** (GitHub model). A 403-vs-404 differential would let any account holder enumerate other orgs' private names.
2. **401** only for missing/invalid credentials where credentials are required, always with `WWW-Authenticate: Bearer realm="pub", message="…"` — the pub client deletes its stored token on 401, and the message is our only onboarding channel into the CLI.
3. **403** (also carrying `WWW-Authenticate` with an explanatory message) only for insufficient scope/role on a resource the principal can see — e.g. publishing with a read-scoped token.

With `require_auth_for_read` enabled, anonymous requests get the spec-mandated **401** + token-onboarding message (nothing is anonymous-readable, so nothing is enumerable).

**Consequences.** Returning 404 where the spec mandates 401 for protected resources is a **deliberate, documented deviation** (anti-enumeration). Cost: a teammate without a configured token sees "package doesn't exist" instead of "add a token" — mitigated by the org UI's setup snippet (exact `dart pub token add` command) and docs.

**Implementation addendum (2026-08-07, pub protocol HTTP surface).**

- **Where the flag lives, for now.** `require_auth_for_read` ships as boot config (`registry.require_auth_for_read`, default `false`) rather than a `settings`-table row: the runtime-settings cache of [decision 09](#09--always-compiled-backends-runtime-config-selection) does not exist yet. It moves into the table when that lands; the flag's semantics do not depend on where it is read from. This is the one place where the current code reads an "instance setting" from boot config.
- **Ordering inside the ladder.** Credentials are judged **before** existence: the auth extractor runs ahead of the org lookup, so with `require_auth_for_read` on, an anonymous caller gets 401 for an unknown org slug too, instead of a 404 that would confirm which orgs exist on the instance. Org slugs get the same anti-enumeration treatment as package names — an unknown `/o/{slug}/pub` is 404 with no challenge.
- **Unrouted paths under a registry base answer the spec error shape**, not the SPA shell: a client asking for an endpoint we have not implemented (`…/advisories` today) must get parseable JSON, not an HTML page.

## 06 — Retract + admin-only hard delete with tombstone

**Decision.** Published versions are immutable; version numbers are never reusable. The normal lifecycle tool is **retraction** (version stays downloadable, excluded from new resolutions) plus package-level `discontinued`/`replaced-by` and `unlisted`. Hard delete exists for corporate reality (leaked secrets, legal takedown): requires org owner/admin role **and** step-up authentication, writes an audit event, removes bytes from blob storage, and leaves a tombstone — the name+version stays burned forever. Deviation from pub.dev's "publishing is forever" is deliberate and gated.

**Implementation addendum (2026-08-07, registry data layer + publish pipeline).** Three details the design left open, decided while building it:

- **What a tombstone is, physically.** Hard delete does not delete the row: it sets `versions.tombstone`, clears the metadata document (`pubspec` → `{}`) and the rendered README/CHANGELOG, and keeps `archive_sha256` and `archive_size`. Clearing the payload matters because the usual reason for a hard delete *is* leaked material; keeping the hash keeps blob accounting honest. The `(package_id, version)` unique index is deliberately **not** partial, so it covers tombstones and the number can never be republished. Tombstoned versions vanish from listings but remain findable by exact version, so callers can distinguish "burned" from "never existed".
- **Blob removal is conditional.** Storage is content-addressed, so several versions can share one object (byte-identical uploads; later, proxy-cached upstream archives). The service deletes the blob only when no live version still references the hash — otherwise it keeps the bytes and records `blob_removed: false` in the audit event. Deleting shared bytes would break a hash already pinned in somebody's `pubspec.lock` ([protocol.md sharp edge 3](protocol.md#sharp-edges-violate--break-clients)).

  **Addendum (2026-08-07, unreferenced-blob GC).** The bytes a conditional delete keeps become collectable when the last sharer goes, which is what `jobs/src/gc.rs` sweeps up — together with the orphans an interrupted publish leaves (bytes are written before the version row on purpose) and staged uploads nobody finalized. Three rules make it safe: a key is collectable only when **both** registers agree — live `versions` *and* cached `upstream_versions`, because the proxy stores its archives under the same content-addressed keys a local publish does; nothing inside the grace period is touched (`min_age`, default 24 h, validated to exceed the 1-hour staged-upload TTL — an upload is finalizable, and therefore live, that whole time with no row referencing it); and a key the job does not fully recognize is left strictly alone. It ships **disabled and dry-run**, because byte stability is the one property this system cannot repair after the fact.
- **Un-retraction has a window; retraction does not.** Retracting is always allowed; restoring is allowed for `registry.unretract_window_days` (default **7**, pub.dev's rule) after the retraction. The flag propagates into resolvers and lockfile decisions, so flipping it back weeks later resurrects a version the ecosystem has already routed around. The window lives in the service layer — the repository only records the flag.

**Implementation addendum (2026-08-07, management surface).** Two consequences of "the number stays burned forever" that only became visible once orgs could be deleted:

- **Deleting an organization that owns packages *archives* it; it never erases it.** A name claim and a version row are exactly the things decision 06 promises survive forever, and both hang off the org row by foreign key — so erasing the org would either fail halfway through or un-burn a claimed name. `DELETE /api/v1/orgs/{slug}` therefore refuses with **409** while the org owns packages, and `force: true` takes the only other coherent path: `orgs.archived_at` is stamped, every membership and invitation is deleted, every org-bound token is revoked, and every package is flipped **private + unlisted + discontinued** through the registry service (so the search index follows in the same breath). The org then serves nothing and discloses nothing, its slug stays taken, and nothing a `pubspec.lock` pins changes. An org with no packages *is* erased outright — there is nothing durable to protect. Archived orgs answer **404** on the public profile and on every management route: they are gone as far as the product is concerned, and the row is a storage artefact. The alternative designs were both worse: cascading the packages away contradicts this decision outright, and refusing forever leaves an operator with no way to retire an organization at all.
- **Hard delete gained a mandatory `reason`, and a confirmation that names the version.** `DELETE /api/v1/packages/{name}/versions/{version}` takes `{confirm: "{name}@{version}", reason}` on top of the Admin role and the S-06 step-up. The reason goes into the audit event: "who destroyed these bytes" without "why" is not an answer anybody can act on months later, and this is the one operation in the system with no undo.

## 07 — Upstream proxy: read-through cache AND mirror mode

**Decision.** Both modes ship:

- **Read-through** (default): on first request, fetch listing/archive from pub.dev, verify `archive_sha256` at ingest, store bytes forever (byte-identical, never re-tar), serve from cache from then on; stale-serving when upstream is down; circuit breaker on upstream failures.
- **Mirror mode**: a periodic sync worker watches upstream for changes and pulls them proactively (full enumeration via `/api/package-names` for the initial sweep and drift repair, recent-changes polling for the fast path). Enables air-gap-adjacent and regional-mirror deployments. Same ingest pipeline as read-through — mirror mode is "read-through warmed by a worker", not a second implementation.

Retraction/discontinued/advisories metadata from upstream is refreshed on listing fetches and preserved verbatim.

**Implementation addendum (2026-08-07, read-through proxy).** Seven things the decision left open, decided while landing the read-through half:

- **A cached listing has a TTL, and that TTL is the product decision.** The pub client re-fetches the version listing before *every* resolve, so "read-through" cannot mean "ask upstream on every request" — that is a proxy, not a cache, and it makes upstream's availability our availability. `upstream.listing_ttl_secs` (default **300**) is therefore the knob that trades how quickly an upstream retraction becomes visible here against how much traffic leaves the instance. Archives have no TTL: they are immutable by [S-18](security.md#4-supply-chain--registry-integrity), so once verified they are cached forever.
- **The upstream is a trait, and there is exactly one door into it.** `UpstreamClient` (real impl over reqwest+rustls; a scripted one in tests) keeps every integrity, staleness, and concurrency behaviour testable without a network — the behaviours only exist when upstream *misbehaves*, and a suite that needs a misbehaving pub.dev does not run. The pipeline behind it is entered from one place, `resolve_target` in the pub protocol module, and only on `Resolution::Unclaimed`; the `Target::Upstream` arm *carries* the service, so a handler cannot reach the proxy for a locally claimed name even by accident (S-16).
- **A degraded upstream is a 404, never a 5xx.** Unreachable upstream, open circuit, refused bytes, malformed listing: whatever is cached is served with a staleness marker in tracing and metrics, and whatever was never cached answers 404. A 5xx here would be retried up to seven times by the client ([protocol.md sharp edge 2](protocol.md#sharp-edges-violate--break-clients)) — one upstream outage becoming a retry storm. The staleness marker deliberately stays **off the wire**: the response shape is the spec's, and an extra field or header would be a protocol change no client asked for.
- **An upstream 404 does not evict.** pub.dev does not unpublish, so a 404 for a package we hold cached is far more likely an upstream defect than a real disappearance — and it does not count against the circuit breaker either, since it is a fact about the package, not about upstream's health.
- **The circuit breaker is per-instance and in-process.** It protects this instance's request threads and latency; a breaker shared through the KV layer would turn one instance's network partition into everybody's outage, which is the opposite of what a breaker is for. Half-open lets exactly one probe through with its failure budget already spent, so a failed probe re-opens immediately.
- **Single-flight is a per-key lock plus a cache re-check**, not a shared future: N simultaneous misses of one package produce one upstream fetch, and the followers pay one cache read rather than inheriting the leader's error. Distinct packages never queue behind each other; a separate semaphore caps total in-flight upstream requests.
- **`advisoriesUpdated` is stored verbatim but not re-emitted.** Sharp edge 11 makes the field a promise that `…/advisories` exists and agrees with it; advertising it while the endpoint is unimplemented would make every proxied package fail an advisory fetch. The snapshot keeps the value so the field can be switched on with the endpoint, not re-derived later.

**Verified against the real pub.dev and the real client** (Dart SDK 3.12.2, 2026-08-07): a proxied listing of `path` re-emits all 76 versions with pub.dev's own `archive_sha256` set and pubspecs byte-for-byte, with every `archive_url` rewritten to the instance; the proxied archive is byte-identical to pub.dev's and its hash is what lands in `pubspec.lock`; `dart pub get` resolves an 11-package graph through the proxy and the resolved code runs; and with the upstream made unreachable the same resolve still succeeds from cache while an uncached name answers one clean "could not find package", not a retry storm.

**Implementation addendum (2026-08-07, mirror worker).** The second half is built: a leader-locked worker in the jobs crate (`jobs/src/mirror.rs`) driving `UpstreamService::refresh`, plus the S-17 alarm the mode makes detectable. Six decisions the "periodic sync worker" sentence left open:

- **"Warmed by a worker" is enforced by the entry point, not by convention.** The worker owns exactly one thing — *when* — and `refresh` is `listing` with the read TTL replaced by a caller-supplied freshness floor. Same validator, same hash-before-store, same byte-drift freeze, same breaker, same semaphore, same single-flight, same snapshot writer. There is no mirror-only ingest path to drift from the read-through one, which is the failure mode a second implementation would have.
- **Both modes chunk, and the chunk is the tick's cost bound.** `full` walks upstream's `/api/package-names` index; `recent` walks our own cache **oldest snapshot first** (`upstream_packages_stale_idx`, created for this in migration 0004). The second needs no cursor by construction: refreshing a package moves it to the back of that ordering, so repeated ticks sweep the whole cache and an interrupted tick simply re-reads what it had not reached. `chunk` bounds how long one tick holds the leader lock; `concurrency` bounds our in-flight refreshes while the service's semaphore still bounds upstream's.
- **The sweep cursor is durable and the page cache is not.** `jobs.cursor` holds `{page, offset, completed_at}` as JSON; a restart resumes at 30 000 names in rather than at zero. The fetched index page is cached in-process purely so a chunked sweep does not re-download several megabytes per tick — losing it costs one fetch, never progress. Re-processing a handful of names across a restart is a *mirror completeness* question the next pass settles, not a correctness one: nothing here decides what a client resolves.
- **A sweep repeats.** `resweep_after` (default 24 h) restarts enumeration after a completed one. This is not only decision 07's "drift repair": enumeration is the **only** channel through which this instance can ever learn that upstream has *started* carrying a name we claim, because the read path structurally never asks upstream about a claimed name (S-16). A mirror that enumerated once would go permanently blind to new S-17 shadowing.
- **A claimed name is observed and then left alone.** Finding one on the sweep raises the S-17 alarm and skips the package: caching it would store bytes resolution can never serve. This is the second of the two arrival orders — the first (a publish claiming a name we already proxy) is detected in the publish pipeline, which is where that order becomes visible.
- **Bytes are opt-in.** `[upstream.mirror] archives = false` by default mirrors metadata only and leaves archives to the read-through path — resolution stays fast, storage stays small. An air-gapped instance sets it and pays for it, bounded per pass by `archive_versions` (newest live versions first; retracted ones are skipped, since they are excluded from new resolutions anyway).

Everything is off by default (`mode = "off"`): mirroring is a deliberate decision about egress and storage, and the config validator refuses a mirror with `upstream.enabled = false` — a worker fetching packages resolution can never serve is an expensive way to do nothing that looks like a working mirror from outside.

**Verified against the real pub.dev** (`pubd` on SQLite + filesystem blobs, 2026-08-07). `mode = "full"` with a 6-package chunk swept pub.dev's index — **86 642 names**, 1.6 MB decompressed, one page, `nextUrl: null` — mirroring metadata and the newest archive of each package. The process was killed mid-sweep and restarted: the first tick after the restart resumed at the stored offset and answered `skipped: 6` with **zero** upstream requests, because the packages the interrupted tick had already saved were inside the freshness floor; the following ticks continued from there and the counters accumulated across the restart. A name claimed locally (`aaroh_chat`, which pub.dev also carries) produced the S-17 alarm — one `upstream.shadowing` audit row, one register row, and **no** `upstream_packages` row for it. A blob-GC dry run over the resulting store enumerated all 58 objects and found every one referenced through the proxy cache.

That session also produced the one wire-level surprise: **pub.dev answers `406 NotAcceptable` on `/api/package-names` unless the request carries `Accept-Encoding: gzip`** ("Client must accept gzip content") — so the header is mandatory there, not an optimization. It is sent on the two JSON endpoints and gzip is decoded **by hand** (flate2, with the size cap applied to the *decoded* document); the HTTP client is deliberately left without transparent content decoding, because a client that silently decodes bodies would also decode an archive body, and "the bytes we hash and store are the bytes that arrived" is the proxy's core promise ([sharp edge 3](protocol.md#sharp-edges-violate--break-clients), S-19). 45 of the 86 642 names are legacy mixed-case ones that predate pub's naming rules; they are dropped from the sweep with a counted warning, since they could not be claimed here and their pubspecs would fail the publish validator too.

**Implementation addendum (2026-08-07, adversarial review of the proxy surface).** One rule was wrong and is now stated explicitly, because it is the difference between a breaker that protects the instance and one that takes it down:

- **Only *reachability* failures reach the circuit breaker.** The breaker is per-instance and instance-wide, so whatever opens it degrades every package. The original code counted every non-404 failure, which put "upstream answered promptly with a document our validator refuses" and "upstream is unreachable" in the same bucket — and since the pub client re-fetches a listing before *every* resolve, one CI job on one such package would have opened the circuit for the whole instance, over and over. A listing we cannot use, like a 404, is a fact about **one package**; a timeout, a connection error, or the transient status family is a fact about **upstream**. Symmetrically, the archive path now feeds the breaker too: with a warm listing cache and a dead archive host it was the only thing still going out, and it was the one branch the breaker could not see. Recorded in [S-19.a](security.md#4-supply-chain--registry-integrity) with the other findings from that review (special-use hostnames in the SSRF guard, a short body named as a transport failure rather than as tampering, and `Content-Length` no longer sizing an allocation).

The same review measured the one residue it could not close: an unclaimed-name miss costs an upstream round trip while a claimed-but-unreadable name costs two indexed reads, so two byte-identical 404s differ by ~640× in latency and a name's *claimed-ness* is timeable without a credential. Every uniform-latency alternative is worse than the leak; `require_auth_for_read` is what closes it. [S-04.c](security.md#1-authentication) carries the numbers and the reasoning — and [S-16.b](security.md#4-supply-chain--registry-integrity) records that `upstream_policy = block` binds to the org's *base*, not to its members, who can still reach upstream through the public root.

## 08 — 10 UI locales from day one

**Decision.** en, ru, fr, it, de, es, pt, ja, ko, zh-Hans (the foxic pool). i18n is wired from the first component (roadmap step 5); English is the bundled fallback; other locales load lazily.

## 09 — Always-compiled backends, runtime config selection

**Decision.** No cargo feature matrix for backends. All implementations (sqlite+postgres, fs+s3+memory, moka+redis) compile into every binary; config selects at startup (kellnr's proven model). Boot config comes from layered sources: defaults → TOML file → env (`PUB_*`-style prefix, `_FILE` suffix support for secret mounts) → CLI flags; validated with fail-fast startup errors and a printed effective-config summary (secrets masked). Runtime-changeable settings (SMTP, rate limits, proxy policy, org policies, banners) live in a `settings` table, cached per instance via `ArcSwap`, invalidated across instances through the KV broker.

**Implementation addendum (2026-08-07, runtime settings + the admin surface).** The `settings` half of this decision is now live (`core/src/settings.rs`, `PATCH /api/v1/admin/settings`). Six things it left open:

- **Boot config is the *default* of a runtime setting, not a competing source.** `Settings::runtime_defaults()` projects the TOML/env layer onto the document, and `SettingsCache` serves `defaults + stored sections`. So an instance whose `settings` table was never written behaves exactly as its config file says; the moment an administrator writes a section, the stored one wins; clearing it falls back again. Two sources with no defined precedence is how "which value is live?" becomes unanswerable, and the summary an operator reads at startup would start lying.
- **A *section* is the unit of change.** Five keys — `registration`, `rate_limits`, `smtp`, `branding`, `upstream` — each holding a whole section, each with its own version. A single blob would make a SMTP change clobber a concurrent branding change; a field-level patch would need a merge rule per field and would race identically. A section this build does not know is left untouched rather than dropped, so a rolling upgrade cannot lose a newer release's settings.
- **The cache is always readable, and that is a deliberate failure mode.** An absent, corrupt, or unparseable section falls back to the boot default with a warning instead of failing the read. These settings gate registration and rate limits: an outage that closed sign-in instance-wide would be a worse failure than serving the operator's configured values.
- **Propagation is a broker publish *plus* a version poll, and the poll is the one that is load-bearing.** A write goes `SettingsRepo::upsert` → local `reload` → `Kv::publish(settings.changed)`; peers reload on the message, and reconcile through `SettingsCache::refresh_if_changed` every 45 s regardless. Redis pub/sub guarantees nothing across a reconnect, and "instance 3 is still enforcing the old rate limit" is invisible from outside. `SettingsRepo::get_version` (the sum of per-key versions) makes the poll one integer comparison. The publish is best-effort: a broker outage costs one poll interval, never the durability of a write that is already committed.
- **What is *not* runtime-changeable stays boot-only** ([S-25](security.md#6-secrets--configuration)): the DB URL, blob credentials, the Redis URL, the JWT keyring, the OTP pepper, the KEK, OIDC client secrets, and the public base URL. The one credential that moved is the **SMTP password**, which S-26 already places in the settings table — it is sealed under the env KEK before storage, accepted on write, and never returned (the read DTO has no field for it). So does `auth.instance_admins`, for a different reason: it is the bootstrap of the very surface that edits settings, and a list stored *in* that surface would let one compromised admin session make itself permanent.
- **Instance administration is bootstrapped two ways, and neither needs a running admin.** `auth.instance_admins` is a boot-config email list, applied at startup to existing accounts and at registration to new ones. When it is empty — the default, and the whole point of the `docker run` deployment minimum — the **first account created on an instance that has no administrator yet** becomes one, through a single-statement `UPDATE … WHERE NOT EXISTS (SELECT 1 FROM users WHERE is_instance_admin)`, so two concurrent first registrations cannot both win it. Removing an address from the list does **not** demote: revoking administration is an audited action on the admin surface, not a side effect of a config edit somebody may have reverted by accident.

## 10 — Blob storage via `object_store`

**Decision.** One `BlobStore` trait in `core`, implemented over `object_store` (LocalFileSystem, InMemory, AmazonS3-compatible incl. MinIO). Downloads return `DownloadPlan::Redirect(presigned_url)` where the backend supports signing (S3) or `DownloadPlan::Stream(...)` (fs/memory) — decided per request, designed in from day one. Archives are stored content-addressed by sha256; the exact uploaded bytes are what is served forever.

## 11 — Search behind a trait

**Decision.** `PackageSearch` trait with per-database implementations: PostgreSQL `tsvector` + GIN + `pg_trgm`; SQLite FTS5 with sync triggers. No external search service; tantivy/Meilisearch possible later as a third impl. Filter vocabulary copies pub.dev's tag architecture (`sdk:`, `platform:`, `topic:`, `is:`, `license:`, `dependency:`) plus a cross-format `format:` tag (decision 21) so search, badges, and API stay consistent across the whole artifact space.

**Implementation addendum (2026-08-07, search backend + public read model).** Migration 0007 in both dialects, and seven decisions the trait sentence left open:

- **The index is a denormalized document, not a view over `packages`.** One `package_search` row per package that has at least one live version, carrying the newest version's description, topics, README text, and the counts the UI renders — plus a `package_tags` table holding the exact-match dimensions (`topic:`, `dependency:`) and, with them, the reverse dependency graph. Searching the live tables instead would mean a JSON scan of every pubspec per query. The cost is that the index is **derived data**: it is rebuildable in full by `jobs/src/reindex.rs`, which is precisely what makes it safe for the publish path to log an index-write failure rather than fail a publish whose bytes, rows, and audit record are already committed.
- **Visibility is enforced *inside* the implementation, through the existing chokepoint.** Every read takes a `SearchView` — the set of orgs in which `authorize(actor, ReadPackages, …)` succeeds, computed by calling that function, not by reimplementing it — and each backend emits `visibility = 'public' OR org_id ∈ view` before anything the query grammar can influence. No filter, text, or cursor can widen it. `unlisted` gets a second mandatory clause: hidden from discovery everywhere except inside its own org, which is what the flag means (it stays resolvable by name — that is `resolve`, a different question). Facet totals and instance counters run the same predicate, because a count that disagrees with the listing leaks exactly what the listing hides ([S-04.d](security.md#1-authentication)).
- **The parser never fails.** A search box is the one input where a syntax error must not be an error page: unparseable tokens are collected into `unknown_filters` and echoed back, so the UI can say what it ignored. It also removes an oracle — a malformed filter and a filter that matched nothing look the same. Untrusted text never becomes engine syntax: every term is quoted (FTS5 `"…"`, tsquery `'…'`), so `OR`, `NEAR`, `&`, `!`, `<->`, and `:` inside a term are data.
- **"Ascending score is best" is a cross-backend convention, and it is what lets the cursor codec live in `core`.** SQLite's `bm25()` is already negative-is-better; Postgres' `ts_rank_cd` is negated to match. Cursors are keyset and **ordering-bound**: the token carries a one-character sort tag, and presenting it under a different `sort` is `invalid_argument` rather than a silently reshuffled page.
- **`relevance` without query text degrades to `updated`.** There is nothing to rank, and ordering by an all-zero score would make pagination depend on the database's row order.
- **The backends are allowed to differ in *recall*, never in visibility.** Postgres adds fuzzy name matching through `pg_trgm` (`blok` → `flutter_bloc`); SQLite gets prefix matching but no typo tolerance, because a full-text index matches lexemes and a typo is not a lexeme. The trigram branch only ever adds rows; everything the contract suite asserts holds identically on both.
- **The read model serves *local* packages only.** A name that resolves through the upstream proxy has no package row here and answers 404 on the app API — proxied packages are installable but not browsable. Making them browsable means rendering somebody else's metadata under our chrome and is a product decision of its own; it lands with the upstream-cache admin surface.

Two supporting choices recorded here because they are visible on the wire: **instance counters are scoped to the caller's view** (an absolute package count on a public page publishes the size of every org's private inventory, and an absolute zero on a fully private instance is a useless dashboard), and the **publishing account is shown only inside the owning org** — the organization is this registry's publisher (orgs replace pub.dev's publishers), and a public page has no reason to hand out staff names.

Branding for the landing dashboard (`GET /api/v1/home`) ships as boot config `[branding]`, the same interim arrangement `registry.require_auth_for_read` uses: [decision 09](#09--always-compiled-backends-runtime-config-selection) files it under runtime settings, and it moves into the `settings` table when the `ArcSwap` cache lands.

## 12 — Auth factors

**Decision.** Self-written auth, no Firebase, no auth SaaS. Sign-in paths: (a) **email OTP — the always-available baseline** — 8-digit CSPRNG code, hashed at rest, 10-minute expiry, single-use, ≤5 attempts per code, resend throttling, uniform anti-enumeration responses; (b) **OIDC — fully optional (zero or more providers configured)**: each provider is issuer + client id/secret + display label; Google is the first-class preset but any spec-compliant IdP works (the `openidconnect` crate is provider-agnostic; corporate buyers often ban consumer Google). Confidential client, authorization code + PKCE S256, `state` + `nonce`, full `id_token` validation, identity keyed by `(iss, sub)`, account linking only via verified email. An instance-level **sign-in domain policy** (email-domain allowlist, e.g. only `@corp.com`) applies uniformly to OIDC and OTP across sign-in/registration/invites ([S-31](security.md#7-platform)). Optional **TOTP authenticator app** as a second factor (email OTP is a single factor per NIST 800-63B and is never marketed as MFA), plus hashed one-time recovery codes. Step-up (fresh second factor, "sudo mode") required for the dangerous actions enumerated in [S-06](security.md#1-authentication) — the normative list lives there. WebAuthn/passkeys: schema-prepared (polymorphic `credentials` table), targeted at v1.1.

**Implementation addendum (2026-08-07, OIDC + TOTP slice).** Three choices made at build time, recorded here because they refine the letter of the design; normative detail in [S-01.a/S-02.a/S-05.a/S-06.a](security.md#1-authentication):

- The OIDC crate is hand-rolled over the same strict-verification core as the S-07 JWT plane (the `openidconnect` crate named above was not adopted — one JWS verifier style across the codebase, no unused surface). The browser↔flow binder is an opaque server-side **`flow_id`** (KV record: state/nonce/PKCE verifier), not a `__Host-` cookie — the API stays cookieless per decision 03; the binding property is preserved.
- A **never-seen OIDC identity requires a verified email** to link or register; a known `(iss, sub)` signs in without one. Unverifiable identities are refused rather than parked in half-registered accounts.
- **Step-up freshness = fresh login ∨ fresh step-up verification** within `auth.step_up_minutes` (default 15). Accounts without TOTP satisfy S-06's "or re-auth" arm by logging in again; the step-up endpoint itself demands an enrolled second factor.

## 13 — CLI/API token format

**Decision.** GitHub-style: `<prefix>_<30 base62 chars><6 base62 CRC32 checksum>` (~178 bits entropy; prefix TBD with product name, see 17). Stored as SHA-256 hash + first-8-chars display hint (argon2 deliberately not used: tokens are high-entropy and verified per request — crates.io rationale). Scopes: `read`, `publish`, `retract`, `admin`; org-bound, optional package-name patterns; default expiry 90 days; last-used tracking (write-throttled); show-once UX with the exact `dart pub token add` command; published regex for secret scanners; revocation effective within ≤60 s (no server-side token caching beyond that). The credential-type enum leaves room for short-lived exchanged CI credentials — trusted publishing via GitHub/GitLab OIDC token exchange (later tier).

**Implementation addendum (2026-08-07, pub protocol HTTP surface).**

- **The header, and nowhere else.** Tokens are accepted on `Authorization: Bearer` only. The spec defines no query-parameter credential and the client sends none, so `?token=` is not supported — a query credential lands in access logs, proxy logs, and `Referer` headers, and would reach users' `pubspec.lock` files through `archive_url`.
- **The offline checks are the plane boundary.** Prefix + length + base62 charset + CRC32 run before the hash lookup, which is what makes a browser access JWT structurally unusable on pub routes ([decision 03](#03--sessions-jwt-access--refresh-sessions-kv-backed-revocation)'s "never mixed") without a hand-written special case, and keeps fabricated strings off the database.
- **Package patterns**: a trailing `*` matches any suffix, anything else is an exact name; an empty list means no narrowing. Deliberately not a regex — this is an authorization decision, and a catastrophic-backtracking pattern would be a denial of service with extra steps. Patterns narrow reads of **private** packages only (a public package is readable with no credential at all, so hiding one would make a token worse than none) and are enforced at publish **finalize**, which is the first moment a package name exists in the flow.
- **The role is re-derived per request** from the durable membership, never cached in the token row: a token outlives role changes by design, so a user who has left the org authenticates and authorizes nothing.

## 19 — RBAC: cumulative role levels with a single authorize() chokepoint

**Context.** Org roles here are genuinely cumulative — Read ⊂ Read+Write ⊂ RW+Admin ⊂ RW+Admin+Owner. A bitmask earns its complexity only when permissions are non-linear (auditor-only, retract-only, billing-only); in this design that plane is already served by scoped CLI tokens and, later, per-package grants — so the org role can stay linear.

**Decision.** An org membership carries an **ordered role level**, stored as a small integer with gaps for future insertions: `0` none, `50` **Read** (resolve/download), `100` **Write** (publish, manage own packages), `200` **Admin** (members, tokens, package settings), `250` **Owner** (org lifecycle, danger zone). Checks are `level >= required`; an intermediate role (e.g. a future `150` Maintainer) slots in without migration. Wire protocol and UI use role *names* — numbers are a storage/comparison detail. JWT claims carry `{org_id: level}` (decision 03). Every check flows through a single `authorize(actor, action, resource)` chokepoint, so if a genuinely non-linear org permission ever appears, adding a bitmask overlay is a contained refactor, not an audit of scattered comparisons. Invariants: ≥1 Owner per org; invitations default to Read; grants at Write level or above are step-up-gated (S-06). CLI-token scopes (`read`/`publish`/`retract`/`admin`) remain the fine-grained, non-linear plane.

**Implementation addendum (2026-08-07, management + administration surface).** Four decisions the ladder sentence left open, all made while wiring the mutations:

- **Instance administration is a second, orthogonal plane — not the top of this ladder.** `Action::AdministerInstance` on `Resource::Instance` is decided by `users.is_instance_admin`, and the two ladders never imply each other: an org Owner administers their org, an instance admin holds no org role they were not granted. Extending the role ladder upwards instead would have meant "Owner of any org" quietly becoming a step towards reading every org's private inventory. `authorize()` additionally refuses a **mismatched** action/resource pair (an org action aimed at the instance, or vice versa) rather than falling through, so a wiring mistake is a denial and not an accidental grant on the other plane.
- **The admin flag is read from the row per request, never from a token.** [S-07](security.md#2-sessions--web-plane) limits access-token claims to `sub`/`sid`/org levels/timestamps, and an `adm` claim would be a deviation from a normative requirement for no gain — while costing correctness, since a demotion would then take up to one access TTL to bite. The `InstanceAdmin` extractor pays one indexed read on a surface nobody calls in a loop, and a demotion or suspension is effective on the very next request.
- **The org slug is immutable.** It *is* the virtual registry base (`/o/{slug}/pub`, decision 01), so `PATCH /api/v1/orgs/{slug}` carries name, description, and upstream policy — and no slug. Renaming it would break every `PUB_HOSTED_URL`, every stored `archive_url`, and every CI token configuration pointing at the old one, silently and all at once.
- **Org management answers 403 where package management answers 404.** Org slugs are not secret ([S-04.b](security.md#1-authentication)), so an insufficient role on a real org is a 403 that tells a Read member what they are missing. Packages are the opposite: a management route resolves the package through the read model's own ladder *first*, so a package the caller cannot read answers the same 404 an unknown name does — checking the role first would make `PATCH /api/v1/packages/{name}/options` an existence oracle for another org's private packages.

## 20 — Realtime: SSE event stream + notification center

**Decision.** The backend exposes a Server-Sent-Events stream (`GET /api/v1/events`) for live updates: package publishes/retractions in the principal's orgs, membership and invitation events, shadowing alarms, token-expiry warnings, admin announcements, settings changes for admin UIs. Delivery: per-instance in-process broadcast, fanned out across instances via the KV broker (Redis pub/sub) — consistent with decision 03's scaling gate; single instance needs no extra infra. Implementation notes: the browser client uses fetch-streaming rather than `EventSource` (which cannot set an `Authorization` header); keep-alive comments; best-effort `Last-Event-ID` replay from a short per-user ring buffer — the stream is a hint channel, the REST API remains the source of truth. On top of the same events sits a **notification center**: per-user persisted notifications (unread counts, mark-read, preferences per category), with email delivery for high-importance ones (invites, security events). Security constraints in [S-32](security.md#7-platform).

**Implementation addendum (2026-08-07, the realtime layer).** Seven decisions the sentence above left open, all made while wiring `crates/events`, `GET /api/v1/events`, and the notification surface:

- **The audience is a property of the event, not a rule in the stream.** `DomainEvent::audience()` answers `Org(id)` | `Instance` | `User(id)`, and the SSE filter consults **nothing else** — no package flags, no per-variant special case. That is what keeps a new event variant from defaulting to "everybody" by omission: the match is exhaustive, so adding one without deciding its audience does not compile. Org-scoped events reach that org's `Read+` members and nobody else, *including for a public package*: the stream is a member's channel over their own organizations, the public read model is the REST API, and the alternative would let a package flipped to private mid-stream still announce its next publish to strangers.
- **The replay ring is per *instance*, not per user.** The design said "a short per-user ring buffer"; a per-user buffer would require resolving every event's audience to a user set at *emit* time and keeping a queue per account — a fan-out cost paid for readers who are not connected. The implementation keeps one bounded ring of recent envelopes per instance and applies the **same** visibility filter to a replay that it applies to live delivery, so the guarantee a reader gets is identical and no principal can widen what they see by reconnecting. Event ids are ULIDs minted where the event originates, so a `Last-Event-ID` from instance A still compares in time order against instance B's ring.
- **Consumers run only on the instance that emitted the event.** A peer receiving an event over the broker feeds it to its *stream* and to nothing else. The notification center running on every replica would file one row per replica for one event, which is how a fan-out becomes a duplicate factory. The broker payload therefore carries an `origin`, which is also the loop breaker for Redis echoing a publisher its own messages.
- **A consumer's output re-enters the stream, never the consumers.** The notification center returns one `UserNotified` event per recipient; those are broadcast and republished but not fed back through the consumer list, so there is no cycle to bound. `UserNotified` additionally reports **no notification category**, which is what makes "the notification center cannot notify itself" structural rather than a guard somebody can delete.
- **Notification fan-out happens at write time, one row per recipient.** Storing the event once and filtering per reader would mean a member who joins tomorrow inherits today's private-package activity, and a member who leaves keeps seeing it. The cost is bounded by `realtime.max_notification_recipients` (default 200, validated ≤ 500 because the batched preference lookup binds one parameter per recipient); past the bound the fan-out is capped with a counted warning rather than growing a publish request without limit.
- **Three categories, not one per event type.** `package` | `org` | `security`, with the event→category map on the event itself. A preference list curated per event *name* is a preference list nobody curates. `org` and `security` are the high-importance tier and reach a mailbox by default; `package` does not, because a publish firehose in everybody's inbox is the fastest way to get the sender filtered into a folder and the other two categories missed. `security` additionally narrows the org audience to **Admin+** — a shadowing alarm is addressed to the people who can act on it.
- **Known gap, recorded rather than papered over: deleting an org notifies nobody.** `OrgDeleted` is org-scoped, and by the time it is emitted the deletion has already removed every membership, so the audience resolves empty. The affected members *do* get their sessions revoked (S-09), which is the signal they act on. Closing it properly needs either a user-scoped variant or a recipient list on the event; it lands with the webhook work, which needs per-subscriber addressing anyway.

## 21 — Multi-format artifact space (pub first; npm, cargo, … later)

**Decision.** The registry is designed Artifactory-style as a **single artifact space over multiple package formats**. V1 ships the pub protocol only, but every shared seam is format-agnostic from day one:

- Core entities carry a `format` discriminator: packages unique per `(format, name)`; name claims, resolution policy, and shadowing alarms are per-format; version rows hold common fields (version, ordering key, sha256, retracted, timestamps) plus format-specific metadata as JSON (pubspec / package.json / Cargo index entry).
- The blob store is content-addressed and format-blind already.
- URL space reserves the format segment now: `/o/{org}/pub` (future `/o/{org}/npm`, `/o/{org}/cargo`), public roots `/pub` (future `/npm`, `/cargo`). The `api` crate hosts one protocol module per format, each implementing its wire contract against the shared core traits.
- One search across formats (`format:` filter tag), one permission model (decision 19), one token plane (scopes apply uniformly per format), one audit/notification/webhook pipeline.
- Upstream proxying generalizes: per-format upstreams (pub.dev, registry.npmjs.org, crates.io) share the ingest pipeline, integrity rules (S-19), and policy engine (S-16).

**Consequences.** Pub-specific logic (pubspec parsing, advisories mapping, README pipeline specifics) lives in the pub protocol module and format adapters — never in shared entities. npm's `@scope/name` maps naturally onto orgs; cargo needs a sparse-index endpoint — both are protocol-module work, not core rework. Non-goal for v1: shipping any second format.

**Implementation addendum (2026-08-07, registry data layer).** Two shared seams were fixed while landing the entities; both are format-agnostic by construction and neither can be retrofitted cheaply:

- **Version ordering is a stored precedence key.** `core::SemVer` implements semver.org §11 precedence (pre-release rules included, build metadata excluded), and `SemVer::sort_key()` projects a version onto a string whose *bytewise* order equals that precedence: fixed-width zero-padded core numbers, a release/pre-release marker, and one prefixed segment per pre-release identifier separated by a byte below every legal identifier character. Storing it (`versions.version_sort`) makes version listing and keyset pagination one index scan instead of an in-memory sort, and keeps ordering identical on both backends. It is **collation-sensitive**: the Postgres column carries `COLLATE "C"` because a locale/ICU collation folds punctuation and case and silently reorders pre-releases (verified: an ICU-collated column sorts `1.0.0-a-b` before `1.0.0-a.b`, which is backwards). The contract suite orders a table containing exactly those adversarial pairs on both backends. Other formats reuse the same key — npm and cargo are semver too.
- **Blob keys are `<format>/<sha256[0..2]>/<sha256>.tar.gz`.** Content addressing already makes the hash unique, so the format prefix is not for collision avoidance: it keeps per-format lifecycle operations (a bulk purge, a per-format retention policy, a bucket-level rule) expressible as a prefix, and the two-character shard keeps directory fan-out sane on the filesystem backend.

## 22 — Domain event bus; webhooks and integrations on top

**Decision.** All domain events (publish, retract, membership/invitation, shadowing alarm, token lifecycle, settings changes) flow through **one internal event bus** — the single seam that fans out to: the SSE stream (decision 20), the notification center, the audit log, and **outbound webhooks**. Webhooks (v1.1): configured per org (and instance-wide by admins) with event-type filters; deliveries signed with HMAC-SHA256 (`X-Pub-Signature` header), executed by the jobs crate with exponential-backoff retries and a dead-letter state; delivery log in the UI. Security constraints in [S-33](security.md#7-platform) (SSRF guards, encrypted secrets, TLS-by-default). Richer integrations (Slack/Telegram templates, CI triggers) build on the same bus later.

**Implementation addendum (2026-08-07, the bus itself).** Three things the "one internal event bus" sentence left open:

- **The audit log is *not* a bus consumer, and that is deliberate.** Every service writes its audit row directly, before or alongside the event, because the audit log is **durable truth under a compliance requirement** ([S-22](security.md#5-audit--abuse)) while the bus is explicitly a hint channel whose consumers may fail silently. Routing audit through a sink that swallows errors would make "append-only, INSERT-only, every mutation recorded" depend on a broadcast channel's health. The bus and the audit log share the *vocabulary* (`DomainEvent::name()` is the audit action) and nothing else.
- **`EventSink::emit` returns nothing, and the bus honours that all the way down.** Consumer errors, broker outages, and undecodable peer messages are logged and dropped. A publish whose bytes, rows, and audit record are committed must not fail because a notification could not be written — the same stance the search-index write already takes ([decision 11](#11--search-behind-a-trait)).
- **Webhooks are a seam, not a stub.** `EventConsumer` is the interface a delivery worker will implement; nothing about the bus needs to change to add one, because the consumer contract already returns follow-up events (which is how a delivery-status event will reach the UI) and already runs on exactly one instance per event (which is what stops N replicas from delivering one webhook N times).

## 23 — Monitoring is optional

**Decision.** Observability exports are config-gated and **off by default**: the Prometheus `/metrics` endpoint (optionally on its own listen address), OTLP trace export, and JSON log shipping are each enabled explicitly. `tracing` instrumentation and `/healthz` are always on — near-free and needed by orchestrators. No monitoring stack is required to run the product.

## 24 — Theme registry, Patina palette

> **Status: proposed.** The palette direction was chosen by the owner (2026-08-07); this entry's *wording* has not been reviewed yet.

**Decision.** Four related choices, made together on 2026-08-07:

- **Palette "Patina".** The product's default look is warm graphite neutrals (OKLCH hue 60–85 at whisper chroma) with a desaturated teal accent (hue 195), replacing the initial indigo/violet system. Chosen by the owner from three validated directions; the alternates — *iris* (refined indigo) and *nocturne* (night-blue/blurple) — are kept in `web/packages/tokens/candidates/` as future-theme material, each a complete palette that passes the contrast gate.
- **Themes are a registry, not a light/dark binary.** A theme is a named `[data-theme="<name>"]` block in `packages/tokens/theme.css` overriding the raw `--pub-*` token set; `:root` carries light, which is also the SSR default and the fallback for unknown names. The registry has three synchronized members: the CSS blocks, `THEMES` in `packages/ui/src/theme.ts` (picker + persistence), and the theme list in the anti-FOUC inline script. The contrast gate **discovers** theme blocks by parsing `theme.css` and asserts the same WCAG AA pairs for every theme — registering a theme in CSS is enough to put it under the gate. `localStorage.pub_theme` holds `"system"` or a theme name; anything unknown counts as system, so stale stored values from removed themes degrade gracefully.
- **AMOLED is the third theme.** True-black canvas (`oklch(0 0 0)` — an OLED panel switches those pixels off), surfaces barely lifted, the same Patina accent/status families as dark. It is a darkness variant of dark, not a second brand; `system` resolves only to light/dark — amoled is always an explicit choice. The `dark:` Tailwind variant matches the whole dark family (dark + amoled).
- **Seed-theme seam (documented, not implemented).** A future Material-You-style adaptive theme derives the same raw token set from one seed color at runtime and attaches it under a new `data-theme` scope. The `--pub-*` token *names* are the generation contract; the semantic `@theme` layer needs no changes; a generated set must pass the same contrast pairs the static gate asserts, evaluated at generation time. No generator ships now.
