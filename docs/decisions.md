## 01 — Per-org virtual registry URLs

**Context.** Pub has no npm-style scopes; package names are flat. The registry both hosts private/public packages and proxies pub.dev. Dependency confusion (private name shadowed by a public upstream package) is the primary attack class against this architecture, and the URL/namespace model cannot be changed cheaply later.

**Decision.** Each organization gets a virtual registry endpoint: `PUB_HOSTED_URL = https://<host>/o/<org>/pub`. The trailing `/pub` is the **format segment** — it reserves sibling URL space for future artifact formats (`/o/<org>/npm`, `/o/<org>/cargo`; decision 21) and cannot be retrofitted cheaply, so it exists from day one. That endpoint resolves, in deterministic priority order:

1. Packages owned by the org (private or public).
2. Public packages owned by other orgs on this instance.
3. pub.dev via the proxy pipeline — only if the name is not claimed on the instance (**local always wins**, never version-based races).

Package names are **globally unique per instance per format**: a name is claimed for an org at first publish and recorded in a claim table keyed by `(format, name)`. If a claimed name later appears upstream, the local package keeps winning and org admins are alerted (shadowing alarm). A public root endpoint per format (`https://<host>/pub`) serves only public + proxied packages for anonymous/simple use.

**Consequences.** One URL per org covers private deps, instance-public deps, and pub.dev simultaneously — no `hosted:` boilerplate per dependency. Resolution policy is enforceable per org: upstream `allow` (default) now, `delay` quarantine and `allowlist` later. Cross-org name contention exists by design (flat pub ecosystem semantics); squatting inside an instance is an admin-policy matter, with org name-prefix reservations (e.g. `acme_*` reserved at claim time, never proxied) as the planned enforcement mechanism (later tier).

**Implementation addendum (2026-08-07, pub protocol HTTP surface).** Three things the "resolution order" sentence left implicit, decided while wiring it:

- **The base is the namespace, not the principal.** Inside `/o/{org}/pub` a package owned by *another* org resolves only if it is **public** — another org's private package stays invisible **even to a principal who is a member of that other org**. Without this rule the same `PUB_HOSTED_URL` would mean a different package set per user, and a `pubspec.lock` written by one developer would stop resolving for their colleague. The public root `/pub` likewise resolves nothing private, not even the caller's own. The rule lives in `PackageRepo::resolve_in_base` (a *provided* method, like `resolve` — one policy above two SQL dialects) and is asserted by a contract function on both backends.
- **"Local always wins" is structural.** `Resolution::Unclaimed` is the only value that may ever authorize an upstream lookup, and it is produced on exactly one code path: after `lookup_claim` returned `None`. A locally claimed name therefore cannot reach the proxy no matter what a caller does with the result, and the pub-protocol handlers never call `get_by_name` on a read path at all.
- **Publishing a name another org holds answers 403, not 404** — a narrow, deliberate exception to the visibility-first ladder ([decision 05](#05--anonymous-read-configurable-default-allowed)), scoped to the *publish* verb. The caller has already proven publish authority in its own org, cross-org name contention is accepted by this decision as a design property, and the alternative — "package not found" in response to an attempt to *create* one — is actively misleading on the CLI's one messaging channel. The message names the package (which the caller supplied) and never the holding org. **Ownership is decided before existence** (corrected 2026-08-07 during the conformance review): the publish pipeline checks the claim before the duplicate-version pre-check, because answering "version 1.0.0 already exists" to a caller who does not hold the name is a version-existence oracle for somebody else's private package, spendable one publish attempt at a time. Both routes to the denial emit the same sentence, so an existing version is indistinguishable from a new one.

Publishing is refused at the public root with a 403 pointing at the org URL: a publish needs an owning org, and the root has none.

**Implementation addendum (2026-08-07, per-org upstream policy).** The policy named in "Consequences" is now a column: `orgs.upstream_policy`, `allow` (default) | `block`, migration 0005. `delay` and `allowlist` are additional variants of the same enum rather than a different mechanism, which is why the field and its enforcement point land with the read-through proxy instead of with the later modes — retrofitting a resolution policy onto orgs once the proxy is serving traffic is a migration *plus* a behaviour change on a live path. Three properties:

- **Blocked is indistinguishable from unknown.** An unclaimed name inside a `block`ed org's base answers the same **404** as a name nobody has ever heard of. A distinct status would tell any member that the name exists upstream, which is the enumeration leak the 404 ladder exists to prevent ([S-04](security.md#1-authentication)).
- **The policy is about *upstream*, not about reads.** A blocked org's own packages and instance-public packages resolve exactly as before; only step 3 of the resolution order is removed.
- **The public root has no org**, so it follows the instance-level switch (`[upstream].enabled`) alone. Two gates, not one: the operator's and the org's.

## 02 — sqlx repository traits with per-backend implementation crates

**Context.** SQLite and PostgreSQL must both be first-class (config-driven). sqlx `Any` driver loses compile-time checking and native type mapping. SeaORM 2.0 (kellnr's route) offers one migration set but is days old and takes SQL control away; the owner explicitly chose sqlx.

**Decision.** Domain repository traits (`PackageRepo`, `UserRepo`, `TokenRepo`, `SessionRepo`, `AuditRepo`, `SettingsRepo`, …) live in the `core` crate. Two implementation crates — `db-postgres` and `db-sqlite` — each with their own `migrations/` and their own SQL. Each backend uses its idioms: advisory locks vs single-writer locking, tsvector vs FTS5, `TIMESTAMPTZ`/`INET`/partial indexes vs SQLite equivalents. (Cross-instance signaling deliberately lives in the KV broker, not PG LISTEN/NOTIFY — see decision 03.)

**Consequences.** Some SQL is written twice; in exchange both backends are free to be idiomatic. The API layer never sees sqlx types — only `core` traits and domain structs.

**Amendment (2026-08-07, runtime queries are the norm — verified by spike).** The original wording assumed compile-time `query!` macros. The implementation deliberately uses runtime `query`/`query_as`, and a spike on sqlx 0.9 (per-crate `sqlx.toml`, renamed `DATABASE_URL` vars, committed `.sqlx/`, six queries converted, full pipeline green) resolved the question: the once-blocking CLI workflow now works, but the macro idiom conflicts with this codebase's load-bearing patterns — the `COLS` single-source column lists cannot be expressed (macros require string literals; ~150 call sites would inline copies), SQLite STRICT booleans need `AS "col: bool"` noise everywhere, deliberate String-bind `INET`/`JSONB` idioms are rejected and need `::text::…` rewrites, `QueryBuilder` list/filter endpoints (~10% of sites, permanently) can never convert, and — because `core` stays sqlx-free — macros cannot replace the `TryFrom<Row>` corruption-curating boilerplate, only duplicate its checking. Schema/SQL drift is instead caught by the dual-backend contract suite in `pub-db-tests`, which exercises every repository method against real databases in the same CI run. **Norm: runtime queries; no `.sqlx/`, no `SQLX_OFFLINE`.** Revisit trigger: a real drift escape the contract suite misses, or sqlx gaining const/computed SQL fragments.

## 03 — Sessions: JWT access + refresh sessions, KV-backed revocation

**Context.** Web UI needs multi-instance-correct sessions. foxic's per-process moka blocklist leaks revoked sessions across instances.

**Decision.**

- **Access token**: short-lived JWT (default 10–15 min, configurable) stored in `localStorage`. Claims: `sub` (user id), `sid` (session id), org memberships as **role levels** per org (decision 19), `iat`/`exp`. Signed with **Ed25519**, keys carry `kid` for rotation.
- **Refresh token = server-side session**: opaque token, hash at rest, rotated on every refresh with **reuse detection** (presenting a rotated-out token revokes the whole session); the sessions table powers the device/session management UI. Client-side the refresh token lives in `localStorage` next to the access token. Defaults: idle timeout 30 days (sliding), absolute cap 90 days — both instance-configurable.
- **Revocation**: durable truth is `sessions.revoked_at` in the DB — the refresh endpoint always validates the session row (not revoked, within idle/absolute limits). The revoked-`sid` set with TTL (= access TTL) in the KV layer is the fast path checked on every authenticated request; its keyspace must not evict early and the check fails closed (S-09). Logout revokes the current session; the explicit revoke-all action and **any permission/role change revoke all of the user's sessions**, so stale role claims can never outlive the access TTL.
- **Scaling gate**: a Redis-compatible store **and broker** (pub/sub) is mandatory for more than one instance. With the in-memory KV backend the config validator refuses `instances > 1`. This one rule also carries rate-limit counters, publish locks, and runtime-settings invalidation — no PG LISTEN/NOTIFY needed.
- CLI/API tokens are a fully separate credential plane (see 13); cookies are not used for API auth, browser tokens are never accepted on pub endpoints.

**Alternatives considered.** The research baseline (IETF BFF guidance, OWASP) recommends server-side cookie sessions for the browser. The JWT+localStorage model was chosen deliberately by the owner: a uniform token plane across SPA/PWA, offline-friendly interceptor architecture (proven in foxic), and future split/CDN static serving without cookie-domain coupling. The rejected concerns are compensated explicitly here and in [security.md §2](security.md#2-sessions--web-plane).

**Consequences.** localStorage is XSS-readable — including the refresh token, whose theft-bound is rotation + reuse detection + idle/absolute caps rather than the 15-minute access TTL. Compensations: strict CSP (nonce for the single inline theme script, no `unsafe-inline`), backend-sanitized README HTML, and publish/retract/role-grant/token-mint actions reserved to CLI tokens or gated by step-up (S-06), so a stolen web session alone can neither publish nor silently escalate. With the in-memory KV backend (single instance) a process restart clears the blocklist for up to one access TTL — an accepted, documented single-node risk. Revocation is instance-coherent by construction otherwise.

**Amendment (2026-08-07, rate-limit counters are spent atomically — closes D3).** "This one rule also carries rate-limit counters" said where the counters live, not how they are spent. They were spent with a `get` → decide → `set_ttl` round trip, which is not a bound at all: N concurrent tasks all read the same count, all decide *allowed*, and a burst of size N costs one unit of budget. The in-memory backend does not save it — one *process* is not one *task*. This is the same defect [S-03.a](security.md#1-authentication) already fixed for the OTP attempt budget, left unfixed for every window around it.

- **One atomic `Kv::incr`, and the increment precedes the decision.** `hit` spends first and decides on the returned count, exactly like the S-03.a budget. `Kv::incr` is atomic in both backends by contract (`traits.rs` states it normatively; moka's per-key upsert lock, `MULTI: INCR + PEXPIRE`), and that contract is now asserted by a test rather than assumed.
- **The window moves into the key, because the TTL cannot carry it.** Both backends re-arm the TTL on *every* increment, so a counter under sustained traffic would never expire and a TTL-shaped window would never reset. The key becomes `{prefix}:{floor(now / window)}` and the TTL degrades to pure garbage collection (2× window). This also keeps the limiter on the **injected clock** the rest of the auth stack is tested against — moka expires on real time, so a window read from the KV TTL would be untestable and would drift from every other time-dependent decision.
- **Windows become aligned tumbling instead of anchored at the first hit.** `Retry-After` is now the time to the next boundary — still the true remainder of the window that is actually refusing the request ([S-24.a](security.md#5-audit--abuse)), which is the property the client contract depends on. The accepted cost is the classic fixed-window edge: up to 2× the limit across a boundary. Recorded as accepted rather than hidden; the exit path, if it is ever observed in practice, is a two-window weighted estimate over the same two keys, which needs no new KV primitive.
- **Every per-call-site outage stance is unchanged**, and that is deliberate: auth buckets fail **closed**, the token-auth-failure bucket degrades to a plain 401, and the publish budget fails **open** per [S-24.c](security.md#5-audit--abuse). `hit` still only propagates its error — mechanically sweeping the four call sites to one stance would be a silent normative violation that no test catches today.

## 04 — Single binary now, optional split later

**Decision.** The Astro build output (pre-compressed `.br`/`.gz`) and the service worker are embedded into the Rust binary (`rust-embed`); cache tiers/CSP/security headers are tower layers. `docker run` one container with SQLite + filesystem storage is a supported production minimum. The Docker image is a thin wrapper around the same binary. A split mode (static assets served by CDN/nginx separately) is planned later for large deployments; route layout must keep static assets under a clean prefix so the split stays mechanical.

**Implementation addendum (2026-08-07, HTTP hygiene wave — D8/D13).** The "cache tiers/CSP/security headers are tower layers" clause is now concrete, with four choices the sentence left open:

- **The CSP is two-tier, and the hashes are computed at startup, not committed.** API and pub-protocol responses answer `default-src 'none'; frame-ancestors 'none'`; HTML documents get a strict `'self'`+sha256 policy whose hashes come from scanning the *embedded* build's inline scripts and styles at router construction (`assets.rs`) — self-adapting to whatever dist is embedded, which is exactly the reality decision 14's CSP note recorded (Astro emits framework inline bootstraps beyond our one authored script). A defective scan refuses to boot rather than serving a policy that blanks the page. Two consequences the adversarial review caught before they shipped: an HTML **304 must re-carry the document policy** (RFC 9111 — browsers replace stored headers from a 304, and the API-tier value would have bricked every cached page), and the root **`sw.js` needs its own worker policy** (`connect-src 'self'` is what lets the offline shell install; a worker's CSP comes from its own response, not the document's).
- **Cache tiers ride the embed's own hashes.** `_astro/*` is `immutable` for a year, documents and `sw.js` are `no-cache`, everything API-shaped is `no-store`; strong ETags come from rust-embed's precomputed sha256 (never the build mtime — not reproducible), and archives serve `private, immutable` with the content-hash ETag they already have (S-18).
- **CORS is locked to the parsed origin of `server.public_url`** (now validated at boot: http/https, host, no query/fragment — an opaque origin would have serialized to the literal `null`, which is an allow-list for sandboxed pages), credentials off; the S-12.a server-side check remains the non-delegating layer.
- **Deadlines and shedding are path-aware** (`[http]` section): SSE is exempt, publish finalize and cold-cache proxied archives ride larger budgets, `/healthz` never sheds, and middleware statuses (408/413/503) answer the per-family error shape so the pub client's retry behavior stays spec-true.

The **pre-compressed `.br`/`.gz`** clause of this decision remains unimplemented on both sides (the web build emits neither, the server serves identity-encoded) — still open here, deliberately not smuggled into the hygiene wave.

## 05 — Anonymous read configurable, default allowed

**Decision.** Public and proxied packages are readable without authentication by default (pub.dev-like DX, public-instance showcase possible). An instance-level `require_auth_for_read` flag flips everything to token-only for strict corporate policies.

Status-code ladder (normative; mirrored in [S-04/S-14](security.md#1-authentication)):

1. **Visibility first**: any package the principal cannot read — another org's private package or an unknown name — returns **404, for anonymous and authenticated principals alike** (GitHub model). A 403-vs-404 differential would let any account holder enumerate other orgs' private names.
2. **401** only for missing/invalid credentials where credentials are required, always with `WWW-Authenticate: Bearer realm="pub", message="…"` — the pub client deletes its stored token on 401, and the message is our only onboarding channel into the CLI.
3. **403** (also carrying `WWW-Authenticate` with an explanatory message) only for insufficient scope/role on a resource the principal can see — e.g. publishing with a read-scoped token.

With `require_auth_for_read` enabled, anonymous requests get the spec-mandated **401** + token-onboarding message (nothing is anonymous-readable, so nothing is enumerable).

**Consequences.** Returning 404 where the spec mandates 401 for protected resources is a **deliberate, documented deviation** (anti-enumeration). Cost: a teammate without a configured token sees "package doesn't exist" instead of "add a token" — mitigated by the org UI's setup snippet (exact `dart pub token add` command) and docs.

**Implementation addendum (2026-08-07, pub protocol HTTP surface).**

- **Where the flag lives, for now.** `require_auth_for_read` ships as boot config (`registry.require_auth_for_read`, default `false`) rather than a `settings`-table row: the runtime-settings cache of [decision 09](#09--always-compiled-backends-runtime-config-selection) does not exist yet. It moves into the table when that lands; the flag's semantics do not depend on where it is read from. This is the one place where the current code reads an "instance setting" from boot config.
- **Ordering inside the ladder.** Credentials are judged **before** existence: the auth extractor runs ahead of the org lookup, so with `require_auth_for_read` on, an anonymous caller gets 401 for an unknown org slug too, instead of a 404 that would confirm which orgs exist on the instance. Org slugs get the same anti-enumeration treatment as package names — an unknown `/o/{slug}/pub` is 404 with no challenge.
- **Unrouted paths under a registry base answer the spec error shape**, not the SPA shell: a client asking for an endpoint we have not implemented (`…/advisories` today) must get parseable JSON, not an HTML page.

**Amendment (2026-08-07, the flag moved into the settings table — closes the D31 half).** The addendum above promised `require_auth_for_read` would move out of boot config "when the runtime-settings cache lands". It landed; the flag did not move, and that stale interim is now closed: a sixth settings section `registry` carries the flag, boot config remains its **default** per [decision 09](#09--always-compiled-backends-runtime-config-selection), and the pub-protocol extractor reads `runtime.current().registry.require_auth_for_read`. The extractor's ordering rule is untouched — credentials are still judged before the org lookup, or org slugs become enumerable.

Two consequences worth naming, because this is the **first security-relevant flag to enter the always-readable cache**:

- **A corrupt `registry` section falls back to the operator's boot value**, not to a hard default and not to an error. That is decision 09's deliberate always-readable failure mode applied to a flag that gates anonymous reads; it is defensible (the operator's own configured intent is the safest thing to fall back to) but it means a mangled row silently restores boot behaviour rather than announcing itself.
- **A rolling upgrade can differ per replica.** An older binary ignores a section it does not know, so during a mixed-version window anonymous readability may differ between replicas. This is the same forward-compatibility trade decision 09 already accepted for `registration` — recorded again here because it is now visible to *unauthenticated* callers.

## 06 — Retract + admin-only hard delete with tombstone

**Decision.** Published versions are immutable; version numbers are never reusable. The normal lifecycle tool is **retraction** (version stays downloadable, excluded from new resolutions) plus package-level `discontinued`/`replaced-by` and `unlisted`. Hard delete exists for corporate reality (leaked secrets, legal takedown): requires org owner/admin role **and** step-up authentication, writes an audit event, removes bytes from blob storage, and leaves a tombstone — the name+version stays burned forever. Deviation from pub.dev's "publishing is forever" is deliberate and gated.

**Implementation addendum (2026-08-07, registry data layer + publish pipeline).** Three details the design left open, decided while building it:

- **What a tombstone is, physically.** Hard delete does not delete the row: it sets `versions.tombstone`, clears the metadata document (`pubspec` → `{}`) and the rendered README/CHANGELOG, and keeps `archive_sha256` and `archive_size`. Clearing the payload matters because the usual reason for a hard delete *is* leaked material; keeping the hash keeps blob accounting honest. The `(package_id, version)` unique index is deliberately **not** partial, so it covers tombstones and the number can never be republished. Tombstoned versions vanish from listings but remain findable by exact version, so callers can distinguish "burned" from "never existed".
- **Blob removal is conditional.** Storage is content-addressed, so several versions can share one object (byte-identical uploads; later, proxy-cached upstream archives). The service deletes the blob only when no live version still references the hash — otherwise it keeps the bytes and records `blob_removed: false` in the audit event. Deleting shared bytes would break a hash already pinned in somebody's `pubspec.lock` ([protocol.md sharp edge 3](protocol.md#sharp-edges-violate--break-clients)).

  **Addendum (2026-08-07, unreferenced-blob GC).** The bytes a conditional delete keeps become collectable when the last sharer goes, which is what `jobs/src/gc.rs` sweeps up — together with the orphans an interrupted publish leaves (bytes are written before the version row on purpose) and staged uploads nobody finalized. Three rules make it safe: a key is collectable only when **both** registers agree — live `versions` *and* cached `upstream_versions`, because the proxy stores its archives under the same content-addressed keys a local publish does; nothing inside the grace period is touched (`min_age`, default 24 h, validated to exceed the 1-hour staged-upload TTL — an upload is finalizable, and therefore live, that whole time with no row referencing it); and a key the job does not fully recognize is left strictly alone. It ships **disabled and dry-run**, because byte stability is the one property this system cannot repair after the fact.
- **Un-retraction has a window; retraction does not.** Retracting is always allowed; restoring is allowed for `registry.unretract_window_days` (default **7**, pub.dev's rule) after the retraction. The flag propagates into resolvers and lockfile decisions, so flipping it back weeks later resurrects a version the ecosystem has already routed around. The window lives in the service layer — the repository only records the flag.

**Implementation addendum (2026-08-07, management surface).** Two consequences of "the number stays burned forever" that only became visible once orgs could be deleted:

- **Deleting an organization that owns packages *archives* it; it never erases it.** A name claim and a version row are exactly the things decision 06 promises survive forever, and both hang off the org row by foreign key — so erasing the org would either fail halfway through or un-burn a claimed name. `DELETE /api/v1/orgs/{slug}` therefore refuses with **409** while the org owns packages, and `force: true` takes the only other coherent path: `orgs.archived_at` is stamped, every membership and invitation is deleted, every org-bound token is revoked, and every package is flipped **private + unlisted + discontinued** through the registry service (so the search index follows in the same breath). The org then serves nothing and discloses nothing, its slug stays taken, and nothing a `pubspec.lock` pins changes. An org with no packages *is* erased outright — there is nothing durable to protect. Archived orgs answer **404** on the public profile and on every management route: they are gone as far as the product is concerned, and the row is a storage artefact. The alternative designs were both worse: cascading the packages away contradicts this decision outright, and refusing forever leaves an operator with no way to retire an organization at all.
- **Hard delete gained a mandatory `reason`, and a confirmation that names the version.** `DELETE /api/v1/packages/{name}/versions/{version}` takes `{confirm: "{name}@{version}", reason}` on top of the Admin role and the S-06 step-up. The reason goes into the audit event: "who destroyed these bytes" without "why" is not an answer anybody can act on months later, and this is the one operation in the system with no undo.

## 07 — Upstream proxy: read-through cache AND mirror mode

**Decision.** Both modes ship:

- **Read-through** (default): on first request, fetch listing/archive from pub.dev, verify `archive_sha256` at ingest, store bytes forever (byte-identical, never re-tar), serve from cache from then on; stale-serving when upstream is down; circuit breaker on upstream failures.
- **Mirror mode**: a periodic sync worker watches upstream for changes and pulls them proactively (full enumeration via `/api/package-names` for the initial sweep and drift repair, recent-changes polling for the fast path). Enables air-gap-adjacent and regional-mirror deployments. Same ingest pipeline as read-through — mirror mode is "read-through warmed by a worker", not a second implementation.

Retraction/discontinued/advisories metadata from upstream is refreshed on listing fetches and preserved verbatim.

**Implementation addendum (2026-08-07, read-through proxy).** Seven things the decision left open, decided while landing the read-through half:

- **A cached listing has a TTL, and that TTL is the product decision.** The pub client re-fetches the version listing before *every* resolve, so "read-through" cannot mean "ask upstream on every request" — that is a proxy, not a cache, and it makes upstream's availability our availability. `upstream.listing_ttl_secs` (default **300**) is therefore the knob that trades how quickly an upstream retraction becomes visible here against how much traffic leaves the instance. Archives have no TTL: they are immutable by [S-18](security.md#4-supply-chain--registry-integrity), so once verified they are cached forever.
- **The upstream is a trait, and there is exactly one door into it.** `UpstreamClient` (real impl over reqwest+rustls; a scripted one in tests) keeps every integrity, staleness, and concurrency behaviour testable without a network — the behaviours only exist when upstream *misbehaves*, and a suite that needs a misbehaving pub.dev does not run. The pipeline behind it is entered from one place, `resolve_target` in the pub protocol module, and only on `Resolution::Unclaimed`; the `Target::Upstream` arm *carries* the service, so a handler cannot reach the proxy for a locally claimed name even by accident (S-16).
- **A degraded upstream is a 404, never a 5xx.** Unreachable upstream, open circuit, refused bytes, malformed listing: whatever is cached is served with a staleness marker in tracing and metrics, and whatever was never cached answers 404. A 5xx here would be retried up to seven times by the client ([protocol.md sharp edge 2](protocol.md#sharp-edges-violate--break-clients)) — one upstream outage becoming a retry storm. The staleness marker deliberately stays **off the wire**: the response shape is the spec's, and an extra field or header would be a protocol change no client asked for.
- **An upstream 404 does not evict.** pub.dev does not unpublish, so a 404 for a package we hold cached is far more likely an upstream defect than a real disappearance — and it does not count against the circuit breaker either, since it is a fact about the package, not about upstream's health.
- **The circuit breaker is per-instance and in-process.** It protects this instance's request threads and latency; a breaker shared through the KV layer would turn one instance's network partition into everybody's outage, which is the opposite of what a breaker is for. Half-open lets exactly one probe through with its failure budget already spent, so a failed probe re-opens immediately.
- **Single-flight is a per-key lock plus a cache re-check**, not a shared future: N simultaneous misses of one package produce one upstream fetch, and the followers pay one cache read rather than inheriting the leader's error. Distinct packages never queue behind each other; a separate semaphore caps total in-flight upstream requests.
- **`advisoriesUpdated` is stored verbatim but not re-emitted.** Sharp edge 11 makes the field a promise that `…/advisories` exists and agrees with it; advertising it while the endpoint is unimplemented would make every proxied package fail an advisory fetch. The snapshot keeps the value so the field can be switched on with the endpoint, not re-derived later.

**Verified against the real pub.dev and the real client** (Dart SDK 3.12.2, 2026-08-07): a proxied listing of `path` re-emits all 76 versions with pub.dev's own `archive_sha256` set and pubspecs byte-for-byte, with every `archive_url` rewritten to the instance; the proxied archive is byte-identical to pub.dev's and its hash is what lands in `pubspec.lock`; `dart pub get` resolves an 11-package graph through the proxy and the resolved code runs; and with the upstream made unreachable the same resolve still succeeds from cache while an uncached name answers one clean "could not find package", not a retry storm.

**Implementation addendum (2026-08-07, mirror worker).** The second half is built: a leader-locked worker in the jobs crate (`jobs/src/mirror.rs`) driving `UpstreamService::refresh`, plus the S-17 alarm the mode makes detectable. Six decisions the "periodic sync worker" sentence left open:

- **"Warmed by a worker" is enforced by the entry point, not by convention.** The worker owns exactly one thing — *when* — and `refresh` is `listing` with the read TTL replaced by a caller-supplied freshness floor. Same validator, same hash-before-store, same byte-drift freeze, same breaker, same semaphore, same single-flight, same snapshot writer. There is no mirror-only ingest path to drift from the read-through one, which is the failure mode a second implementation would have.
- **Both modes chunk, and the chunk is the tick's cost bound.** `full` walks upstream's `/api/package-names` index; `recent` walks our own cache **oldest snapshot first** (`upstream_packages_stale_idx`, created for this in migration 0004). The second needs no cursor by construction: refreshing a package moves it to the back of that ordering, so repeated ticks sweep the whole cache and an interrupted tick simply re-reads what it had not reached. `chunk` bounds how long one tick holds the leader lock; `concurrency` bounds our in-flight refreshes while the service's semaphore still bounds upstream's.
- **The sweep cursor is durable and the page cache is not.** `jobs.cursor` holds `{page, offset, completed_at}` as JSON; a restart resumes at 30 000 names in rather than at zero. The fetched index page is cached in-process purely so a chunked sweep does not re-download several megabytes per tick — losing it costs one fetch, never progress. Re-processing a handful of names across a restart is a *mirror completeness* question the next pass settles, not a correctness one: nothing here decides what a client resolves.
- **A sweep repeats.** `resweep_after` (default 24 h) restarts enumeration after a completed one. This is not only decision 07's "drift repair": enumeration is the **only** channel through which this instance can ever learn that upstream has *started* carrying a name we claim, because the read path structurally never asks upstream about a claimed name (S-16). A mirror that enumerated once would go permanently blind to new S-17 shadowing.
- **A claimed name is observed and then left alone.** Finding one on the sweep raises the S-17 alarm and skips the package: caching it would store bytes resolution can never serve. This is the second of the two arrival orders — the first (a publish claiming a name we already proxy) is detected in the publish pipeline, which is where that order becomes visible.
- **Bytes are opt-in.** `[upstream.mirror] archives = false` by default mirrors metadata only and leaves archives to the read-through path — resolution stays fast, storage stays small. An air-gapped instance sets it and pays for it, bounded per pass by `archive_versions` (newest live versions first; retracted ones are skipped, since they are excluded from new resolutions anyway).

Everything is off by default (`mode = "off"`): mirroring is a deliberate decision about egress and storage, and the config validator refuses a mirror with `upstream.enabled = false` — a worker fetching packages resolution can never serve is an expensive way to do nothing that looks like a working mirror from outside.

**Verified against the real pub.dev** (`pubd` on SQLite + filesystem blobs, 2026-08-07). `mode = "full"` with a 6-package chunk swept pub.dev's index — **86 642 names**, 1.6 MB decompressed, one page, `nextUrl: null` — mirroring metadata and the newest archive of each package. The process was killed mid-sweep and restarted: the first tick after the restart resumed at the stored offset and answered `skipped: 6` with **zero** upstream requests, because the packages the interrupted tick had already saved were inside the freshness floor; the following ticks continued from there and the counters accumulated across the restart. A name claimed locally (`aaroh_chat`, which pub.dev also carries) produced the S-17 alarm — one `upstream.shadowing` audit row, one register row, and **no** `upstream_packages` row for it. A blob-GC dry run over the resulting store enumerated all 58 objects and found every one referenced through the proxy cache.

That session also produced the one wire-level surprise: **pub.dev answers `406 NotAcceptable` on `/api/package-names` unless the request carries `Accept-Encoding: gzip`** ("Client must accept gzip content") — so the header is mandatory there, not an optimization. It is sent on the two JSON endpoints and gzip is decoded **by hand** (flate2, with the size cap applied to the *decoded* document); the HTTP client is deliberately left without transparent content decoding, because a client that silently decodes bodies would also decode an archive body, and "the bytes we hash and store are the bytes that arrived" is the proxy's core promise ([sharp edge 3](protocol.md#sharp-edges-violate--break-clients), S-19). 45 of the 86 642 names are legacy mixed-case ones that predate pub's naming rules; they are dropped from the sweep with a counted warning, since they could not be claimed here and their pubspecs would fail the publish validator too.

**Implementation addendum (2026-08-07, adversarial review of the proxy surface).** One rule was wrong and is now stated explicitly, because it is the difference between a breaker that protects the instance and one that takes it down:

- **Only *reachability* failures reach the circuit breaker.** The breaker is per-instance and instance-wide, so whatever opens it degrades every package. The original code counted every non-404 failure, which put "upstream answered promptly with a document our validator refuses" and "upstream is unreachable" in the same bucket — and since the pub client re-fetches a listing before *every* resolve, one CI job on one such package would have opened the circuit for the whole instance, over and over. A listing we cannot use, like a 404, is a fact about **one package**; a timeout, a connection error, or the transient status family is a fact about **upstream**. Symmetrically, the archive path now feeds the breaker too: with a warm listing cache and a dead archive host it was the only thing still going out, and it was the one branch the breaker could not see. Recorded in [S-19.a](security.md#4-supply-chain--registry-integrity) with the other findings from that review (special-use hostnames in the SSRF guard, a short body named as a transport failure rather than as tampering, and `Content-Length` no longer sizing an allocation).

The same review measured the one residue it could not close: an unclaimed-name miss costs an upstream round trip while a claimed-but-unreadable name costs two indexed reads, so two byte-identical 404s differ by ~640× in latency and a name's *claimed-ness* is timeable without a credential. Every uniform-latency alternative is worse than the leak; `require_auth_for_read` is what closes it. [S-04.c](security.md#1-authentication) carries the numbers and the reasoning — and [S-16.b](security.md#4-supply-chain--registry-integrity) records that `upstream_policy = block` binds to the org's *base*, not to its members, who can still reach upstream through the public root.

## 09 — Always-compiled backends, runtime config selection

**Decision.** No cargo feature matrix for backends. All implementations (sqlite+postgres, fs+s3+memory, moka+redis) compile into every binary; config selects at startup (kellnr's proven model). Boot config comes from layered sources: defaults → TOML file → env (`PUB_*`-style prefix, `_FILE` suffix support for secret mounts) → CLI flags; validated with fail-fast startup errors and a printed effective-config summary (secrets masked). Runtime-changeable settings (SMTP, rate limits, proxy policy, org policies, banners) live in a `settings` table, cached per instance via `ArcSwap`, invalidated across instances through the KV broker.

**Implementation addendum (2026-08-07, runtime settings + the admin surface).** The `settings` half of this decision is now live (`core/src/settings.rs`, `PATCH /api/v1/admin/settings`). Six things it left open:

- **Boot config is the *default* of a runtime setting, not a competing source.** `Settings::runtime_defaults()` projects the TOML/env layer onto the document, and `SettingsCache` serves `defaults + stored sections`. So an instance whose `settings` table was never written behaves exactly as its config file says; the moment an administrator writes a section, the stored one wins; clearing it falls back again. Two sources with no defined precedence is how "which value is live?" becomes unanswerable, and the summary an operator reads at startup would start lying.
- **A *section* is the unit of change.** Six keys — `registration`, `rate_limits`, `smtp`, `branding`, `upstream`, and `registry` (added 2026-08-08 with `require_auth_for_read`, see the amendment to [decision 05](#05--anonymous-read-configurable-default-allowed)) — each holding a whole section, each with its own version. A single blob would make a SMTP change clobber a concurrent branding change; a field-level patch would need a merge rule per field and would race identically. A section this build does not know is left untouched rather than dropped, so a rolling upgrade cannot lose a newer release's settings.
- **The cache is always readable, and that is a deliberate failure mode.** An absent, corrupt, or unparseable section falls back to the boot default with a warning instead of failing the read. These settings gate registration and rate limits: an outage that closed sign-in instance-wide would be a worse failure than serving the operator's configured values.
- **Propagation is a broker publish *plus* a version poll, and the poll is the one that is load-bearing.** A write goes `SettingsRepo::upsert` → local `reload` → `Kv::publish(settings.changed)`; peers reload on the message, and reconcile through `SettingsCache::refresh_if_changed` every 45 s regardless. Redis pub/sub guarantees nothing across a reconnect, and "instance 3 is still enforcing the old rate limit" is invisible from outside. `SettingsRepo::get_version` (the sum of per-key versions) makes the poll one integer comparison. The publish is best-effort: a broker outage costs one poll interval, never the durability of a write that is already committed.
- **What is *not* runtime-changeable stays boot-only** ([S-25](security.md#6-secrets--configuration)): the DB URL, blob credentials, the Redis URL, the JWT keyring, the OTP pepper, the KEK, OIDC client secrets, and the public base URL. The one credential that moved is the **SMTP password**, which S-26 already places in the settings table — it is sealed under the env KEK before storage, accepted on write, and never returned (the read DTO has no field for it). So does `auth.instance_admins`, for a different reason: it is the bootstrap of the very surface that edits settings, and a list stored *in* that surface would let one compromised admin session make itself permanent.
- **Instance administration is bootstrapped two ways, and neither needs a running admin.** `auth.instance_admins` is a boot-config email list, applied at startup to existing accounts and at registration to new ones. When it is empty — the default, and the whole point of the `docker run` deployment minimum — the **first account created on an instance that has no administrator yet** becomes one, through a single-statement `UPDATE … WHERE NOT EXISTS (SELECT 1 FROM users WHERE is_instance_admin)`, so two concurrent first registrations cannot both win it. Removing an address from the list does **not** demote: revoking administration is an audited action on the admin surface, not a side effect of a config edit somebody may have reverted by accident.

**Amendment (2026-08-07, the mailer resolves from the cache — closes D10).** Runtime SMTP was accepted, sealed and audited by the admin surface, and then ignored: the mailer was built once at boot from `[smtp]` and frozen into three services, so an operator who configured SMTP only in the UI got an instance that delivered no mail while the UI reported `password_set: true`. The stored password had **no reader at all** — nothing ever unsealed it. Four rules close it:

- **Resolution happens per send, memoized on a fingerprint of the *sealed* section.** A `RuntimeMailer` reads the settings cache at the top of every send and compares a fingerprint of (host, port, username, from, security, `password_sealed`) against the transport it is holding; only a mismatch unseals and rebuilds. Fingerprinting the sealed blob means a password rotation is detected without unsealing anything on the hot path. The memo is not polish: the SMTP transport is a connection pool, and rebuilding per send would throw pooling away.
- **A failed rebuild keeps the previous transport — but there must *be* one.** An unparsable `from` address or a bad host is logged once per fingerprint, not applied. One typo in the admin UI must not turn off sign-in instance-wide — the same stance decision 09 already takes for an unparseable section. **Amended 2026-08-07 after the wave's adversarial review**: this rule was implemented as "keep the previous transport, or fall back to the in-memory sink", and the second half is a silent black hole. After a restart nothing is memoized, so an unbuildable section sent every sign-in code into an in-process `Vec` while the queue marked each row delivered, the counters reported success and the test-mail action answered `delivered: true` for a host it never contacted — an instance nobody can sign in to where every signal says mail works, where the same misconfiguration used to be a hard boot failure. The correct behaviour: the in-memory fallback covers the **no host configured** case only; a configured-but-unbuildable section with nothing memoized is an **error on the send path**, which the queue turns into a retry and then a dead letter — visible, countable and answerable. A failure mode nobody can observe is not graceful degradation (the same principle decision 22's amendment states).
- **An unbuildable section is refused at the write, not discovered at the send.** The runtime validator parses `from` as a mailbox and builds the relay before storing, so the admin surface answers 400 with the offending field instead of accepting a section that will fail hours later on a path with no user attached.
- **The boot password applies only to the boot endpoint — host, port, username *and transport security*.** `runtime_defaults()` does not project `[smtp].password` into `password_sealed`, so "runtime SMTP with the operator's boot password" needs an explicit rule: the boot credential is used **only when the effective host, port, username and security mode all equal the boot values**; otherwise an absent sealed password means no credentials. (**Security added 2026-08-07** by the wave's adversarial review, which found the three-field version insufficient: an instance admin who never held the password could PATCH the section to `security = "none"`, leaving host/port/username untouched so the boot fallback still applied, and then trigger a send — putting `AUTH PLAIN` with the operator's credential on the wire in cleartext. The gate exists to keep that credential out of an instance admin's reach, and a downgrade is as effective a redirection as a new hostname.)

  **Corrected the same day, after the fix pass was itself reviewed.** This bullet first carried a second clause — "a boot-provenance credential is never attached to an unencrypted transport" — added as belt and braces. It was wrong in both directions and shipped as a regression that two independent verification lenses caught. Against the *attack* it is dead code: once `security` joined the endpoint gate, a runtime downgrade can no longer reach the boot credential at all, so the second guard can never fire on an instance admin. Against the *operator* it is live code: `security = "none"` with a password is a legal, validated and documented boot configuration — a local relay that wants SMTP AUTH without TLS — and refusing to build it, combined with the new rule that an unbuildable section fails the send, turned that deployment into a total mail outage where every message dead-letters and nobody can sign in. **The endpoint gate is the entire mechanism.** An operator who configures an unencrypted relay with credentials in their own boot file has made an explicit choice about their own network; the product's job is to stop an *instance admin* from redirecting that credential, which the gate does. Without that clause an instance administrator sets `smtp.host` to a server they control, leaves the password unset, and receives the operator's SMTP credential — an instance-admin → operator-credential escalation that the write-only design of [S-26.a](security.md#6-secrets--configuration) does not otherwise cover, because it is about *reading back*, not about *redirecting*. Clearing the runtime password still falls back to boot, subject to the same match.
- **Propagation is lazy, and "current settings" ≠ "current mailer".** A peer that sends no mail never rebuilds; it rebuilds on its next send after its 45 s reconciliation. That is strictly weaker than the settings version being current, and it is the honest statement — nothing pushes a transport rebuild.

A **"send test mail" admin action** (`POST /api/v1/admin/settings/smtp/test`) accompanies this, because a write-only credential with lazy propagation is otherwise undiagnosable. It is deliberately shaped: it takes no recipient (the acting administrator's own verified address is the target, which removes the mail-bomb vector and needs no new S-24 bucket), a delivery failure is `200 {delivered:false, detail}` rather than a 5xx (a wrong SMTP config is not a server fault), it audits on **both** outcomes and never records a credential, it calls the mailer directly rather than riding the queue of [decision 26](#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path) (synchronous diagnosis is its entire purpose), and it is **not** S-06 step-up gated — it neither escalates authority nor destroys anything, and this sentence exists so a reviewer reads that as a decision rather than an oversight.

Finally, the runtime plane now mirrors the boot validator's refusal of a username without a password (accounting for the boot fallback above). Today it can store a half-credential that the transport silently drops while the surface reports `password_set: false` next to a filled-in username.

**Decision.** One `BlobStore` trait in `core`, implemented over `object_store` (LocalFileSystem, InMemory, AmazonS3-compatible incl. MinIO). Downloads return `DownloadPlan::Redirect(presigned_url)` where the backend supports signing (S3) or `DownloadPlan::Stream(...)` (fs/memory) — decided per request, designed in from day one. ## 11 — Search behind a trait

**Decision.** `PackageSearch` trait with per-database implementations: PostgreSQL `tsvector` + GIN + `pg_trgm`; SQLite FTS5 with sync triggers. No external search service; tantivy/Meilisearch possible later as a third impl. Filter vocabulary copies pub.dev's tag architecture (`sdk:`, `platform:`, `topic:`, `is:`, `license:`, `dependency:`) plus a cross-format `format:` tag (decision 21) so search, badges, and API stay consistent across the whole artifact space.

**Implementation addendum (2026-08-07, search backend + public read model).** Migration 0007 in both dialects, and seven decisions the trait sentence left open:

- **The index is a denormalized document, not a view over `packages`.** One `package_search` row per package that has at least one live version, carrying the newest version's description, topics, README text, and the counts the UI renders — plus a `package_tags` table holding the exact-match dimensions (`topic:`, `dependency:`) and, with them, the reverse dependency graph. Searching the live tables instead would mean a JSON scan of every pubspec per query. The cost is that the index is **derived data**: it is rebuildable in full by `jobs/src/reindex.rs`, which is precisely what makes it safe for the publish path to log an index-write failure rather than fail a publish whose bytes, rows, and audit record are already committed.
- **Visibility is enforced *inside* the implementation, through the existing chokepoint.** Every read takes a `SearchView` — the set of orgs in which `authorize(actor, ReadPackages, …)` succeeds, computed by calling that function, not by reimplementing it — and each backend emits `visibility = 'public' OR org_id ∈ view` before anything the query grammar can influence. No filter, text, or cursor can widen it. `unlisted` gets a second mandatory clause: hidden from discovery everywhere except inside its own org, which is what the flag means (it stays resolvable by name — that is `resolve`, a different question). Facet totals and instance counters run the same predicate, because a count that disagrees with the listing leaks exactly what the listing hides ([S-04.d](security.md#1-authentication)).
- **The parser never fails.** A search box is the one input where a syntax error must not be an error page: unparseable tokens are collected into `unknown_filters` and echoed back, so the UI can say what it ignored. It also removes an oracle — a malformed filter and a filter that matched nothing look the same. Untrusted text never becomes engine syntax: every term is quoted (FTS5 `"…"`, tsquery `'…'`), so `OR`, `NEAR`, `&`, `!`, `<->`, and `:` inside a term are data.
- **"Ascending score is best" is a cross-backend convention, and it is what lets the cursor codec live in `core`.** SQLite's `bm25()` is already negative-is-better; Postgres' `ts_rank_cd` is negated to match. Cursors are keyset and **ordering-bound**: the token carries a one-character sort tag, and presenting it under a different `sort` is `invalid_argument` rather than a silently reshuffled page.
- **`relevance` without query text degrades to `updated`.** There is nothing to rank, and ordering by an all-zero score would make pagination depend on the database's row order.
- **The backends are allowed to differ in *recall*, never in visibility.** Postgres adds fuzzy name matching through `pg_trgm` (`blok` → `flutter_bloc`); SQLite gets prefix matching but no typo tolerance, because a full-text index matches lexemes and a typo is not a lexeme. The trigram branch only ever adds rows; everything the contract suite asserts holds identically on both.
- **The read model serves *local* packages only.** A name that resolves through the upstream proxy has no package row here and answers 404 on the app API — proxied packages are installable but not browsable. Making them browsable means rendering somebody else's metadata under our chrome and is a product decision of its own; it lands with the upstream-cache admin surface.

Two supporting choices recorded here because they are visible on the wire: **instance counters are scoped to the caller's view** (an absolute package count on a public page publishes the size of every org's private inventory, and an absolute zero on a fully private instance is a useless dashboard), and the **publishing account is shown only inside the owning org** — the organization is this registry's publisher (orgs replace pub.dev's publishers), and a public page has no reason to hand out staff names.

Branding for the landing dashboard (`GET /api/v1/home`) shipped as boot config `[branding]`, the same interim arrangement `registry.require_auth_for_read` used: [decision 09](#09--always-compiled-backends-runtime-config-selection) files it under runtime settings, and it moves into the `settings` table when the `ArcSwap` cache lands. **Both interims are now closed** — branding reads the cache (see [decision 17](#17--branding-default-pub-white-label-token-prefix-pub_)), and the flag moved with the `registry` section ([decision 05](#05--anonymous-read-configurable-default-allowed)).

## 12 — Auth factors

**Decision.** Self-written auth, no Firebase, no auth SaaS. Sign-in paths: (a) **email OTP — the always-available baseline** — 8-digit CSPRNG code, hashed at rest, 10-minute expiry, single-use, ≤5 attempts per code, resend throttling, uniform anti-enumeration responses; (b) **OIDC — fully optional (zero or more providers configured)**: each provider is issuer + client id/secret + display label; Google is the first-class preset but any spec-compliant IdP works (the `openidconnect` crate is provider-agnostic; corporate buyers often ban consumer Google). Confidential client, authorization code + PKCE S256, `state` + `nonce`, full `id_token` validation, identity keyed by `(iss, sub)`, account linking only via verified email. An instance-level **sign-in domain policy** (email-domain allowlist, e.g. only `@corp.com`) applies uniformly to OIDC and OTP across sign-in/registration/invites ([S-31](security.md#7-platform)). Optional **TOTP authenticator app** as a second factor (email OTP is a single factor per NIST 800-63B and is never marketed as MFA), plus hashed one-time recovery codes. Step-up (fresh second factor, "sudo mode") required for the dangerous actions enumerated in [S-06](security.md#1-authentication) — the normative list lives there. WebAuthn/passkeys: schema-prepared (polymorphic `credentials` table), targeted at v1.1.

**Implementation addendum (2026-08-07, OIDC + TOTP slice).** Three choices made at build time, recorded here because they refine the letter of the design; normative detail in [S-01.a/S-02.a/S-05.a/S-06.a](security.md#1-authentication):

- The OIDC crate is hand-rolled over the same strict-verification core as the S-07 JWT plane (the `openidconnect` crate named above was not adopted — one JWS verifier style across the codebase, no unused surface). The browser↔flow binder is an opaque server-side **`flow_id`** (KV record: state/nonce/PKCE verifier), not a `__Host-` cookie — the API stays cookieless per decision 03; the binding property is preserved.
- A **never-seen OIDC identity requires a verified email** to link or register; a known `(iss, sub)` signs in without one. Unverifiable identities are refused rather than parked in half-registered accounts.
- **Step-up freshness = fresh login ∨ fresh step-up verification** within `auth.step_up_minutes` (default 15). Accounts without TOTP satisfy S-06's "or re-auth" arm by logging in again; the step-up endpoint itself demands an enrolled second factor.

## 13 — CLI/API token format

**Decision.** GitHub-style: `<prefix>_<30 base62 chars><6 base62 CRC32 checksum>` (~178 bits entropy; prefix TBD with product name, see 17). Stored as SHA-256 hash + first-8-chars display hint (argon2 deliberately not used: tokens are high-entropy and verified per request — crates.io rationale). Scopes: `read`, `publish`, `retract`, `admin`; org-bound, optional package-name patterns; default expiry 90 days; last-used tracking (write-throttled); show-once UX with the exact `dart pub token add` command; published regex for secret scanners; revocation effective within ≤60 s (no server-side token caching beyond that). The credential-type enum leaves room for short-lived exchanged CI credentials — trusted publishing via GitHub/GitLab OIDC token exchange (later tier).

**Implementation addendum (2026-08-07, pub protocol HTTP surface).**

- **The header, and nowhere else.** Tokens are accepted on `Authorization: Bearer` only. The spec defines no query-parameter credential and the client sends none, so `?token=` is not supported — a query credential lands in access logs, proxy logs, and `Referer` headers, and would reach users' `pubspec.lock` files through `archive_url`.
- **The offline checks are the plane boundary.** Prefix + length + base62 charset + CRC32 run before the hash lookup, which is what makes a browser access JWT structurally unusable on pub routes ([decision 03](#03--sessions-jwt-access--refresh-sessions-kv-backed-revocation)'s "never mixed") without a hand-written special case, and keeps fabricated strings off the database.
- **Package patterns**: a trailing `*` matches any suffix, anything else is an exact name; an empty list means no narrowing. Deliberately not a regex — this is an authorization decision, and a catastrophic-backtracking pattern would be a denial of service with extra steps. Patterns narrow reads of **private** packages only (a public package is readable with no credential at all, so hiding one would make a token worse than none) and are enforced at publish **finalize**, which is the first moment a package name exists in the flow.
- **The role is re-derived per request** from the durable membership, never cached in the token row: a token outlives role changes by design, so a user who has left the org authenticates and authorizes nothing.

**Addendum (2026-08-07, authority changes reach the token plane — closes D37; owner-decided).** Re-deriving the role per request keeps a stale token from *authorizing* anything, but the credential itself used to survive every authority change — a suspended user's token authenticated normally, and a demoted member's `admin`-scoped token sat in the list looking legitimate. Three rules close that:

- **A lowered role revokes the tokens the new role can no longer mint.** On `AuthorityChange::Redefined` downward and on `Withdrawn`, the member's tokens in that org whose scopes exceed the new level are revoked (withdrawal revokes them all). "What a scope is worth" has exactly one source — the same scope→action mapping the mint gate uses (`read`→Read, `publish`/`retract`→Write, `admin`→Admin) — evaluated in Rust over `list`+`revoke`, never duplicated into per-dialect SQL. A *raised* role revokes nothing, mirroring S-09.a's grant row. Each sweep audits `token.revoked` with the authority-change reason and a count; notification-wise it piggybacks on the existing `org.member` event rather than growing a new variant.
- **Suspension gates the credential plane at the repository.** `find_active_by_hash` answers only tokens of `active` users (a join, not a service-layer read), so a suspended account's tokens stop authenticating within the S-13 ≤60 s bound and resume on unsuspension — reversible, like suspension itself. On the wire a suspended user's token is indistinguishable from a revoked one (uniform 401, S-14.a-consistent); the pub client will drop its stored copy, which after unsuspension costs one `dart pub token add` — accepted.
- **Tokens can be scoped below the holder's role by design** (org binding + scope sets + package patterns), so the sweep compares *the token's scopes*, not the holder, against the new level: a Read-scoped token survives a demotion to Read untouched.

## 14 — Frontend shape

**Decision.** Bun workspaces monorepo. `apps/site` — Astro 7: landing + docs as SSG with per-locale routes; `/app/[...rest]` is a prerendered shell mounting a single `client:only` SolidJS island with `@solidjs/router` (browser mode). ## 19 — RBAC: cumulative role levels with a single authorize() chokepoint

**Context.** Org roles here are genuinely cumulative — Read ⊂ Read+Write ⊂ RW+Admin ⊂ RW+Admin+Owner. A bitmask earns its complexity only when permissions are non-linear (auditor-only, retract-only, billing-only); in this design that plane is already served by scoped CLI tokens and, later, per-package grants — so the org role can stay linear.

**Decision.** An org membership carries an **ordered role level**, stored as a small integer with gaps for future insertions: `0` none, `50` **Read** (resolve/download), `100` **Write** (publish, manage own packages), `200` **Admin** (members, tokens, package settings), `250` **Owner** (org lifecycle, danger zone). Checks are `level >= required`; an intermediate role (e.g. a future `150` Maintainer) slots in without migration. Wire protocol and UI use role *names* — numbers are a storage/comparison detail. JWT claims carry `{org_id: level}` (decision 03). Every check flows through a single `authorize(actor, action, resource)` chokepoint, so if a genuinely non-linear org permission ever appears, adding a bitmask overlay is a contained refactor, not an audit of scattered comparisons. Invariants: ≥1 Owner per org; invitations default to Read; grants at Write level or above are step-up-gated (S-06). CLI-token scopes (`read`/`publish`/`retract`/`admin`) remain the fine-grained, non-linear plane.

**Implementation addendum (2026-08-07, management + administration surface).** Four decisions the ladder sentence left open, all made while wiring the mutations:

- **Instance administration is a second, orthogonal plane — not the top of this ladder.** `Action::AdministerInstance` on `Resource::Instance` is decided by `users.is_instance_admin`, and the two ladders never imply each other: an org Owner administers their org, an instance admin holds no org role they were not granted. Extending the role ladder upwards instead would have meant "Owner of any org" quietly becoming a step towards reading every org's private inventory. `authorize()` additionally refuses a **mismatched** action/resource pair (an org action aimed at the instance, or vice versa) rather than falling through, so a wiring mistake is a denial and not an accidental grant on the other plane.
- **The admin flag is read from the row per request, never from a token.** [S-07](security.md#2-sessions--web-plane) limits access-token claims to `sub`/`sid`/org levels/timestamps, and an `adm` claim would be a deviation from a normative requirement for no gain — while costing correctness, since a demotion would then take up to one access TTL to bite. The `InstanceAdmin` extractor pays one indexed read on a surface nobody calls in a loop, and a demotion or suspension is effective on the very next request.
- **The org slug is immutable.** It *is* the virtual registry base (`/o/{slug}/pub`, decision 01), so `PATCH /api/v1/orgs/{slug}` carries name, description, and upstream policy — and no slug. Renaming it would break every `PUB_HOSTED_URL`, every stored `archive_url`, and every CI token configuration pointing at the old one, silently and all at once.
- **Org management answers 403 where package management answers 404.** Org slugs are not secret ([S-04.b](security.md#1-authentication)), so an insufficient role on a real org is a 403 that tells a Read member what they are missing. Packages are the opposite: a management route resolves the package through the read model's own ladder *first*, so a package the caller cannot read answers the same 404 an unknown name does — checking the role first would make `PATCH /api/v1/packages/{name}/options` an existence oracle for another org's private packages.

**Addendum (2026-08-07, role-grant ceiling — closes D39; owner-decided).** `ManageMembers` said who may manage members; nothing said *which levels* they may touch, so an org Admin could grant — or become, through an accomplice — an Owner. The decided rule:

- **A non-Owner actor manages only levels strictly below their own** — both the level being granted *and* the level the target currently holds (an Admin neither appoints another Admin nor demotes or removes one). **An Owner is exempt from the ceiling entirely** and manages every level including other Owners; the ≥1-Owner invariant stays enforced transactionally in the repositories and is unaffected.
- **Self-directed *reduction* is always allowed** (owner-decided 2026-08-07): a member may demote themselves to any lower level or remove themselves regardless of the ceiling, because lowering your own authority is never an escalation — this is how an Admin leaves an organization today. Self-*raising* stays under the ceiling (an Admin cannot promote themselves to Owner), and the ≥1-Owner invariant still blocks a sole Owner's self-removal or self-demotion with the same `last_owner` 409. A dedicated Read/Write leave route does not exist yet (those roles never reach the management surface); that affordance lands with the account surface (S-29) and is recorded as roadmap debt.
- **Invitation *revocation* is deliberately ceiling-exempt.** Cancelling a pending invitation destroys a grant rather than making one, so any member who can manage invitations (Admin+) may revoke any pending invitation including an Owner-level one an Owner sent — the worst case is undoing a grant that had not taken effect, never acquiring authority.
- **The check lives in the org service**, next to `apply_authority_change`, so every mutation path (add, role change, removal, invitation *creation*) inherits it and no route can forget it. Invitations are ceiling-checked when sent; the role is frozen into the row (as it always was — "an invitation never lowers"), so a later demotion of the inviter does not retroactively invalidate an outstanding invitation. Denials are the standard `forbidden` 403 whose message names role *names*, not numbers, per this decision's wire rule; no new error code (the UI prevents rather than branches).
- **The UI warns before Admin and Owner transitions** — assigning either level, and demoting or removing a holder of either — with a confirmation dialog; role pickers offer only levels the caller's ceiling allows. This is presentation on top of the server rule, never a substitute for it.

## 20 — Realtime: SSE event stream + notification center

**Decision.** The backend exposes a Server-Sent-Events stream (`GET /api/v1/events`) for live updates: package publishes/retractions in the principal's orgs, membership and invitation events, shadowing alarms, token-expiry warnings, admin announcements, settings changes for admin UIs. Delivery: per-instance in-process broadcast, fanned out across instances via the KV broker (Redis pub/sub) — consistent with decision 03's scaling gate; single instance needs no extra infra. Implementation notes: the browser client uses fetch-streaming rather than `EventSource` (which cannot set an `Authorization` header); keep-alive comments; best-effort `Last-Event-ID` replay from a short per-user ring buffer — the stream is a hint channel, the REST API remains the source of truth. On top of the same events sits a **notification center**: per-user persisted notifications (unread counts, mark-read, preferences per category), with email delivery for high-importance ones (invites, security events). Security constraints in [S-32](security.md#7-platform).

**Implementation addendum (2026-08-07, the realtime layer).** Seven decisions the sentence above left open, all made while wiring `crates/events`, `GET /api/v1/events`, and the notification surface:

- **The audience is a property of the event, not a rule in the stream.** `DomainEvent::audience()` answers `Org(id)` | `Instance` | `User(id)`, and the SSE filter consults **nothing else** — no package flags, no per-variant special case. That is what keeps a new event variant from defaulting to "everybody" by omission: the match is exhaustive, so adding one without deciding its audience does not compile. Org-scoped events reach that org's `Read+` members and nobody else, *including for a public package*: the stream is a member's channel over their own organizations, the public read model is the REST API, and the alternative would let a package flipped to private mid-stream still announce its next publish to strangers.
- **The replay ring is per *instance*, not per user.** The design said "a short per-user ring buffer"; a per-user buffer would require resolving every event's audience to a user set at *emit* time and keeping a queue per account — a fan-out cost paid for readers who are not connected. The implementation keeps one bounded ring of recent envelopes per instance and applies the **same** visibility filter to a replay that it applies to live delivery, so the guarantee a reader gets is identical and no principal can widen what they see by reconnecting. Event ids are ULIDs minted where the event originates, so a `Last-Event-ID` from instance A still compares in time order against instance B's ring.
- **Consumers run only on the instance that emitted the event.** A peer receiving an event over the broker feeds it to its *stream* and to nothing else. The notification center running on every replica would file one row per replica for one event, which is how a fan-out becomes a duplicate factory. The broker payload therefore carries an `origin`, which is also the loop breaker for Redis echoing a publisher its own messages.
- **A consumer's output re-enters the stream, never the consumers.** The notification center returns one `UserNotified` event per recipient; those are broadcast and republished but not fed back through the consumer list, so there is no cycle to bound. `UserNotified` additionally reports **no notification category**, which is what makes "the notification center cannot notify itself" structural rather than a guard somebody can delete.
- **Notification fan-out happens at write time, one row per recipient.** Storing the event once and filtering per reader would mean a member who joins tomorrow inherits today's private-package activity, and a member who leaves keeps seeing it. The cost is bounded by `realtime.max_notification_recipients` (default 200, validated ≤ 500 because the batched preference lookup binds one parameter per recipient); past the bound the fan-out is capped with a counted warning rather than growing a publish request without limit.
- **Three categories, not one per event type.** `package` | `org` | `security`, with the event→category map on the event itself. A preference list curated per event *name* is a preference list nobody curates. `org` and `security` are the high-importance tier and reach a mailbox by default; `package` does not, because a publish firehose in everybody's inbox is the fastest way to get the sender filtered into a folder and the other two categories missed. `security` additionally narrows the org audience to **Admin+** — a shadowing alarm is addressed to the people who can act on it.
- **Known gap, recorded rather than papered over: deleting an org notifies nobody.** `OrgDeleted` is org-scoped, and by the time it is emitted the deletion has already removed every membership, so the audience resolves empty. The affected members *do* get their sessions revoked (S-09), which is the signal they act on. Closing it properly needs either a user-scoped variant or a recipient list on the event; it lands with the webhook work, which needs per-subscriber addressing anyway.

**Amendment (2026-08-07, fan-out moves off the request path — closes D2).** "Fan-out happens at write time, one row per recipient" was a statement about *storage shape* that the implementation also read as a statement about *when*, and the bill came due on the publish path: one finalize with 200 recipients ran ~400 queries, up to 200 blocking SMTP sessions and 200 follow-up broker publishes **inside a request the pub client retries up to seven times**. The storage shape is right and is kept. The timing is not.

- **The emitting request writes exactly one row.** The bus consumer becomes an enqueuer: one durable job carrying the event envelope, deduplicated on the event id. Audience resolution, the batched insert, the unread counts and the mail all move into the worker. In-request cost becomes constant in the recipient count — which is Phase 2's exit criterion for this item, and is asserted by a test that publishes to a 1-member and a 150-member org and demands identical row counts.
- **`UserNotified` follow-ups are published only after the batch transaction commits.** The event contract promises that a client acting on an event finds the row; publishing from inside the transaction would break exactly that. The fan-out's own queue row is completed in that same transaction, which is what makes fan-out **exactly once** rather than at-least-once (a transactional outbox), while mail stays at-least-once by design.
- **The recipient cap stays at 200 in this wave, and its justification is now weaker.** The addendum above justified the cap by cost *on the publish path* — "an org with thousands of members would otherwise turn one publish into thousands of inserts on the publish path". Off the request path that argument evaporates, and the cap stops being a latency guard and becomes a silent correctness loss: members 201..N of a large org never learn about a publish, a membership change or a shadowing alarm. Deliberately **not** resolved by this wave, because raising or removing it is a product decision about who gets notified, not a consequence of moving the work — and bundling it into a mechanical relocation is how product policy gets invented by an implementer. The number stays where it is, its meaning is now "a pure abuse bound", and the choice between keeping it, raising the default, and paging the membership inside the worker is recorded as roadmap debt (D42). Note for whoever takes it: moving the number is coupled to the 500-recipient batch clamp in both dialects' preference lookup and to the validator's ≤500 rule.

## 21 — Multi-format artifact space (pub first; npm, cargo, … later)

**Decision.** The registry is designed Artifactory-style as a **single artifact space over multiple package formats**. V1 ships the pub protocol only, but every shared seam is format-agnostic from day one:

- Core entities carry a `format` discriminator: packages unique per `(format, name)`; name claims, resolution policy, and shadowing alarms are per-format; version rows hold common fields (version, ordering key, sha256, retracted, timestamps) plus format-specific metadata as JSON (pubspec / package.json / Cargo index entry).
- The blob store is content-addressed and format-blind already.
- URL space reserves the format segment now: `/o/{org}/pub` (future `/o/{org}/npm`, `/o/{org}/cargo`), public roots `/pub` (future `/npm`, `/cargo`). The `api` crate hosts one protocol module per format, each implementing its wire contract against the shared core traits.
- One search across formats (`format:` filter tag), one permission model (decision 19), one token plane (scopes apply uniformly per format), one audit/notification/webhook pipeline.
- Upstream proxying generalizes: per-format upstreams (pub.dev, registry.npmjs.org, crates.io) share the ingest pipeline, integrity rules (S-19), and policy engine (S-16).

**Consequences.** Pub-specific logic (pubspec parsing, advisories mapping, README pipeline specifics) lives in the pub protocol module and format adapters — never in shared entities. npm's `@scope/name` maps naturally onto orgs; cargo needs a sparse-index endpoint — both are protocol-module work, not core rework. Non-goal for v1: shipping any second format.

**Implementation addendum (2026-08-07, registry data layer).** Two shared seams were fixed while landing the entities; both are format-agnostic by construction and neither can be retrofitted cheaply:

- **Version ordering is a stored precedence key.** `core::SemVer` implements semver.org §11 precedence (pre-release rules included, build metadata excluded), and `SemVer::sort_key()` projects a version onto a string whose *bytewise* order equals that precedence: fixed-width zero-padded core numbers, a release/pre-release marker, and one prefixed segment per pre-release identifier separated by a byte below every legal identifier character. Storing it (`versions.version_sort`) makes version listing and keyset pagination one index scan instead of an in-memory sort, and keeps ordering identical on both backends. It is **collation-sensitive**: the Postgres column carries `COLLATE "C"` because a locale/ICU collation folds punctuation and case and silently reorders pre-releases (verified: an ICU-collated column sorts `1.0.0-a-b` before `1.0.0-a.b`, which is backwards). The contract suite orders a table containing exactly those adversarial pairs on both backends. Other formats reuse the same key — npm and cargo are semver too.
- **Blob keys are `<format>/<sha256[0..2]>/<sha256>.tar.gz`.** Content addressing already makes the hash unique, so the format prefix is not for collision avoidance: it keeps per-format lifecycle operations (a bulk purge, a per-format retention policy, a bucket-level rule) expressible as a prefix, and the two-character shard keeps directory fan-out sane on the filesystem backend.

## 22 — Domain event bus; webhooks and integrations on top

**Decision.** All domain events (publish, retract, membership/invitation, shadowing alarm, token lifecycle, settings changes) flow through **one internal event bus** — the single seam that fans out to: the SSE stream (decision 20), the notification center, the audit log, and **outbound webhooks**. Webhooks (v1.1): configured per org (and instance-wide by admins) with event-type filters; deliveries signed with HMAC-SHA256 (`X-Pub-Signature` header), executed by the jobs crate with exponential-backoff retries and a dead-letter state; delivery log in the UI. Security constraints in [S-33](security.md#7-platform) (SSRF guards, encrypted secrets, TLS-by-default). Richer integrations (Slack/Telegram templates, CI triggers) build on the same bus later.

**Implementation addendum (2026-08-07, the bus itself).** Three things the "one internal event bus" sentence left open:

- **The audit log is *not* a bus consumer, and that is deliberate.** Every service writes its audit row directly, before or alongside the event, because the audit log is **durable truth under a compliance requirement** ([S-22](security.md#5-audit--abuse)) while the bus is explicitly a hint channel whose consumers may fail silently. Routing audit through a sink that swallows errors would make "append-only, INSERT-only, every mutation recorded" depend on a broadcast channel's health. The bus and the audit log share the *vocabulary* (`DomainEvent::name()` is the audit action) and nothing else.
- **`EventSink::emit` returns nothing, and the bus honours that all the way down.** Consumer errors, broker outages, and undecodable peer messages are logged and dropped. A publish whose bytes, rows, and audit record are committed must not fail because a notification could not be written — the same stance the search-index write already takes ([decision 11](#11--search-behind-a-trait)).
- **Webhooks are a seam, not a stub.** `EventConsumer` is the interface a delivery worker will implement; nothing about the bus needs to change to add one, because the consumer contract already returns follow-up events (which is how a delivery-status event will reach the UI) and already runs on exactly one instance per event (which is what stops N replicas from delivering one webhook N times).

**Amendment (2026-08-07, the blast radius of a swallowed emit changed).** "`EventSink::emit` returns nothing, and the bus honours that all the way down" stays true, and a failed enqueue is still swallowed — a publish whose bytes, rows and audit record are committed must not fail because a notification could not be written. But the *cost* of one swallowed call is no longer one recipient's missing row: with [decision 26](#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path) it is an entire event's fan-out **plus every email that fan-out would have produced** — including a sign-in code, which turns a loud 500 into a silent "the mail never arrived". Swallowing therefore now comes with obligations that are part of the contract, not optional instrumentation: a loud error log, a `notification_enqueue_failed_total` counter, and dead-lettered rows that are visible on the admin job surface. A failure mode nobody can observe is not a graceful degradation.

## 23 — Monitoring is optional

**Decision.** Observability exports are config-gated and **off by default**: the Prometheus `/metrics` endpoint (optionally on its own listen address), OTLP trace export, and JSON log shipping are each enabled explicitly. `tracing` instrumentation and `/healthz` are always on — near-free and needed by orchestrators. No monitoring stack is required to run the product.

**Amendment (2026-08-14, when the exports were actually built — see [decision 28](#28--the-observability-plane-its-own-listener-bounded-labels-and-timing-that-stays-opt-in)).** Two of the three clauses above changed shape:

- **"Optionally on its own listen address" became the only shape.** `/metrics` is served by a second listener and is never mounted on the application router; [decision 28](#28--the-observability-plane-its-own-listener-bounded-labels-and-timing-that-stays-opt-in) records the three reasons the main one is the wrong place for it.
- **OTLP is withdrawn, not deferred.** `telemetry.otlp` was a declared flag whose only behaviour was a startup `warn!`. A config key that names a capability the binary does not have is worse than its absence — it survives into an operator's file, their template, and their expectations. The key is **removed**; trace export returns as a decision of its own when it is built, and until then the honest statement is that this product exports metrics and logs, not traces.

JSON log shipping is unchanged in intent and now real: `telemetry.log_format` selects it.

## 24 — Theme registry, Patina palette

> **Status: proposed.** The palette direction was chosen by the owner (2026-08-07); this entry's *wording* has not been reviewed yet.

**Decision.** Four related choices, made together on 2026-08-07:

- **Palette "Patina".** The product's default look is warm graphite neutrals (OKLCH hue 60–85 at whisper chroma) with a desaturated teal accent (hue 195), replacing the initial indigo/violet system. Chosen by the owner from three validated directions; the alternates — *iris* (refined indigo) and *nocturne* (night-blue/blurple) — are kept in `web/packages/tokens/candidates/` as future-theme material, each a complete palette that passes the contrast gate.
- **Themes are a registry, not a light/dark binary.** A theme is a named `[data-theme="<name>"]` block in `packages/tokens/theme.css` overriding the raw `--pub-*` token set; `:root` carries light, which is also the SSR default and the fallback for unknown names. The registry has three synchronized members: the CSS blocks, `THEMES` in `packages/ui/src/theme.ts` (picker + persistence), and the theme list in the anti-FOUC inline script. The contrast gate **discovers** theme blocks by parsing `theme.css` and asserts the same WCAG AA pairs for every theme — registering a theme in CSS is enough to put it under the gate. `localStorage.pub_theme` holds `"system"` or a theme name; anything unknown counts as system, so stale stored values from removed themes degrade gracefully.
- **AMOLED is the third theme.** True-black canvas (`oklch(0 0 0)` — an OLED panel switches those pixels off), surfaces barely lifted, the same Patina accent/status families as dark. It is a darkness variant of dark, not a second brand; `system` resolves only to light/dark — amoled is always an explicit choice. The `dark:` Tailwind variant matches the whole dark family (dark + amoled).
- **Seed-theme seam (documented, not implemented).** A future Material-You-style adaptive theme derives the same raw token set from one seed color at runtime and attaches it under a new `data-theme` scope. The `--pub-*` token *names* are the generation contract; the semantic `@theme` layer needs no changes; a generated set must pass the same contrast pairs the static gate asserts, evaluated at generation time. No generator ships now.

## 25 — Interaction feedback: liquid-glass sheen + ripple

> **Status: accepted.** Records the owner's explicit choice (2026-08-07), made after trying a four-style interactive prototype (no effects / sheen only / ripple only / both): *"ликвид гласс блик везде, риппл только там где есть интерактивность (кнопки, таблицы где строки кликабельны)"*.

**Decision.** The UI kit ships exactly two dynamic interaction effects, with two different scopes:

- **Sheen everywhere.** A liquid-glass specular highlight — a soft `currentColor` radial gradient that follows the pointer — appears on hover on **every control**: buttons (and links styled through `buttonVariants`), menu items, tab triggers, the ThemePicker trigger, and the opt-in `interactive` variants of Card and TableRow. Hover-only by media query (`hover: hover`): on touch the sheen does not exist and the ripple carries the feedback.
- **Ripple only where pressing acts.** A Material-style wave expands from the press point and fades on release (keyboard activation ripples from the center) — on genuinely press-activated elements only: buttons, menu items, tab triggers, `interactive` cards and table rows. Static badges, static cards, and plain rows get neither effect; disabled elements get neither. An interactive Badge/chip variant is deliberately **not** built until a screen needs one.

**Mechanics that keep it inside the design system** (full rules in `web/DESIGN.md` §5a/§7a):

- **`currentColor`, bounded alpha, no new tokens.** Both effects paint the host's own text token at a keyframe-carried opacity ceiling (sheen 10%, ripple 15%), so they read on flat surfaces in all three registered themes, adapt to any future theme for free, and cannot push a gate-checked AA pair under 4.5:1. The §5 gradients ban stands for decoration; §5a records this as the one sanctioned exception.
- **Reduced motion erases, not freezes.** The base state of both layers is invisible; only `forwards`-fill animations reveal them, so the existing global unlayered `animation: none` reset collapses the whole layer with zero motion media checks in JS (a timer replaces `animationend` as the wave's cleanup of last resort).
- **Two Solid directives** (`use:sheen` / `use:ripple` in `packages/ui/src/feedback.ts`, ~1.3 kB minified, wired via `ref` in the kit) plus one component-layer stylesheet (`feedback.css`). Recipes carry the `fx-*` classes; screens never hand-write them. The focus-visible ring contract is untouched (interactive table rows use an inset ring because a `<tr>` clips its ripple via `clip-path`, which would eat an outward ring).

## 26 — Durable job queue: async fan-out and outbound mail off the request path

> **Status: accepted.** Recorded 2026-08-07 before implementation, as the second Phase 2 wave's enabling decision (closes D2, D20; the mechanism [decision 22](#22--domain-event-bus-webhooks-and-integrations-on-top) already promised webhooks would need).

**Context.** [Decision 22](#22--domain-event-bus-webhooks-and-integrations-on-top) gave the product one event bus and called webhooks "a seam, not a stub". [Decision 20](#20--realtime-sse-event-stream--notification-center) put notification fan-out and its email on the emitting request. Both were right about *shape* and silent about *when*, and the result was that the two slowest things in the system — a per-recipient write loop and a blocking SMTP conversation — ran inside HTTP requests, including a publish finalize the pub client retries up to seven times. There is no queue anywhere in the codebase: `crates/jobs` is an interval scheduler and the `jobs` table holds one cursor row per job name.

**Decision.** A **durable, database-backed job queue** becomes the second consumer seam off the event bus.

- **It lives in the database, not in the KV.** `Kv` has no enumeration primitive by design, so a queue cannot be drained from it — the same reason the download-stats store already rejected a KV backing. One `job_queue` table, paired forward-only migrations per dialect, claimed with `FOR UPDATE SKIP LOCKED` on Postgres and a single-writer `UPDATE … RETURNING` on SQLite. The Postgres claim is written now even though multi-instance is Phase 3 ([D1](roadmap.md)), because retrofitting a claim strategy onto a live queue is a change to a path that is already carrying sign-in mail.
- **Two granularities, deliberately different.** One row per **event** for fan-out, one row per **message** for mail. A per-event fan-out row is what makes the fan-out exactly once; per-message mail rows are what give a single bad recipient its own retry and its own dead-letter state instead of poisoning the other 199.
- **Fan-out is exactly once; mail is at-least-once, and that is stated rather than hidden.** The fan-out handler writes every recipient's row *and completes its own queue row* in one transaction (a transactional outbox), plus a dedupe key on the event id. Mail cannot be transactional across an SMTP conversation, so a crash between "sent" and "completed" redelivers — acceptable precisely because [S-03](security.md#1-authentication) makes a duplicate OTP harmless (single-use, replacement-invalidated) and because the alternative, marking sent-before-sending, loses mail instead of duplicating it.
- **The drain is on unconditionally.** Every other job carries an `enabled` key; this one must not. An operator who disables the mail drain cannot sign in to re-enable it, and an instance with no SMTP configured is already covered by the in-memory mailer. It is leader-locked like the other jobs, and retention runs on its own tick so the queue does not become the next unbounded table.

- **Retention is per terminal state, and the three windows mean different things.** (Stated here 2026-08-08, after the fix pass; the original wording said only "done rows purged after 24 h", which described one of the three and was the number five code comments ended up citing a transient debt id for instead.) **`done` rows: 24 h** — a delivered message is kept only long enough to answer "did that actually go out?". **`suppressed` rows: 1 h** — an [S-04.a](security.md#1-authentication) uniformity row has no reader at all once the request that filed it has been answered, and it carries the attempted address, so it is the shortest window and deliberately shorter than `done`. **`dead` rows: 30 d** — a dead letter is the one state an operator still has to act on, so it outlives the others by a wide margin and its deletion is logged individually, naming what is being destroyed. A row in `pending` or `running` is never touched by retention, at any age: retention is not a way to cancel work. Code that needs to explain one of these windows cites *this bullet*, not a debt number — debt ids are transient and get reused, which is exactly how a comment ends up pointing at an unrelated item.
- **Queued mail payloads are sealed under the env KEK** ([S-26](security.md#6-secrets--configuration)): a rendered OTP body is a live credential sitting in a table, and the mechanism for that is the one already sealing TOTP seeds and the SMTP password. Consequence recorded: with the ephemeral development KEK a restart costs at most an undelivered code, because these rows live for minutes.
- **Every send is bounded by a timeout.** This is not a nicety — it *replaces* a bound that this change removes. The transport sets no deadline of its own, and today the only thing truncating a hung SMTP conversation is the `[http]` request deadline. In a worker, a hung relay would hold its lease and then starve every lease behind it.
- **This is the webhook mechanism.** [S-33](security.md#7-platform) webhooks land as another job kind and another handler, with the retry/backoff/dead-letter machinery already built and already tested. Nothing about the bus changes.

**Consequences.**

- **The S-04 timing oracle disappears as a side effect** ([S-04.a](security.md#1-authentication)). `request_otp` mapped an SMTP failure to a 500 for a *deliverable* address while a policy-blocked one answered 200 instantly — an existence oracle you could trigger by taking the mail server down. Both branches now perform one identical enqueue, differing only in the row's state (a blocked address files a **suppressed** row that is never claimable and carries no deliverable payload — its only job is to make the two branches cost the same; the audit log already records the rejection, so the row tells a database reader nothing new). The `?` that produced the 500 is gone, so SMTP can no longer fail a sign-in request at all.
- **Delivery is no longer observable from the response**, which changes what an integration test can assert. The suite drives the real worker to exhaustion at the points where it used to read the outbox synchronously, rather than asserting against a fake — the queue is on the sign-in path, so a test double there would be testing the wrong thing.
- **A queued code's clock does not restart.** The KV pending-auth record remains the authority on expiry and single use per [S-03.a](security.md#1-authentication); queue latency can only make a code arrive too late to use, never extend its life.

**Amendment (2026-08-07, three corrections from the wave's own adversarial review — all recorded before the fixes were written).**

- **Exactly-once fan-out is enforced by a uniqueness constraint, not by a cross-table transaction.** The original wording asked the handler to complete its queue row "in one transaction" with the recipient rows. The implementation could not: the repositories are separate trait objects with no unit-of-work seam, and threading notification rows through the queue repository to borrow its transaction is a layering inversion for one caller. The **stronger** answer was already half-present — migration 0009's own header claims "one row per (recipient, event)" and the schema never enforced it. It does now: `notifications` carries the originating `event_id`, a partial unique index covers `(user_id, event_id)`, and the batched insert is `ON CONFLICT DO NOTHING`. A re-run after a crash converges to the same rows no matter where it died, and — unlike a transaction — the guarantee also holds against any *future* path that re-emits the same event. Mail was already idempotent by its `mail:{event}:{recipient}` dedupe key, which the review verified against both dialects. Net: the promise of this decision is kept and its mechanism is different; the shape it rules out (papering over duplicates in the handler) is still ruled out.
- **The queue has a priority dimension, because one FIFO across kinds starves sign-in.** Interactive mail (a sign-in code, an invitation) and bulk mail (a 200-recipient notification broadcast) share one table and are claimed in id order, so a CI pipeline publishing into a large org can file thousands of rows ahead of the next OTP. At a realistic SMTP pace that backlog outlives `otp::PENDING_TTL`, which means unrelated traffic takes sign-in down instance-wide with nothing dead-lettered and nothing on the admin surface. A `priority` column ordered ahead of the id fixes the ordering, and the drain dispatches a claimed batch with bounded concurrency instead of strictly serially. Adding the dimension now is far cheaper than after [S-33](security.md#7-platform) webhooks become a third kind on the same table.

  **Refined the same day, after the fix pass was reviewed.** "Ordered ahead of the id" was implemented literally, as one statement per claim with `ORDER BY priority, id` — which put `priority` between `kind` and `run_after` in the index and thereby demoted `run_after <= now` from a seek bound to a post-filter. Measured on the relay-outage shape (200k rows backed off into the future, the exact state the retry ladder produces): **6.59 ms per claim against 0.006 ms**, on a write statement that holds SQLite's single write lock up to 64 times per tick; on Postgres the planner abandoned the index for a sequential scan. The claim therefore **drains one priority lane at a time** — an equality on `priority`, ordered `run_after, id` inside it — which restores the seek and is a *stronger* fairness property than ordering within one batch, because the interactive lane is emptied before the bulk lane is touched at all. Two consequences: within a lane the claim order is **readiness order**, so a row that has been retried repeatedly does not cut ahead of everything filed while it was waiting; and the lane set is **closed** (`INTERACTIVE`, `BULK`) with both repositories refusing an off-lane enqueue, because a lane nobody claims is a row nobody delivers. Adding a lane later is still a constant, not a migration.
- **The send timeout does not bound a drain; the drain bounds itself.** This decision said a per-send timeout is what stops a hung relay from starving the queue. It is not sufficient: a tick could claim batch after batch, each item paying the full timeout, so one drain could run far past its own lease and past the scheduler's lock TTL — after which a second drain acquires the lock, reaps the still-running items back to `pending`, and re-sends them. The timeout stays, and three bounds join it: the drain re-reads the clock per pass (so leases and retry backoffs are computed from the real present rather than from the tick's start), the drain stops when it has consumed a fraction of its own lease, and the job lock is released only by the holder that took it.

## 27 — Rate-limit identity: what a bucket is keyed on, and what happens when the KV is down

> **Status: accepted.** Recorded 2026-08-14 before implementation, as the Phase 2 wave-2 enabling decision for the limiter (closes [D14](roadmap.md), [D41](roadmap.md) and [S-13](security.md#3-cliapi-tokens)'s unimplemented "per-token rate limits"; the atomic half of the same roadmap item closed in wave 1 as [S-24.d](security.md#5-audit--abuse)).

**Context.** [S-24](security.md#5-audit--abuse) promises limiting "per-IP / per-account / per-token / per-org", an in-process fallback when the KV is down, and read-path limiting that fails open. What exists is six credential endpoints bucketed per IP, one publish budget per org, and nothing else: the read path is unbucketed on both planes, a token is not a rate-limit identity anywhere, and a KV outage answers 503 and takes sign-in down instance-wide ([S-24.e](security.md#5-audit--abuse)). The three gaps share one root — **no notion of "who is this request" exists before the handler runs**, so every bucket that has ever been added was keyed on the only thing the middleware could see.

**Decision.** The limiter gets an identity model, and the identity is derived from the request alone — no database read, on any plane.

- **Three identity classes, resolved in this order.**
  1. `tok:{sha256(secret)[..16]}` when the bearer credential passes the **offline** CLI-token gate (`token::validate` — prefix, length, charset, CRC32; the same check `authenticate_cli_token` runs before it touches the database). This is [S-13](security.md#3-cliapi-tokens)'s per-token limit.
  2. `usr:{sub}` when the bearer credential is an access JWT that **verifies** (Ed25519 against the keyring — local, no I/O). Verified, never decoded-and-trusted: an unverified `sub` would let anyone spend a victim's budget by asserting their user id.
  3. `ip:{client_ip}` for everything else, including a credential that is neither of the above, resolved under the [S-24.a](security.md#5-audit--abuse) trusted-proxy stance.
- **The key holds a truncated hash, never a credential.** 16 hex characters of the token's SHA-256 — enough to separate tokens, and a collision merges two budgets, which is the strict direction. The full hash is what the database stores; there is no reason for a second system to hold a credential-equivalent value.
- **Read-path buckets exist on both planes and fail open.** Two numbers rather than one per surface: `read_per_ip_minute` (default 600) applies to `ip:` identities, `read_per_identity_minute` (default 3000) to `tok:` and `usr:`. Identity keying is the entire point of the split — a CI fleet behind one NAT is one IP and many tokens, while a scraper is one IP and no credential, so a single per-IP number cannot be set to a value that is both meaningful for the second and survivable for the first. A KV error allows the request and logs; this is a quota, not a gate, and [S-24](security.md#5-audit--abuse) says so.
- **The forged-token loophole is bounded by a bucket that already exists, and no lookup is added to prove it.** An attacker can mint unlimited CRC32-valid strings and therefore unlimited `tok:` buckets. On the pub protocol plane every such request fails `authenticate_cli_token`, which spends `token_auth_fail_per_ip_minute` (30/min/IP) — so the whole family is bounded per IP by a limit that predates this decision. On the app-API plane a CLI token never authenticates at all: the request is refused by the extractor before it reaches the database. Neither plane offers amplification, so the middleware stays lookup-free. **This is the clause to re-check** if a future plane starts accepting CLI tokens without spending the failure budget.
- **`/healthz` stays exempt and becomes cheap.** [S-24](security.md#5-audit--abuse) exempts health checks and that does not change; what changes is the cost of the exemption. Its three backend pings are memoized for one second, so a probe loop cannot be used as an unauthenticated three-backend amplifier — the complaint behind [D14](roadmap.md)'s mention of it. One second is short enough that no orchestrator observes a stale verdict and long enough that a flood collapses to one probe per backend per second.
- **The SSE stream is exempt**, for the same reason it is exempt from the request deadline: it is one request per session, not a rate.
- **Auth-abuse buckets fail closed onto a per-instance in-process limiter** (closes [D41](roadmap.md), rewrites [S-24.e](security.md#5-audit--abuse)). A fixed-size table of atomic slots, the bucket key hashed into a slot: memory is bounded **by construction** rather than by an eviction policy, which matters because the keys are attacker-chosen (`rl:otp:email:{address}`). Slot collisions merge two buckets' counts, which can only refuse more, never less.

**Consequences.**

- **The fallback is looser than the KV it replaces, and the number is stated rather than discovered.** With N replicas, the aggregate budget during a KV outage is up to **N × the limit**, because each instance counts alone. That is the honest cost of the requirement as written; the alternative currently shipping is a 503 that takes sign-in down instance-wide for the length of the outage. A limiter that is N times looser for a few minutes is the smaller failure, and an operator reading [S-24.e](security.md#5-audit--abuse) now sees the trade instead of a promise.
- **A read bucket is advisory and a credential bucket is not.** Two stances now coexist in one middleware; each call site names its own, exactly as [S-24.d](security.md#5-audit--abuse) established for the KV error path.
- **The publish budget is untouched** — still per org, still failing open per [S-24.c](security.md#5-audit--abuse).
- **A large CI fleet sharing one token shares one bucket.** 3000 requests/minute is far above a `dart pub get` over a few hundred dependencies and far below what a runaway loop produces, but the shape is worth documenting rather than tuning blind: the number is runtime-changeable from the admin surface, and the bucket fails open, so the failure mode of guessing wrong is slow, not broken.

## 28 — The observability plane: its own listener, bounded labels, and timing that stays opt-in

> **Status: accepted.** Recorded 2026-08-14 before implementation (closes [D9](roadmap.md); amends [decision 23](#23--monitoring-is-optional), whose "optionally on its own listen address" this makes the only shape).

**Context.** The Prometheus recorder installs behind `telemetry.prometheus` and its handle is retained for the whole process — and consumed by nothing. There is no `/metrics` route, so 21 emitted instruments are unreachable, there are zero HTTP metrics and zero histograms, the log format is hard-coded, and `telemetry.otlp` is a `warn!`. The roadmap's scout found four traps inside the obvious implementation; this decision exists so they are answered by design rather than rediscovered.

**Decision.**

- **`/metrics` is served by its own listener** (`telemetry.metrics_listen`, default `127.0.0.1:9090`, bound only when `telemetry.prometheus = true`) and is **never** mounted on the application router. Three independent reasons, each fatal on its own: the D8 load shedder exempts only `/healthz`, so a main-listener scrape goes dark exactly when the instance is saturated and the scrape matters most; `family_of("/metrics")` is `Family::Other`, so the response would carry no cache tier at all; and mounting it on the instance's public origin makes internal cardinality a public artifact by default, forcing an authentication stance onto a surface whose entire ecosystem assumes a network boundary instead. A separate listener answers all three and needs no auth clause. The default binds loopback: an operator who scrapes from another host sets the address deliberately, and the ops page says so.
- **The `route` label is bounded by construction.** It is `MatchedPath` when present, and otherwise **one constant per response family** (`{api}`, `{pub}`, `{asset}`) — never `uri().path()`. Both routers' fallbacks (`assets::spa_fallback`, `pub_v2`'s `unimplemented_endpoint`) leave `MatchedPath` unset, so the textbook derivation hands any unauthenticated caller an unbounded label and a memory leak dressed as a metric.
- **The recorder gets an upkeep task.** `install_recorder` spawns nothing; with only counters and gauges that is harmless, and it stops being harmless in this same decision, which adds the first histogram. Upkeep is spawned wherever the recorder is installed, not left to the caller who happens to add the next instrument.
- **HTTP RED metrics**: `http_requests_total{route,method,status}` and an `http_request_duration_seconds` histogram on the same labels, recorded **outside** the shed and the deadline so that 503s, 408s and 429s are counted rather than being the responses that go missing.
- **`Server-Timing` is opt-in, off by default, and never emitted on the authentication family** ([S-04.d](security.md#1-authentication)). The header hands a client an exact server-side duration; on a surface that answers 404 for both "no such package" and "not yours" (decision 05) and 401 uniformly for unknown/revoked/expired ([S-14](security.md#3-cliapi-tokens)), that converts a network-noise measurement into a clean read. Three places had instructed an implementer to emit it and none qualified it — which is how [D20](roadmap.md)'s freshly closed timing oracle would have been reopened by the least-resistance implementation. The gate is now written down *before* the header exists: `telemetry.server_timing = false` by default, and the auth family is excluded even when it is true.
- **`telemetry.log_format = "pretty" | "json"`** replaces the hard-coded value, so log shipping needs no code change.
- **`telemetry.otlp` is removed** rather than deferred — see the [decision 23](#23--monitoring-is-optional) amendment.
- **The metric catalogue is checked, not maintained.** `architecture.md` lists 11 names against 21 emitted, with nothing asserting the two agree. Every instrument gets a `describe_*!` (so the exposition carries `# HELP` and `# TYPE`), the descriptions live in one catalogue in the telemetry crate, and a test asserts the document's table matches that catalogue exactly — the same shape as the generated config reference's drift test.

**Consequences.**

- **A second listener is a second thing to bind, and a bind failure is fatal.** An address already in use means the operator asked for an export they are not getting; failing at startup is the same stance the rest of the config validator takes.
- **Docker exposes one port and documents the second.** The image keeps its single `EXPOSE`; the ops page shows the compose mapping and warns that `0.0.0.0:9090` publishes an unauthenticated surface.
- **`publishes_total` starts being emitted**, from the publish finalize — it was in the catalogue and in no code path.
- **The histogram is the first instrument with unbounded internal state**, which is why upkeep is part of this decision rather than a follow-up.

## 29 — A mail plane that cannot hide, and an offline way back in

> **Status: accepted.** Recorded 2026-08-14 before implementation (closes [D43](roadmap.md), the one Critical debt outside Phase 3, and the ops half of [D53](roadmap.md)).

**Context.** [Decision 26](#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path) moved outbound mail off the request path, which is right and has a cost nobody paid at the time: a dead mail plane is now **invisible for about twenty-one minutes** (eight attempts over a 1270-second ladder before a row can reach `dead`) and every surface that would show it needs an authenticated instance-admin session. On an OTP-only instance a dead mail plane is precisely what prevents obtaining that session, and there is no offline path back in — a stored `smtp` section replaces the boot section wholesale, so correcting the config file and restarting does not restore mail, and `pubd` ships one subcommand.

**Decision.**

- **The signal fires on the first failure, not on the eighth.** A `mail_transport_unusable` gauge is set when the transport cannot be resolved — at startup and on any send — and cleared on the next success, so it is a state, not an event. Alongside it, the **first** delivery failure of a message writes one audit row (`mail.delivery_failed`); the retries do not, because an audit log that grows with the retry ladder is a log nobody reads. Neither signal waits for the attempt budget and neither requires a session: the gauge is on the [decision 28](#28--the-observability-plane-its-own-listener-bounded-labels-and-timing-that-stays-opt-in) listener, the audit row is a durable table row an operator can read straight from the database.
- **An alert rule ships with the product**, not as a suggestion in prose — `docs/ops/monitoring.md` carries the Prometheus rules for this gauge and for the supply-chain signals ([D9](roadmap.md)'s "reference dashboard and alert rules"), so an operator's first exposure to the mail plane's health is not an incident.
- **`pubd reset-smtp` is the supported offline path back in.** It deletes the stored `smtp` section — which requires a `SettingsRepo::delete` the trait did not have — so the operator's boot `[smtp]` becomes authoritative again. It runs once the configuration has loaded — which is where it reads the database URL and the boot section it is restoring — needs no other subsystem, and a running instance picks the change up through the existing version poll without a restart. Unlike `generate-secrets` it does require a config that validates, which is the right trade: the instance this rescues is a running one whose config is fine and whose mail plane is not.
- **Minting a session offline is deliberately not built.** Recorded so the next reader does not re-derive it: on the default deployment the KV is in-process, so an offline `pubd` cannot inject a pending OTP into the running server's KV at all, and a minted refresh session would be a second credential-issuing path guarded only by filesystem access. `reset-smtp` plus a correct `[smtp]` restores OTP sign-in, which is what the exit condition asks for. If a deployment ever needs the session path, it is its own decision.
- **The number the admin surface already computes gets rendered.** The standing dead count is the drain job's `phase` string, returned by `GET /api/v1/admin/stats` and dropped by the web jobs table; the table renders it.

**Consequences.**

- **A gauge that is `1` on a transport nobody uses is correct, not noise.** An instance with no SMTP configured resolves to the in-memory sink, which is a *success* — the gauge stays 0. It goes to 1 only when a host is configured and the transport cannot be built or the send fails, which is the state an operator must act on.
- **`SettingsRepo::delete` is a new capability on a runtime-settings surface**, so it is contract-tested on both dialects and reachable only from the offline subcommand — no API route deletes a section, because the admin API's "clear this" already means "write an empty section" and those are different operations with different results.
- **The KEK inventories grow a line.** Queued mail bodies are sealed under `auth.kek` and dead-letter on the *first* attempt if it cannot open them, so a restore under a different KEK silently discards in-flight messages; the backup and runbook inventories name that now.

## 30 — Retention: one window per table, a delete that stays bounded, and a privilege that survives the feature

> **Status: accepted.** Recorded 2026-08-14 before implementation (Phase 2 item 6, wave 3a). Closes the data half of [D12](roadmap.md) plus [D46](roadmap.md), [D47](roadmap.md) and [D48](roadmap.md); rewrites [S-23](security.md#5-audit--abuse) and amends [S-22](security.md#5-audit--abuse) and [S-06](security.md#1-authentication).

**Context.** Six tables grow without a bound: `sessions`, `invitations`, `notifications`, `download_stats`, `audit_log`, and `job_queue` — the last of which has retention already and spends it in three unbatched `DELETE`s on every five-second drain tick ([D47](roadmap.md)). S-23 is one sentence naming three different windows and an export nobody built. And the feature walks straight into a documented hardening: the Postgres provisioning template ends with `REVOKE UPDATE, DELETE, TRUNCATE ON audit_log FROM pub_app`, `AuditRepo` matches it by exposing no delete at all, and **no CI leg would notice** a retention job failing at the database, because compose and CI both connect as the owner ([D46](roadmap.md)).

The owner's constraint shapes every clause below: retention has to work **automatically on a default install**, configured by "how long to keep" and nothing else. An operator who never reads this document must still end up with an instance that does not grow forever — which rules out a maintenance DSN as a *precondition* and rules out a CLI-only answer.

**Decision.**

- **One window per table, expressed in days, `0` meaning keep forever.** `[jobs.lifecycle]` carries `retain_audit_days` (default **730** ≈ 24 months), `retain_sessions_days` (**30**), `retain_invitations_days` (**30**), `retain_notifications_days` (**180**) and `retain_download_stats_days` (**0**). No per-row-state sub-conditions: a read notification and an unread one age the same, a revoked session and an expired one age the same. The knob an operator turns is a number of days per table, and that is the whole model.
- **The queue's three windows stay under `[jobs.queue]`, and only the executor moves.** `retain_done_hours`, `retain_suppressed_hours` and `retain_dead_days` are per-*state* properties of that one table, they are already documented and validated there, and renaming them would break every existing config file for no behavioural gain. The lifecycle job reads them from where they are. What this decision moves is who spends them, not where they are written.
- **A session row is never purgeable while it could still authenticate.** The predicate is `last_seen_at < cutoff`, and the validator requires `retain_sessions_days >= auth.refresh_idle_days` (default 30 = 30), so the row is deleted no earlier than the moment the idle window has already made it unusable. An invitation is aged from when it *settled* — `COALESCE(accepted_at, revoked_at, expires_at) < cutoff` — which makes a live pending invitation structurally undeletable at any window, rather than relying on a validator to notice that a 1-day retention would break a 7-day invitation link.
- **The audit log's window is uniform across actions**, which is where this deliberately deviates from S-23's three windows (auth 12 mo, admin/role 24 mo, publish = package lifetime). One general log rendered by one general viewer whose history depth silently depends on which action you filter for is a surface nobody can reason about, and three windows are three numbers to configure for one table. The uniform window is safe because **provenance does not live in the audit log**: `versions.published_by`, `published_by_token` and `published_at` are columns on the version row (S-21), so purging a two-year-old `package.publish` audit event loses the *access record*, never the *provenance*. S-23 is rewritten to say this rather than left contradicted.
- **On Postgres, retention deletes through a `SECURITY DEFINER` function, and the app role still gets no DELETE.** Migration 0012 creates `pub_audit_prune(cutoff timestamptz, batch int) RETURNS bigint`, owned by the role that runs migrations; the `REVOKE UPDATE, DELETE, TRUNCATE ON audit_log` in the 0002 template **stays exactly as it is**. This is the answer because it keeps the property S-22 actually buys: evidence of an attack is *recent*, a blanket `GRANT DELETE ON audit_log` hands a code regression or an injection exactly the rows that matter, and this hands it nothing newer than a month. Three details the adversarial review corrected, each of which the first cut got wrong:
  - **`search_path = pg_catalog, public, pg_temp` *and* `public.`-qualified references.** Pinning the path alone is not the hardening it looks like: Postgres searches an implicit `pg_temp` **first** for relation names unless `pg_temp` is listed explicitly, so a caller could `CREATE TEMP TABLE audit_log (…)` and have the function delete from that — returning a plausible row count while the real log grew forever and the job reported a converged sweep. Demonstrated live against PG 17. Fail-safe for S-22 (evidence preserved, not destroyed) and not an escalation route, but a silent no-op on the one job whose whole promise is that it is never silent.
  - **The database's floor is 29 days, not 30, and the slack is deliberate.** `INTERVAL '30 days'` is calendar arithmetic in the session's `TimeZone` while `chrono::Duration::days(30)` is exactly 720 h, so across an autumn DST transition — or under any NTP skew between the application host and the database host — the two disagree in the refusing direction. Set equal, a legal `retain_audit_days = 30` becomes a prune that fails every pass for about a month, diagnosed by a log line telling the operator to add a grant they already have. The application enforces the real floor; the database refuses what no clock could explain.
  - **`EXECUTE` is revoked from `PUBLIC`.** The default grant would have meant "no operator action required", which is why the first cut relied on it — but on a shared cluster it also hands every role that can reach the database the prune capability over this instance's audit log. The explicit grant is the right trade precisely because the missing-grant path is already built and loud.
- **A privilege error disables audit retention loudly instead of failing every tick.** If the prune is refused by the database, the job records the failure in its durable `JobState`, sets a gauge, logs once per pass naming the missing grant and the ops page that fixes it, and **continues with the other tables**. A tick that dies on audit does not stop sessions from being purged.
- **Every window is its own off switch.** `0` means keep forever, per table, and that is the only way to stop retention on a table. There is no job-level `enabled`: it would be a second and coarser way to say the same thing, and it would also stop the queue's three windows — which live in `[jobs.queue]`, are validated greater than zero there, and include the `suppressed` rows an unauthenticated endpoint files with the attempted address in the clear ([S-04.a](security.md#1-authentication)). Before this decision that purge rode the drain, which has no `enabled` key either; moving the executor must not quietly give it one.
- **Every retention delete is batched and converges across passes.** Each `purge`/`prune` takes a batch bound, deletes at most that many rows per statement, and the caller loops until a pass deletes fewer rows than the batch or the job's wall-clock budget is spent. On SQLite the bound is `WHERE id IN (SELECT id … LIMIT n)`, because `DELETE … LIMIT` needs a non-default compile flag. This is the general form of D47's exit, and it is a correctness property, not a nicety: on SQLite one unbounded `DELETE` holds the process's single write lock for its full duration, and any hold beyond the 5 s busy timeout turns a concurrent publish-finalize or sign-in into `SQLITE_BUSY` rather than a wait. The releases that make a backlog appear at once are ordinary operator actions — lowering a window, restoring a backup, a forward clock correction, a stop long enough for a block of rows to cross the cutoff.
- **One job deletes, and it is not the drain.** A new leader-locked `lifecycle-purge` job (`[jobs.lifecycle]`, every **900 s**, **no `enabled` key at all** — the same shape the drain has, because every window is already its own switch and a job-level flag would silently stop the queue's three windows, which are configured in `[jobs.queue]`; the review found that exact regression) owns every retention delete in the instance, and `QueueRepo::purge` stops being called from the drain tick. The drain delivers; the lifecycle job deletes. That closes D47 structurally rather than by bounding an unbudgeted statement on a five-second tick, and it means the answer to "what deleted my row" is one job, one report, one set of metrics. The interval is fifteen minutes rather than an hour for one reason worth naming: the queue's `suppressed` rows carry addresses typed at a login form by unauthenticated callers on a one-hour window, and moving their deletion from a 5-second tick to an hourly one would have doubled their worst-case lifetime. Fifteen minutes leaves that window essentially as chosen.
- **`download_stats` and version tombstones are excluded, deliberately, and it is written here so nobody "finishes" D12 by deleting them.** Tombstones are what make a hard-deleted version number unpublishable again (decision 06, S-18) — deleting one re-opens a hash somebody pinned. Daily download rows are chart data whose per-version granularity cannot be reconstructed after the fact (the `download_stats` header says so); the correct bound is a monthly roll-up, which is a v1.1 feature, not a purge. `retain_download_stats_days` exists and defaults to `0`.
- **The export is a streaming NDJSON walk that says when it finished.** `GET /api/v1/admin/audit/export` takes the viewer's filters plus an optional `cursor`, walks keyset pages newest-first, and writes one JSON event per line as it goes — one request gets the whole filtered log, and a client whose connection broke resumes from the last id it received. The body ends with a single terminator line (`{"done":true,"count":N}`) because a silently truncated compliance export is worse than a failed one, and once the response head is sent there is no status code left to say so. Instance-admin only, **step-up gated** (an S-06 addendum: the list is about escalation, and this is bulk exfiltration of every actor, IP and user agent the instance has recorded — the one case where "not escalation" is not a reason to skip the prompt), its own rate-limit bucket (12 per hour per administrator, a constant rather than a config key — it bounds a cost, and the S-24.f read budget this route also rides is 3000 a minute, which is the right number for `dart pub get` and the wrong one for a full-table walk), and the request itself writes an `audit.export` row **before** the walk starts, which S-22 already names as an auditable event: an export cut off halfway still happened, and a row appended after a stream that never finished would not exist.
- **The scheduler's lock TTL becomes per registered job** (D48), through a `JobLockTtls` table that the scheduler *and* the manual-run registry are both constructed with. A table rather than a parameter on `Scheduler::add`, deliberately: the invariant at risk is that two code paths taking the same lock under the same name agree on its lifetime, and a per-call-site parameter is exactly the shape that lets them drift — which is how the defect arose. `JobRegistry` reads the same table instead of its own hardcoded 300 s, and only the drain's entry is still derived from `jobs.queue.lease_secs`, so a queue lease stops setting the lock TTL of mirror sync, reindex, blob GC and the download rollup. This wave forces the fix: adding a sixth job to a scheduler with one global TTL derived from a queue lease would give the new job a lock lifetime that means nothing about it.

**Consequences.**

- **A default install now deletes rows on its own.** That is the point, and it is still a behaviour change for anyone upgrading: the first pass on an instance older than a window releases a backlog. The batch bound plus the convergence loop is what makes that survivable rather than a lock-up, and the job's first report names what it removed.
- **The audit log's retention path is dialect-asymmetric in mechanism and identical in contract.** Postgres calls a function it may not be granted; SQLite issues a bounded `DELETE` where the trait boundary is the only enforcement. One trait method, one contract test, two implementations — the same shape as every other repository, with the privilege check as the one thing only Postgres can fail.
- **Partitioning `audit_log` with `DROP PARTITION` was considered and rejected**, though it is the faster answer at volume. It needs a DDL privilege at runtime — strictly *more* dangerous than the DELETE this decision avoids granting — it requires rewriting an existing table in a migration, and SQLite has no equivalent, so it would mean maintaining two retention mechanisms to bound one table. Exit condition, recorded rather than forgotten: if a real deployment's audit volume makes the batched delete too slow to converge, partitioning becomes the Postgres-only fast path behind the same trait method.
- **The queue drain's report loses its `purged` fields and the lifecycle job's report gains them.** Any surface that renders the drain's numbers has to follow, which is the visible half of "one job deletes".
- **A streaming export has no body bound**, which is [D38](roadmap.md) exactly: the D13 deadline covers the response head, and the concurrency permit is released on the head. An export is a long response by design, so this decision does not fix D38 — it adds a second, authenticated, step-up gated, rate-limited instance of it, and says so here rather than leaving it to be discovered.
