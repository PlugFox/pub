# Roadmap

State of the project and the plan forward. Written 2026-08-07 against commit `3cbe504` on branch `foundation`, grounded in a full read-only audit of the code (not of the design docs — where the two disagree, the code is what this document reports). **Updated later the same day against `9cc1bef`** after the first execution wave: D4, D5, D6 and D24 closed (marked in place below), decisions 18/24/25 accepted and 02 amended, dependencies swept to latest stable (Rust 1.97.1, reqwest 0.13), the Patina palette with a three-theme registry and the sheen+ripple interaction layer landed, and the agent tooling (`.claude/` skills, commands, hooks) ported from foxic.

**Updated again 2026-08-07 after the second execution wave** (branch `foundation`, commits `409e430`…`6746ae3`): the rest of Phase 1 landed — D7 (operator docs + generated config reference), D8 (strict CSP, transport headers, cache tiers), D13 (deadlines, load shedding, body caps) and D15 (supply-chain CI) — so Phase 1's exit now hangs on the first tag alone. Two owner-decided authorization rules followed: D39 (role-grant ceiling, decision 19 addendum) and D37 (authority changes reach the token plane, decision 13 addendum / S-13.a), closing the break-glass gap. Both waves ended in adversarial reviews that caught real defects the building agents' green tests missed (a 304 clobbering the document CSP, a service worker killed by its own CSP, a token sweep aborting the session revocation it must follow); D32's `revokeInvitation` half closed in passing, and D40 was recorded.

**Updated again 2026-08-08 after the third execution wave** (branch `foundation`, commits `d0100b2`…`48ed1bc`): Phase 2's first wave — both of that phase's Critical debts (D3 non-atomic rate limiting, D2 synchronous fan-out) plus D10, D20 and D31. A durable job queue ([decision 26](decisions.md#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path)) took notification fan-out and outbound mail off the request path, which closed the S-04 SMTP timing oracle as a side effect; every rate-limit window is now spent with one atomic `Kv::incr`; runtime SMTP finally takes effect. The wave's adversarial review was the most productive one yet: **six blocking defects that 72 new green tests did not see**, among them a live sign-in code stored in the clear as a queued mail *subject* (the body was sealed; subjects are not), an unbuildable SMTP section silently discarding every message while the queue reported delivery, and an instance admin able to redirect the operator's SMTP credential onto a plaintext transport by flipping only `security`. Two genuine product forks were left to the owner rather than defaulted by an implementer (D41, D42), and two review findings filed as debt were closed in the same pass instead. The fix pass was then itself reviewed, which was worth it: it caught a regression the *orchestrator* had introduced through an over-specified decision clause — a "belt and braces" rule that was dead code against the attack it named and turned a legal, documented operator configuration into a total mail outage — plus a measured 1000x degradation in the queue's claim statement that the new index test could not see because it asserted an index name rather than the seek's usable columns.

A closing sweep over everything the wave produced — the scouts' maps, the builders' own deviation notes, both review rounds including the *refuted* findings, and the roadmap read back against the code — added **D43–D56** and corrected fifteen statements in this document that the wave had made false. Two of those entries are the honest cost of what shipped: **D43** (critical) is that a dead mail plane is now invisible for roughly twenty-one minutes and has no supported offline recovery, which is the flip side of moving delivery off the request path, and **D44** is that the fan-out's new per-item deadline borrows the SMTP send timeout, a number that means something else. The rest are residue that had been mentioned in passing and never given a number, including three ways the suite's own tests fail to discriminate (**D51**, **D52**, **D55**) — among them the discovery that every wire-level concurrency test in the suite is green *by construction*, because the `:memory:` harness pins a single connection and staggers the burst before the race can happen.

**Updated again 2026-08-14 after the fourth execution wave** (branch `foundation`, Phase 2 wave 2): the limiter gained an identity model and the instance gained an observability plane, closing **D9, D14, D41, D43, D53 and D54** — including the phase's one remaining Critical. Three decisions were recorded before any code ([27](decisions.md#27--rate-limit-identity-what-a-bucket-is-keyed-on-and-what-happens-when-the-kv-is-down), [28](decisions.md#28--the-observability-plane-its-own-listener-bounded-labels-and-timing-that-stays-opt-in), [29](decisions.md#29--a-mail-plane-that-cannot-hide-and-an-offline-way-back-in)), and one of them had to exist *before* the feature it constrains: [S-04.d](security.md#1-authentication) bans `Server-Timing` on the authentication family, and three documents had told an implementer to emit that header without qualifying it. The wave's own review found two defects its first green run did not: without explicit buckets the Prometheus exporter renders distributions as **summaries**, so every `histogram_quantile` in the alert rules this wave shipped would have returned nothing while `# TYPE` disagreed with the catalogue — pinned now by a test that was demonstrated red against the un-bucketed builder; and a `/healthz` probe memo written as a process-global would have let two `TestApp`s in one binary share a health verdict, which is a test passing for the wrong reason on the exact class of thing [D51](#) is about. Two costs are recorded rather than absorbed: **D57** (mutations are still unbucketed — the identity model a write bucket would key on now exists, the policy does not) and **D58** (an authenticated read verifies its JWT twice, taken deliberately over the alternative of keying a bucket on an unverified `sub`).

**Updated again 2026-08-14 after the fifth execution wave** (branch `foundation`, Phase 2 wave 3a): the tables stopped growing forever. **D12** (its data half), **D46**, **D47** and **D48** closed behind [decision 30](decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature), which had to resolve a head-on collision the roadmap had recorded but not answered: S-23 retention needs to delete from `audit_log`, and S-22's documented Postgres hardening forbids the application from doing exactly that. Both survive — the app role still holds no `DELETE` on that table and prunes through a `SECURITY DEFINER` function that refuses any cutoff newer than thirty days, so the reachable capability is "delete audit rows older than a month" rather than "delete audit rows", which is the distinction that matters because evidence of an attack is recent. The owner's constraint shaped the rest: retention had to work automatically on a default install, so it ships **on**, with one window per table and no per-row-state conditions.

**The adversarial pass was the most productive of the five waves so far**: five lenses, each prompted to refute, found **nine defects behind 1 100+ green tests** — and three of them were *comments and documents asserting the opposite of what the code did*. A handler comment claimed a malformed export cursor cost a 400 when the parse happened after `200 OK` had been committed; a migration comment claimed a pinned `search_path` stopped relation shadowing when Postgres searches `pg_temp` first (demonstrated live: a caller's temp table turned the prune into a silent no-op that still reported a row count); a constant's doc claimed a budget bounded cost when it bounded starts. Each read convincingly because it described the intent rather than the behaviour, which is the same failure the wave-3 working agreement already records about guards that cannot catch the attack they name — **now generalised: a comment asserting a property is a claim, and an unasserted claim drifts exactly like an untested one.** Two of the fixes were redesigns rather than patches: `[jobs.lifecycle]` lost its `enabled` key (it also stopped windows configured in `[jobs.queue]`, including the one holding addresses from unauthenticated callers), and the queue's retention now reports three lines instead of one total, because a single figure hid the dead-letter deletion that decision 26 calls "the one deletion here that is never silent". The mutation lens alone found seven undiscriminating assertions — including a batch bound unproven on four of six tables, among them the very table D47 was filed about.

Three things about this wave are worth recording beyond what shipped. **The predicates were made safe by construction rather than by configuration** — a session ages from `last_seen_at` so a purged row could no longer authenticate, and an invitation ages from when it *settled* so a live pending link is undeletable at any window, neither of which depends on the operator choosing a sane number. **D47 was closed structurally**: rather than bounding the drain's unbatched retention statement in place, retention left the five-second tick entirely, so the invariant is now "one job deletes" rather than "two jobs delete carefully". And the wave wrote **the test D46 said nobody would write** — every existing Postgres test connects as the database owner, which can delete from any table, so the debt's own claim was that a retention job quietly needing a widened grant would pass the entire suite; a new test provisions a role from the 0002 template for real and asserts both that a direct delete is refused and that the prune works.

**Updated again 2026-08-15 after the sixth execution wave** (branch `foundation`, Phase 2 wave 5): the last three items of Phase 2 that were not presigned downloads — **D18, D19, D26** and D32's token-base clause — closed behind [decision 33](decisions.md#33--reaching-the-mechanisms-that-already-exist-the-token-model-on-the-wire-an-operator-surface-for-the-supply-chain-registers-and-errors-that-say-what-the-server-said), with [decision 16](decisions.md#16--error-handling) finally accepted. All three were one shape — a mechanism implemented, tested, and reachable from nothing — and two of the three roadmap entries describing them were **wrong**: D26 claimed the supply-chain registers were invisible when the dashboard had rendered both for months (the gap was reach, not visibility), and D19's "unlimited only for read" turned out to be unexpressible rather than unenforced. The wave's own contract suite caught a cross-dialect divergence in its own new code — a malformed cursor timestamp refused on Postgres and silently accepted on SQLite — which is the suite doing precisely the job it exists for. One cost is recorded rather than absorbed: **a shipped wire contract changed meaning** (`expires_days: null` is now "never"), taken deliberately by the owner and made loud by two guards, and one new debt is opened (**D63**, an alarm count computed over a twenty-row sample).

**Updated again 2026-08-16 after the seventh execution wave** (branch `foundation`, Phase 2 wave 6): **Phase 2 is closed.** Its last item was presigned downloads — [D11](#), the `DownloadPlan::Redirect` branch that had been in `core`, in the handler and in [decision 10](decisions.md#10--blob-storage-via-object_store)'s text since the first slice, and that nothing had ever constructed. [Decision 34](decisions.md#34--presigned-downloads-the-redirect-branch-becomes-reachable-off-by-default-and-honest-about-the-address-a-client-can-dial) and [S-18.a](security.md#4-supply-chain--registry-integrity) were recorded first, and the decision **took the opposite default to the one this document had sketched**: not "on by default for s3" but off, because the counter-example was in this repository — `docker/docker-compose.yml` signs against `http://s3:9000`, an address no client outside that network resolves, and once a redirect is sent there is no fallback left. What can be checked is checked instead, as four boot refusals rather than warnings.

Two things about this wave are worth carrying forward. **The external arbiter earned its place again**: against live MinIO, a `GET`-signed URL is answered **403 SignatureDoesNotMatch** to a `HEAD` — and the pub client `HEAD`s an archive before every fetch, so signing one method for both would have broken every cache probe on the S3 backend while every test in this repository stayed green. That is why `BlobStore::download` now takes the request's method. And **a mutation caught a test that was green by construction**, the [D51](#)/[D52](#) class again: the wire assertion that the presigned redirect carries `Cache-Control: no-store` survived a handler that dropped the header, because the S-28 response pass supplies it for the whole pub family. The guarantee moved to a unit test beside `redirect_to` that fails when the line goes, and the wire test now says in its own comment which of the two proves what.

**Updated again 2026-08-16 after the eighth execution wave** (branch `foundation`, Phase 3 wave 7a): the test stand. [Decision 35](decisions.md#35--backend-legs-that-fail-when-the-backend-is-absent-and-a-harness-that-admits-a-race) closes **D16** and **D51**, and it was taken *before* the distributed lock deliberately — Phase 3's claims are all about what two instances do at once, and every one of them will rest on tests that, until this wave, could not fail. Three things came out of it. **A backend leg now fails when nobody has said anything about its backend**, so "the leg did not run" and "the leg passed" stop being one green; the same gate gave `RedisKv` and the S3 `BlobStore` their **first automated execution in the project's history** (both passed, and the S3 leg dials the presigned URL rather than constructing it, which makes wave 6's hand-run MinIO finding repeatable). **The harness gained the database knob D51 asked for, and it found a real defect on its first run**: a lost refresh-rotation race answered `500 database_error` on SQLite, because `rotate` read the row and then wrote it in a deferred transaction — invisible for as long as the harness pinned the pool to one connection. And **D51's own exit turned out to be reachable in one case out of four**: the three KV-budget race tests still pass against a reverted non-atomic limiter even on a real pool, because that window is nanoseconds wide inside the KV, so each now names the test that does discriminate instead of implying it does.

**Updated again 2026-08-16 after the ninth execution wave** (branch `foundation`, Phase 3 wave 7b): **leader election left the process, and the last Critical debt is closed.** [Decision 36](decisions.md#36--leader-election-leaves-the-process-a-lease-table-a-lock-that-outlives-a-pool-connection-and-a-topology-gate-that-replaces-a-kv-check) closes **D1** and **D45**. Four things are worth carrying forward. **The mechanism is not the one this document sketched**: neither a PG advisory lock nor a Redis key, but a lease row, and the reasons are properties of this codebase rather than opinions about the mechanisms — an advisory lock is session-scoped, so a pooled implementation pins one connection per *held* lock, and the publish lock is keyed on the **package**, so held locks scale with simultaneous publishes until a burst deadlocks the instance on its own database handles; a Redis key can vanish to an eviction policy or a failover that never persisted it, and that failure has no signal at all. **The lock is chosen by the database kind, not by `cluster.replicas`** — an operator who scales one container to two without editing the config is the likeliest way this failure actually happens, and a lock chosen from declared topology would be wrong exactly then. **A lease costs what an in-process lock did not**: a lock held at `SIGTERM` is now a row every other replica has to wait out, so the scheduler learned to finish, release and exit, and `pubd` waits for it — the TTL still bounds a crash, which is all a TTL can bound. And **the harness finally has its Postgres variant**, with the drop-on-`Drop` cleanup decision 35 said had to exist first, which is what let this wave's claims be written as two applications over one database rather than as two objects in one process. The wave also **found a defect it did not cause and could not fix inside its own decision**: the shipped S-22 provisioning template grants the app role nothing on any table a later migration adds — verified live, `t` before the grant and `f` after — which every migration since 0004 has been quietly affected by and which `job_locks` would turn into a total outage on a hardened deployment. It was recorded as **D64** and closed by the wave below.

**Updated again 2026-08-16 after the eleventh execution wave** (branch `foundation`, Phase 3 wave 7d): **Phase 3 is closed, and so is Phase 2's exit.** [Decision 38](decisions.md#38--two-replicas-behind-one-proxy-an-acceptance-stand-that-fails-closed-four-claims-proven-at-the-wire-and-a-measurement-that-is-a-number) delivers item 3 — a `cluster` compose profile with two app containers behind nginx, and a `crates/acceptance` suite that asserts the phase's four claims against those containers rather than against two objects in one process. Four things are worth carrying forward. **The stand found something no in-process test could**: restarting one replica onto a different Redis database turned three of five claims red, and the third was unpredicted — a staged upload's session record lives in the KV, so a publish staged on one replica cannot be finalized by another when the KV is not shared. **Two of the five failures on the first run were the harness, not the product**, and both are worth knowing: the SSE audience filter authorizes from `claims.orgs`, a snapshot taken when the access token was minted, so an owner who creates an org must rotate before the stream will carry its events; and a unique-name helper keyed only on the system clock returned identical names inside one tight loop, which the load driver read as a defect in the publish lock until it was investigated. **The measurement says the second replica buys availability, not publish throughput** — at concurrency 12 the proxy and a single replica are within 1.5 %, because the shared Postgres and blob store saturate first — which is the honest answer to the load test Phase 2 owed, and it is recorded in [ops/capacity.md](ops/capacity.md) with the conditions that produced it. And **the acceptance run is deliberately not a CI leg**: it builds an image and boots five containers, so the opt-out is explicit in `server-ci.yml` and deleting that line is how somebody turns it on.

**Updated again 2026-08-16 after the tenth execution wave** (branch `foundation`, Phase 3 wave 7c): **the hardening recipe reaches the tables it always meant to.** [Decision 37](decisions.md#37--a-grant-that-reaches-the-tables-that-do-not-exist-yet-default-privileges-a-one-time-repair-and-an-upgrade-that-says-so) closes **D64**, the defect the previous wave found in a document rather than in code. Three things are worth carrying forward. **The fix is two grants, not one**: `ALTER DEFAULT PRIVILEGES` reaches the tables a future migration adds and cannot repair the ones already added, so the corrected recipe pairs it with a re-run of the original grant — and puts the `audit_log` `REVOKE` last, because the repair re-grants precisely what S-22 takes away. **The correction travels as migration 0017 rather than an edit to 0002**, whose checksum is applied on every deployment in existence; the SQLite set gains a documented no-op so the two sequences stay in lockstep. And **the upgrade now says it out loud**: `pub_role_grant_gaps()` plus a `WARNING` per affected role, which is a report and deliberately not a repair — a false positive in a report costs a sentence, a false positive in a `GRANT` costs a boundary. The test is the part that had been missing since 0004: it provisions a role at migration 0003 and then upgrades, because a role provisioned against the current schema gets every grant and proves nothing, which is exactly why compose, CI and ~1 200 owner-connected tests never saw this.

**Updated again 2026-08-17 after the twelfth execution wave** (branch `foundation`, Phase 4 wave 8): **the account surface, and with it the last requirement that was marked absent and is not v1.1 by design.** [Decision 39](decisions.md#39--the-account-surface-one-me-the-client-can-trust-an-email-change-that-proves-both-addresses-an-export-that-streams-and-a-deletion-that-keeps-the-attribution-and-nothing-else) closes **S-29** and **D40**. Four things are worth carrying forward. **The absence had an unusual shape**: the storage was designed for this and never used — `users.email` was already nullable behind a partial unique index excluding `NULL` on both dialects, and `UserStatus::Deleted` already carried the words "profile erased, row kept as an attribution tombstone" — while the product could reach neither, and there was no `/api/v1/me` at all. **The wave's own review found the sharper half of a rule the wave had already written**: deletion refuses the last Owner of an org by design, and clearing the instance-admin flag (which anonymization must do, or tombstones count as administrators and `claim_first_admin` is blocked forever) meant deleting the *only* administrator left an instance whose admin flag goes to whoever registers next — so the last instance administrator is refused too, and the membership removals inside a deletion became fatal rather than best-effort. **A client-side defect fell out of the server work rather than the other way round**: the auth interceptor refreshed and *replayed* any 401, and because the S-03.a attempt budget is spent atomically before the comparison, every wrong code cost two of five attempts on three flows — TOTP confirm, step-up, and the new email change. And **one index was bought twice over**: `AuditFilter::actor` has been reachable from the admin audit viewer since that surface landed and had never been index-backed, so migration 0018 fixes an existing full scan of the largest table in the instance and makes the export affordable in the same statement. Its Postgres plan test is the honest kind: the first fixture split 20 000 rows evenly between two actors and the planner *correctly* refused the index, so the fixture became the distribution the index exists for.

The original [10-step website roadmap](https://wiki.plugfox.dev/s/website-roadmap) is complete through step 7; this document replaces its remaining steps with a plan shaped by what actually got built.

### The foundation that is genuinely load-bearing

**Pluggable infrastructure behind core traits.** Every backend is compiled in and chosen by config at startup: SQLite or PostgreSQL (separate implementation crates, dialect-idiomatic SQL, per-dialect migrations), filesystem/in-memory/S3 blobs via `object_store`, in-process or Redis KV. The `core` crate holds domain types and 20 traits — the twentieth is `JobQueueRepo`, added by [decision 26](decisions.md#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path) — and depends on no infrastructure; the API layer never sees a sqlx type. This is the single most valuable structural property of the codebase — it is why SQLite-on-a-laptop and Postgres-in-a-cluster are the same binary.

**A contract suite that runs against every backend.** 34 contract functions exercise every repository method — including the ordering-sensitive and concurrency-sensitive ones, and since wave 7b the leader-election lease itself — on SQLite always and on a live Postgres, which since [decision 35](decisions.md#35--backend-legs-that-fail-when-the-backend-is-absent-and-a-harness-that-admits-a-race) **fails** rather than skipping when nobody has said anything about that backend; the one function that asserts a property under concurrency runs on a file-backed pool rather than `:memory:`, because a single connection cannot race. The same shape now covers the other two traits an operator can reconfigure: `Kv` against memory and Redis, `BlobStore` against memory, filesystem and S3. This has already caught real cross-dialect divergence (Postgres returning `203.0.113.9/32` where SQLite returned the address; C-collation being load-bearing for semver sort keys). The queue walk added in the third wave — lease-once, disjoint concurrent claims, lease expiry re-queue, deadletter, dedupe, retention, index coverage — was run against a live Postgres before the wave closed, because it was the one thing the SQLite-only default could not answer.

**One authorization chokepoint.** `authorize(actor, action, resource)` in `core`; cumulative role levels 0/50/100/200/250 with gaps for future roles; visibility policy expressed once as a provided trait method (`resolve`/`resolve_in_base`) rather than duplicated per dialect or per handler.

**Protocol conformance with an external arbiter.** All 12 sharp edges in `docs/protocol.md` are implemented and tested (50 conformance tests in `api/tests/protocol.rs`), and the behaviours that break real clients — 404-not-401 for unreadable names, `WWW-Authenticate` on both 401 and 403, 4xx-never-5xx for permanent failures, byte-stable archives, `archive_url` under our own base, case-insensitive `Bearer` — were each verified against the real Dart client, not only against our own router.

**Supply-chain integrity by construction.** Archives are content-addressed by sha256 and stored byte-identical; upstream bytes are hashed before storage and quarantined on mismatch; a version's bytes can never be overwritten (byte-drift keeps the cached copy and raises an alarm); a locally claimed name structurally cannot fall through to upstream, because upstream is reachable only from the `Unclaimed` arm of resolution. Dependency confusion was demonstrated end to end: a local `path 9.9.9` wins over pub.dev's real `path` with zero upstream traffic.

**Ingest hardening that survived an adversarial pass.** Streaming tar/gzip validation with caps on size, ratio and entry count; rejection of traversal, absolute paths, symlink escapes, duplicate entries, a smuggled second gzip member, and payload appended past the end-of-archive marker; YAML parsed at the event level with aliases rejected (no billion-laughs); markdown rendered and sanitized server-side.

**Authentication built to a written standard.** Email OTP with an atomic per-code attempt budget spent before comparison, Ed25519 JWT with strict `kid` resolution and algorithm pinning, rotating refresh sessions with reuse detection, multi-provider OIDC with PKCE/state/nonce and an offline mock issuer in tests, TOTP with KEK-sealed seeds and argon2id recovery codes, step-up gating on the full S-06 action list, and 21 dedicated attack tests (HS256-forgery with the Ed25519 public key, `alg=none`, parallel OTP guesses, concurrent refresh, spoofed forwarded headers).

**A normative security document wired into the tests.** `docs/security.md` carries S-01…S-33 plus lettered amendments added when reviews discovered something; tests are named after the requirement they prove. The audit verified every test name it cites actually exists.

### Critical — these make a documented deployment shape unsafe or unusable

| # | Item | Why it matters |

Flagged by the review's refuters as a mutation-testing gap and not resurrected; unchanged at HEAD. **Exit:** split line 523 into the property that is actually true — strict growth for every attempt below the cap, exact equality at and above it — and prove it red against `capped = grown.min(backoff_max).min(base * 2)`, the plateau-early mutant that currently passes the entire suite. |
- **D57** ~~**App-API *mutations* are still unbucketed.**~~ **Closed 2026-08-14** ([decision 32](decisions.md#32--quotas-and-limits-what-an-org-may-store-what-a-caller-may-write-and-one-identity-per-request), [S-24.g](security.md#5-audit--abuse)): every app-API mutation spends a bucket keyed on the same three identity classes as the read path — `write_per_ip_minute` 60, `write_per_identity_minute` 300, both runtime-changeable, failing open, mounted **inside** the S-12 guard so a cross-origin mutation the guard refuses spends nothing. The pub plane is excluded (its one write already spends the S-24.c publish budget) and so are the six credential endpoints, which spend their own closed buckets. **Its stated exit was deliberately not met**, and that is recorded rather than glossed: the exit asked for the invitation cap to be expressed *through* the new bucket instead of as a second mechanism, and decision 32 keeps it a database count on purpose — the count is exact, its window genuinely rolls, and it survives a KV outage, three properties a KV bucket does not have on the one mutation whose cost is mail to a third party. What the invitation site did gain is the per-actor cap S-24 always named, runtime numbers, the metric every other throttle emits, an action name of its own, and — after this wave's review refuted the reasoning in its own decision — the per-window audit dedupe every other throttle already had.
- **D58** ~~**An authenticated read verifies its access token twice.**~~ **Closed 2026-08-14** ([decision 32](decisions.md#32--quotas-and-limits-what-an-org-may-store-what-a-caller-may-write-and-one-identity-per-request)), exactly as its exit specified and for the reason the exit predicted: adding a write bucket would have made it *three* verifications on every write. Identity is resolved once per request in one layer, which stashes the **verified** claims in the request extensions; the read bucket, the write bucket and `AuthContext` all read that. What is cached is a signature-verification result and nothing else — revocation, suspension, step-up and scope still run per request, which is the distinction that makes the cache safe. The stash is bound to the **exact** credential string it verified, because the middleware matches the `Bearer` scheme case-insensitively while the extractor requires the literal prefix: an unconditional stash would have quietly made `bearer <jwt>` authenticate on the app API, a widening smuggled in as an optimization. Proven by a counter rather than asserted in a comment — the test fails `left: 2, right: 1` against a reverted extractor.
- **D56** **SQLite never gathers table statistics, and the obvious remedy is itself unmeasured.** `db-sqlite/src/lib.rs:84-97` sets four connection knobs (WAL, `synchronous=NORMAL`, foreign keys, busy timeout) and nothing else; there is no `after_connect` hook and no `ANALYZE` or `PRAGMA optimize` anywhere in `server/crates` — the only `ANALYZE` in the tree is inside a Postgres test. So `sqlite_stat1` never exists on the default deployment backend, and index choice on `package_search` (5 indexes), `job_queue` (5) and `audit_log` (3) is decided by fixed heuristics for the life of the instance. This is *not* the cause of the wave's measured 1000x claim regression — that was the statement, fixed structurally in `48ed1bc`, with `ANALYZE` (which would have let SQLite recover the plan by skip-scan) the rejected alternative. The debt is the untested asymmetry it leaves behind: measured on a migrated database with 50 000 `package_search` rows, three of the four browse shapes plan identically with and without statistics, but the fourth (`format` filter + `ORDER BY name`) *degrades* under `ANALYZE` — the planner abandons `package_search_name_idx` for a full temp B-tree over 45 000 rows, ~20x slower on the `LIMIT 21` page. Adding `PRAGMA optimize` on SQLite's documented schedule is therefore a change that can silently regress the package browse, and nothing would catch it: the only SQLite plan test runs against an empty `:memory:` database and covers five queue statements. Exit: decide the question with numbers rather than folklore — extend the plan test to load a realistic `package_search` backlog and assert the browse seeks, then either adopt `PRAGMA optimize` (with the plan tests running against a database that has statistics, so tests and production agree) or record in [rules/migrations.md](rules/migrations.md) that pub deliberately runs stats-free and that every index is chosen to be selective without them.

- **D59** **The storage quota is a control an operator can set and cannot observe.** `PackageRepo::org_storage_bytes` is contract-tested on both dialects and index-backed by `versions_org_bytes_idx` (migration 0014), and its only callers are the three enforcement points. `GET /api/v1/admin/orgs` reports the stored override and the effective limit but **not the bytes it is measured against**, so the admin who sets a quota cannot see how close any org is to it, and the 80 % crossing does not close the gap: `DomainEvent::OrgStorageQuotaWarning` is org-audience and `NotificationCategory::Org`, so it reaches the org's own members and never an instance admin, it writes no audit row, and it has no instrument — which is why [ops/monitoring.md](ops/monitoring.md) can alert on `storage_quota_refusals_total` (the wall) and on nothing that precedes it. The number is also unobservable in the direction that matters on upgrade: an operator turning the quota on for the first time cannot tell which orgs are already past it. **Exit:** the admin org listing carries the org's live byte total, with the cost of the aggregate over a full page measured and either batched into one statement or moved to a per-org read; and either the crossing gains an instrument the monitoring page can alert on, or that page states that the wall is the only operator-visible signal and why.
- **D60** **`registry.storage_quota_bytes` has no bound but its type.** The per-org override is validated on both edges — a negative is refused by `AdminService::set_org_storage_quota` and anything above `i64::MAX` dies in the deserializer — because `effective_storage_quota` reads either as *unlimited*, which hands an operator the opposite of the wall they asked for. The instance default sits outside `validate_registry`'s zero-rejecting rule (`0` is its shipped value and means unlimited) and outside every other rule, so the admin surface accepts a one-byte instance quota that refuses every publish on every org following the default. It fails loudly and one more PATCH undoes it, which is why this is debt and not a defect — and why the answer is probably not a floor, since no floor is less arbitrary than another. **Exit:** the admin surface shows the largest org's current usage beside the field so the number is typed against a fact ([D59](#)), or the setting grows a confirmation for a value below the instance's current maximum org usage. A bare minimum constant is explicitly **not** the exit.
- **D61** **`latest` can name a retracted version when the whole window is retracted.** The `latest` rule is evaluated over the newest `LATEST_WINDOW` (1 000) live versions ([decision 32](decisions.md#32--quotas-and-limits-what-an-org-may-store-what-a-caller-may-write-and-one-identity-per-request)); when every version in that window is retracted the rule reaches its last clause and answers the newest version, which is retracted, while an older live stable sits below the window and is still listed. [Sharp edge 9](protocol.md#sharp-edges-violate--break-clients) makes `retracted: true` mean "excluded from new resolution", so the listing recommends as `latest` a version the same document forbids resolving, and the search document takes its description and README from it. `dart pub` does not break — the client resolves out of `versions` and ignores `latest` — but the package page, the search index and the `pub add` snippet all follow it. This is a **regression on two of the three surfaces**: before the window the protocol listing and the indexer scanned unbounded and reached the older live stable; the package page already behaved this way. Decision 32's consequences record only the pre-release shape and are silent on this one. Reachable by a mass retraction of a nightly-publishing package, which is what a leaked credential forces. **Exit:** a window exhausted with no live candidate is resolved rather than guessed — one additional bounded read for the newest non-retracted live version, or an explicit "unknown" that the surfaces render as such — and a wire test builds a fully-retracted window over a live stable and asserts what all three answer.
- **D62** **The `latest` window truncation is not reported by the surface that served it.** `LatestScan::window_exhausted` is public and has one caller: the shared scan behind the package page and the indexer. `build_listing` and `build_proxied_listing` throw the scan away without asking, so the pub-protocol listing — the surface `dart pub` actually reads, and the one that served the answer — says nothing, while `MAX_LISTED_VERSIONS`'s own 10 000-version truncation on the same handler does warn. An operator asking why the registry advertises a nightly as `latest` gets a signal from the page and the indexer and none from the endpoint. **Half of this entry was closed on the day it was written**: the shared scan used to emit a `tracing::warn!`, and because it runs on the *anonymous* package page — bounded only by `read_per_ip_minute`, 600 — a bare read loop wrote 600 lines a minute per address into the one sink an operator cannot rotate away from mid-incident. That is the amplification `first_in_window` exists to stop for `audit_log`, one sink over, on the route whose own comment names "anonymous-reachable in a loop" as the reason the scan is bounded at all. It is now the catalogued counter `latest_window_exhausted_total` plus a `debug!`: same information, once per occurrence, bounded by construction, and alertable. **Exit:** the protocol listing reports its own truncation — the counter is emitted from the listing path too, or the handler consults `window_exhausted` — so the surface that gave the answer is the one that says the answer was windowed.

- **D63** **The dashboard's "active alarms" number is a count over a twenty-row sample.** `AdminService::stats` reads `REGISTER_SAMPLE` (20) rows of `shadowing_alarms` and counts the active ones *in that page* (`admin/src/instance.rs`), so `shadowing_active` saturates at 20 — an instance with 200 open alarms and an instance with 20 render the same figure on the one screen an operator watches. Pre-existing (it dates from the admin surface) and out of the wave that found it, but now adjacent: the register listing beside it can page the whole table, which makes the stat the one number on the panel that cannot be trusted. The sample itself is fine — it is the alarm, and the register behind it is the investigation — the defect is calling a page count a total. **Exit:** a real count, either an `UpstreamRepo::count_shadowing(active)` contract-tested on both dialects and index-backed by `shadowing_alarms_active_idx`, or the figure rendered as "20+" when the sample is full and the panel saying which it is. A count query per dashboard load is affordable; a wrong number on an alarm panel is not.

- **D64** ~~**The shipped Postgres hardening template grants the app role nothing on any table added after it was run.**~~ **Closed 2026-08-16** ([decision 37](decisions.md#37--a-grant-that-reaches-the-tables-that-do-not-exist-yet-default-privileges-a-one-time-repair-and-an-upgrade-that-says-so), wave 7c): the recipe now grants twice — once for what exists, once for what will. Migration **0017** carries the corrected template (`ALTER DEFAULT PRIVILEGES FOR ROLE <migration_role> IN SCHEMA public GRANT … ON TABLES TO pub_app`, keyed on the role that *creates* the object rather than the one being granted to) without editing 0002, whose checksum is applied everywhere; the one-time re-grant an already-provisioned deployment needs is in [ops/upgrade.md](ops/upgrade.md), the whole recipe is in [ops/install.md](ops/install.md#hardening-the-postgres-role-optional), and the `REVOKE` on `audit_log` is documented **last** because the re-grant hands back exactly what it takes away. Deliberately not extended to `ON FUNCTIONS`: [decision 30](decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature) made a `SECURITY DEFINER` function a capability granted one at a time, and a blanket default privilege would have re-made that trade by accident. 0017 also adds `pub_role_grant_gaps()` and raises a `WARNING` naming every role left behind — **reporting, not repairing**, because inferring which role is meant to be the application from the privileges it holds is a guess, and a wrong guess widens somebody's access unasked. The test provisions a role at migration **0003** and *then* upgrades, which is the only vantage point this is visible from; it asserts the refusal through `locks.try_acquire`, that the gap list is exactly the set of tables the upgrade added, and that `audit_log` is still append-only after the repair. Seen red three ways: without the default privileges the later table is refused, without the re-grant `job_locks` is refused, and with the `REVOKE` moved first the `audit_log` delete succeeds. One correction to the original text below: 0014 and 0015 add columns and indexes, **not** tables — the affected set is the fifteen tables from 0004 to 0016, read from the schema. Original text follows. **The shipped Postgres hardening template grants the app role nothing on any table added after it was run — demonstrated live, and `job_locks` makes the consequence total.** `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO pub_app` (the provisioning template in `db-postgres/migrations/0002_identity.sql:163`, asserted as the hardening recipe by [S-22](security.md#5-audit--abuse), architecture.md and [rules/migrations.md](rules/migrations.md)) is a **one-time** grant over the tables that exist when it runs; Postgres carries no default privileges for future objects unless `ALTER DEFAULT PRIVILEGES` says so, and the template does not. Verified against Postgres 17 on 2026-08-16 rather than reasoned about: with a role provisioned exactly per the template, `has_table_privilege` answers `t` for a table created *before* the grant and `f` for one created *after*. Everything migrations 0004–0016 added is therefore unreachable to an app role provisioned once and upgraded since — `job_queue` (mail and fan-out), `notifications`, the quota tables, `register_pages`, and now `job_locks`. The last one is the worst of them: the lock is acquired on **every publish** and **every job tick**, so a hardened deployment that upgrades into this wave loses publishing and all background work at once, with a `permission denied for table job_locks` in the log. Nothing in this repository would notice — `pub_app` exists nowhere but that comment, and compose, CI and every test connect as the database **owner**, which is precisely the blind spot [D46](#) named and closed for one table without noticing it generalised. **Exit:** a decision records the corrected recipe (`ALTER DEFAULT PRIVILEGES FOR ROLE <migration-owner> IN SCHEMA public GRANT … TO pub_app`, plus the re-grant an already-provisioned deployment has to run once), the template text reaches operators through a **new** migration rather than an edit to 0002 (whose checksum is applied everywhere), [ops/upgrade.md](ops/upgrade.md) tells an upgrading operator what to run, and the S-22.a test that already provisions a role from the template is extended to create a table *after* provisioning and assert the app role can use it — running as the owner proves nothing, which is the same sentence D46 was closed with.

## Working agreements for the phases ahead

- **The decision log stays normative.** Anything in this roadmap that changes a decision gets recorded there first; decisions 16 (proposed) and 18 (tbd) are resolved in Phase 1.
- **The review's own fixes get reviewed.** Added 2026-08-08, because the third wave's fix pass introduced a *worse* defect than one it closed: a "belt and braces" credential guard that could never fire on the attack it named, and that turned a legal, documented operator configuration into an instance-wide mail outage. It came from an over-specified clause the **orchestrator** wrote into the decision log, so no implementer was in a position to question it, and the fix pass's own green tests could not see it — the integration harness had no option to boot the configuration it broke. Two lenses found it independently on re-entry. A fix touching auth, credentials or a delivery path is a change like any other and gets the same gate.
- **A decision clause that adds a guard must name what the guard catches that nothing else does.** The same failure again, stated as a rule: "belt and braces" is not a justification. If the primary mechanism already refuses the attack, a second guard only has reachable behaviour on inputs the primary mechanism *allows* — which is, by construction, the legitimate ones.
- **A comment is an unasserted claim, and it drifts exactly like an untested one.** Added 2026-08-14, after wave 3a's review found three: a handler comment claiming a malformed cursor cost a 400 when the parse ran after the response head was committed, a migration comment claiming a pinned `search_path` stopped relation shadowing when Postgres searches `pg_temp` first, and a constant's doc claiming a budget bounded cost when it bounded starts. All three were written by the implementer, all three described the *intent*, and all three read convincingly because of it. When a comment states a property — "this cannot happen", "this is checked first", "this bounds X" — either a test asserts it or the comment says what the code does instead of what it was for.
- **An index test that asserts a name proves nothing.** Assert the seek's usable columns for the exact statement production emits, or a plan test passes while the statement scans. The wave shipped a claim that left `priority` unconstrained (`ORDER BY priority, id` across both lanes), so the seek into `job_queue_claim_prio_idx (kind, priority, run_after, id)` stopped at the `kind` prefix and `run_after <= ?` degraded to a post-filter: 6.59 ms against 0.006 ms per lane on a 200k-row backed-off backlog, inside a write statement that runs up to 64 times a tick, with the name-asserting test green throughout. **The index was correct** — the fix was per-lane claiming (`priority = ?` over `NewQueuedJob::LEVELS` in order, `(run_after, id)` inside a lane), not a migration; migration 0011 is unchanged in both dialects. The durable rule: a multi-lane index is only seekable if the statement constrains the lane, so the query and the index are designed as one unit, and the plan test asserts the seek's usable columns (see also D56 — the plan tests currently EXPLAIN hand-copied SQL rather than the repositories' own).
- **Every phase ends with an adversarial review**, not only tests — the reviews in Phases 1–4 of the build so far found the archive-smuggling hole, the non-atomic OTP budget, the trusted `X-Forwarded-For`, the cross-org version oracle and the browser-only `Content-Type` defect, none of which the building agent's own tests caught.
- **External arbiters over self-reports**: the real `dart pub` client, the real pub.dev, a real browser, a real Postgres. Every claim in this document that says "verified" means one of those was involved.
- **Debt is written down where it lives.** A deviation with a documented reason and an exit condition is acceptable; an undocumented one is a defect.
- **Decisions before code, always.** Anything that changes normative behaviour is recorded in `docs/decisions.md` (and the relevant `S-xx`) *before* implementation — this is what keeps parallel agents from inventing policy and drifting. Genuinely open product forks go to the owner, not to a default.
- **Cadence that has worked twice now:** scout read-only (Explore agents map the exact code before any edit) → record the decision → fan out implementation across non-overlapping file ownership → adversarial review (independent verifiers prompted to *refute*, each finding re-verified) → fix the confirmed → validate on the final state → bookkeeping → commit. The review is a hard gate, not an optional pass: green tests from the building agent are necessary, never sufficient.
- **Model and effort are calibrated to the stakes, not applied uniformly.** Orchestration (this loop) and anything touching auth, the pub protocol, concurrency, distributed locking, or byte-stability run on the strongest available model at `xhigh`+ with a mandatory adversarial pass — these are the "cannot repair after the fact" properties. Ordinary feature work behind the existing traits runs a tier down at `high`; mechanical work (dependency bumps, doc/codegen regeneration, formatting, metrics wiring) runs cheaper at `low`–`medium`. In a workflow this is set per stage (`agent(..., {model, effort})`): cheap finders and mechanical stages low, `verify`/`judge` stages and auth-lens reviewers at the top tier. Reach for a workflow on find→verify and multi-file fan-out; stay solo on conversational and trivially-mechanical turns.
