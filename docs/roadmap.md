# Roadmap

State of the project and the plan forward. Written 2026-08-07 against commit `3cbe504` on branch `foundation`, grounded in a full read-only audit of the code (not of the design docs — where the two disagree, the code is what this document reports). **Updated later the same day against `9cc1bef`** after the first execution wave: D4, D5, D6 and D24 closed (marked in place below), decisions 18/24/25 accepted and 02 amended, dependencies swept to latest stable (Rust 1.97.1, reqwest 0.13), the Patina palette with a three-theme registry and the sheen+ripple interaction layer landed, and the agent tooling (`.claude/` skills, commands, hooks) ported from foxic.

**Updated again 2026-08-07 after the second execution wave** (branch `foundation`, commits `409e430`…`6746ae3`): the rest of Phase 1 landed — D7 (operator docs + generated config reference), D8 (strict CSP, transport headers, cache tiers), D13 (deadlines, load shedding, body caps) and D15 (supply-chain CI) — so Phase 1's exit now hangs on the first tag alone. Two owner-decided authorization rules followed: D39 (role-grant ceiling, decision 19 addendum) and D37 (authority changes reach the token plane, decision 13 addendum / S-13.a), closing the break-glass gap. Both waves ended in adversarial reviews that caught real defects the building agents' green tests missed (a 304 clobbering the document CSP, a service worker killed by its own CSP, a token sweep aborting the session revocation it must follow); D32's `revokeInvitation` half closed in passing, and D40 was recorded.

**Updated again 2026-08-08 after the third execution wave** (branch `foundation`, commits `d0100b2`…`48ed1bc`): Phase 2's first wave — both of that phase's Critical debts (D3 non-atomic rate limiting, D2 synchronous fan-out) plus D10, D20 and D31. A durable job queue ([decision 26](decisions.md#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path)) took notification fan-out and outbound mail off the request path, which closed the S-04 SMTP timing oracle as a side effect; every rate-limit window is now spent with one atomic `Kv::incr`; runtime SMTP finally takes effect. The wave's adversarial review was the most productive one yet: **six blocking defects that 72 new green tests did not see**, among them a live sign-in code stored in the clear as a queued mail *subject* (the body was sealed; subjects are not), an unbuildable SMTP section silently discarding every message while the queue reported delivery, and an instance admin able to redirect the operator's SMTP credential onto a plaintext transport by flipping only `security`. Two genuine product forks were left to the owner rather than defaulted by an implementer (D41, D42), and two review findings filed as debt were closed in the same pass instead. The fix pass was then itself reviewed, which was worth it: it caught a regression the *orchestrator* had introduced through an over-specified decision clause — a "belt and braces" rule that was dead code against the attack it named and turned a legal, documented operator configuration into a total mail outage — plus a measured 1000x degradation in the queue's claim statement that the new index test could not see because it asserted an index name rather than the seek's usable columns.

A closing sweep over everything the wave produced — the scouts' maps, the builders' own deviation notes, both review rounds including the *refuted* findings, and the roadmap read back against the code — added **D43–D56** and corrected fifteen statements in this document that the wave had made false. Two of those entries are the honest cost of what shipped: **D43** (critical) is that a dead mail plane is now invisible for roughly twenty-one minutes and has no supported offline recovery, which is the flip side of moving delivery off the request path, and **D44** is that the fan-out's new per-item deadline borrows the SMTP send timeout, a number that means something else. The rest are residue that had been mentioned in passing and never given a number, including three ways the suite's own tests fail to discriminate (**D51**, **D52**, **D55**) — among them the discovery that every wire-level concurrency test in the suite is green *by construction*, because the `:memory:` harness pins a single connection and staggers the burst before the race can happen.

**Updated again 2026-08-14 after the fourth execution wave** (branch `foundation`, Phase 2 wave 2): the limiter gained an identity model and the instance gained an observability plane, closing **D9, D14, D41, D43, D53 and D54** — including the phase's one remaining Critical. Three decisions were recorded before any code ([27](decisions.md#27--rate-limit-identity-what-a-bucket-is-keyed-on-and-what-happens-when-the-kv-is-down), [28](decisions.md#28--the-observability-plane-its-own-listener-bounded-labels-and-timing-that-stays-opt-in), [29](decisions.md#29--a-mail-plane-that-cannot-hide-and-an-offline-way-back-in)), and one of them had to exist *before* the feature it constrains: [S-04.d](security.md#1-authentication) bans `Server-Timing` on the authentication family, and three documents had told an implementer to emit that header without qualifying it. The wave's own review found two defects its first green run did not: without explicit buckets the Prometheus exporter renders distributions as **summaries**, so every `histogram_quantile` in the alert rules this wave shipped would have returned nothing while `# TYPE` disagreed with the catalogue — pinned now by a test that was demonstrated red against the un-bucketed builder; and a `/healthz` probe memo written as a process-global would have let two `TestApp`s in one binary share a health verdict, which is a test passing for the wrong reason on the exact class of thing [D51](#) is about. Two costs are recorded rather than absorbed: **D57** (mutations are still unbucketed — the identity model a write bucket would key on now exists, the policy does not) and **D58** (an authenticated read verifies its JWT twice, taken deliberately over the alternative of keying a bucket on an unverified `sub`).

**Updated again 2026-08-14 after the fifth execution wave** (branch `foundation`, Phase 2 wave 3a): the tables stopped growing forever. **D12** (its data half), **D46**, **D47** and **D48** closed behind [decision 30](decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature), which had to resolve a head-on collision the roadmap had recorded but not answered: S-23 retention needs to delete from `audit_log`, and S-22's documented Postgres hardening forbids the application from doing exactly that. Both survive — the app role still holds no `DELETE` on that table and prunes through a `SECURITY DEFINER` function that refuses any cutoff newer than thirty days, so the reachable capability is "delete audit rows older than a month" rather than "delete audit rows", which is the distinction that matters because evidence of an attack is recent. The owner's constraint shaped the rest: retention had to work automatically on a default install, so it ships **on**, with one window per table and no per-row-state conditions.

**The adversarial pass was the most productive of the five waves so far**: five lenses, each prompted to refute, found **nine defects behind 1 100+ green tests** — and three of them were *comments and documents asserting the opposite of what the code did*. A handler comment claimed a malformed export cursor cost a 400 when the parse happened after `200 OK` had been committed; a migration comment claimed a pinned `search_path` stopped relation shadowing when Postgres searches `pg_temp` first (demonstrated live: a caller's temp table turned the prune into a silent no-op that still reported a row count); a constant's doc claimed a budget bounded cost when it bounded starts. Each read convincingly because it described the intent rather than the behaviour, which is the same failure the wave-3 working agreement already records about guards that cannot catch the attack they name — **now generalised: a comment asserting a property is a claim, and an unasserted claim drifts exactly like an untested one.** Two of the fixes were redesigns rather than patches: `[jobs.lifecycle]` lost its `enabled` key (it also stopped windows configured in `[jobs.queue]`, including the one holding addresses from unauthenticated callers), and the queue's retention now reports three lines instead of one total, because a single figure hid the dead-letter deletion that decision 26 calls "the one deletion here that is never silent". The mutation lens alone found seven undiscriminating assertions — including a batch bound unproven on four of six tables, among them the very table D47 was filed about.

Three things about this wave are worth recording beyond what shipped. **The predicates were made safe by construction rather than by configuration** — a session ages from `last_seen_at` so a purged row could no longer authenticate, and an invitation ages from when it *settled* so a live pending link is undeletable at any window, neither of which depends on the operator choosing a sane number. **D47 was closed structurally**: rather than bounding the drain's unbatched retention statement in place, retention left the five-second tick entirely, so the invariant is now "one job deletes" rather than "two jobs delete carefully". And the wave wrote **the test D46 said nobody would write** — every existing Postgres test connects as the database owner, which can delete from any table, so the debt's own claim was that a retention job quietly needing a widened grant would pass the entire suite; a new test provisions a role from the 0002 template for real and asserts both that a direct delete is refused and that the prune works.

The original [10-step website roadmap](https://wiki.plugfox.dev/s/website-roadmap) is complete through step 7; this document replaces its remaining steps with a plan shaped by what actually got built.

### The foundation that is genuinely load-bearing

**Pluggable infrastructure behind core traits.** Every backend is compiled in and chosen by config at startup: SQLite or PostgreSQL (separate implementation crates, dialect-idiomatic SQL, per-dialect migrations), filesystem/in-memory/S3 blobs via `object_store`, in-process or Redis KV. The `core` crate holds domain types and 20 traits — the twentieth is `JobQueueRepo`, added by [decision 26](decisions.md#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path) — and depends on no infrastructure; the API layer never sees a sqlx type. This is the single most valuable structural property of the codebase — it is why SQLite-on-a-laptop and Postgres-in-a-cluster are the same binary.

**A contract suite that runs against both databases.** 27 contract functions exercise every repository method — including the ordering-sensitive and concurrency-sensitive ones — on SQLite `:memory:` always and on a live Postgres when `PUB_TEST_POSTGRES_URL` is set. This has already caught real cross-dialect divergence (Postgres returning `203.0.113.9/32` where SQLite returned the address; C-collation being load-bearing for semver sort keys). The queue walk added in the third wave — lease-once, disjoint concurrent claims, lease expiry re-queue, deadletter, dedupe, retention, index coverage — was run against a live Postgres before the wave closed, because it was the one thing the SQLite-only default could not answer.

**One authorization chokepoint.** `authorize(actor, action, resource)` in `core`; cumulative role levels 0/50/100/200/250 with gaps for future roles; visibility policy expressed once as a provided trait method (`resolve`/`resolve_in_base`) rather than duplicated per dialect or per handler.

**Protocol conformance with an external arbiter.** All 12 sharp edges in `docs/protocol.md` are implemented and tested (50 conformance tests in `api/tests/protocol.rs`), and the behaviours that break real clients — 404-not-401 for unreadable names, `WWW-Authenticate` on both 401 and 403, 4xx-never-5xx for permanent failures, byte-stable archives, `archive_url` under our own base, case-insensitive `Bearer` — were each verified against the real Dart client, not only against our own router.

**Supply-chain integrity by construction.** Archives are content-addressed by sha256 and stored byte-identical; upstream bytes are hashed before storage and quarantined on mismatch; a version's bytes can never be overwritten (byte-drift keeps the cached copy and raises an alarm); a locally claimed name structurally cannot fall through to upstream, because upstream is reachable only from the `Unclaimed` arm of resolution. Dependency confusion was demonstrated end to end: a local `path 9.9.9` wins over pub.dev's real `path` with zero upstream traffic.

**Ingest hardening that survived an adversarial pass.** Streaming tar/gzip validation with caps on size, ratio and entry count; rejection of traversal, absolute paths, symlink escapes, duplicate entries, a smuggled second gzip member, and payload appended past the end-of-archive marker; YAML parsed at the event level with aliases rejected (no billion-laughs); markdown rendered and sanitized server-side.

**Authentication built to a written standard.** Email OTP with an atomic per-code attempt budget spent before comparison, Ed25519 JWT with strict `kid` resolution and algorithm pinning, rotating refresh sessions with reuse detection, multi-provider OIDC with PKCE/state/nonce and an offline mock issuer in tests, TOTP with KEK-sealed seeds and argon2id recovery codes, step-up gating on the full S-06 action list, and 21 dedicated attack tests (HS256-forgery with the Ed25519 public key, `alg=none`, parallel OTP guesses, concurrent refresh, spoofed forwarded headers).

**A normative security document wired into the tests.** `docs/security.md` carries S-01…S-33 plus lettered amendments added when reviews discovered something; tests are named after the requirement they prove. The audit verified every test name it cites actually exists.

### What is configured and ready to build on

- **Types**: the frontend generates its API types from the server's OpenAPI document (`bun run gen:api`); a server-side test asserts the document matches the route inventory exactly.

- **D40** No dedicated **leave-organization** affordance for Read/Write members: they never reach the `ManageMembers` surface, so below Admin there is no way to leave an org from the API (an Admin+ can now self-remove per the D39 self-reduction carve-out). Recorded when the ceiling landed; the sanctioned member-facing leave route lands with the account surface (S-29, Phase 4).
- **D41** ~~**S-24's in-process fallback limiter does not exist.**~~ **Closed 2026-08-14** ([S-24.e](security.md#5-audit--abuse) rewritten, decision 27): a KV outage no longer answers 503 and takes sign-in down instance-wide. The fallback is a fixed table of atomic slots — bounded by construction, because bucket keys carry attacker-supplied addresses and a map would turn an outage into a memory-exhaustion primitive — and slot collisions merge budgets, which can only refuse more. The accepted cost is written into the requirement rather than discovered later: N replicas count separately, so an outage lifts the aggregate budget to N × the limit.
- **D42** **The 200-recipient notification cap has outlived its justification.** [Decision 20](decisions.md#20--realtime-sse-event-stream--notification-center) justified `realtime.max_notification_recipients` by the cost *on the publish path*; with fan-out moved to the queue that argument is gone, and the cap is now a silent correctness loss — members 201..N of a large org never learn about a publish, a membership change or a shadowing alarm. Left at 200 deliberately (raising or removing it is a product decision about who gets notified, not a consequence of relocating the work). Moving the number is coupled to the 500-recipient batch clamp in both dialects' preference lookup and the validator's ≤500 rule.
| D55 | **The backoff-ladder test's monotonicity assertion is a tautology, and the ladder can be flattened after attempt 2 with the whole suite green.** `assert!(delay > previous || delay == policy.backoff_for(&item), "attempt {attempts} must not shrink")` (`jobs/src/queue.rs:523`) compares `delay` against a second call to the same deterministic function on the same shadowed item — `backoff_for`'s ±25% jitter is `id.as_bytes()[15] % (spread*2+1)`, not an RNG — so the right-hand disjunct is `delay == delay` and the assertion can never fail for any implementation, including one that returns a constant or shrinks. The disjunct was needed because the true property is non-decreasing rather than strictly increasing (at the test's base/cap the ladder plateaus at attempts 7 and 8). Narrower than first reported: `jobs/tests/queue.rs:373-374` does catch a flat ladder end to end, and the sibling `a_first_attempt_waits_the_base_delay_not_double_it` catches an attempts off-by-one. What nothing catches is a ladder that stops growing after attempt 2 — mutating `capped` to `grown.min(backoff_max).min(base * 2)` yields 10 s, 20 s, 20 s, … forever and leaves `cargo test -p pub-jobs` green with 0 failures. That is exactly the collapsed-ladder retry storm MF4 was filed to prevent, invisible behind a fully green pipeline and a test name a reviewer trusts. Flagged by the review's refuters as a mutation-testing gap and not resurrected; unchanged at HEAD. **Exit:** split line 523 into the property that is actually true — strict growth for every attempt below the cap, exact equality at and above it — and prove it red against `capped = grown.min(backoff_max).min(base * 2)`, the plateau-early mutant that currently passes the entire suite. |
- **D57** **App-API *mutations* are still unbucketed.** The read path is now limited on both planes ([S-24.f](security.md#5-audit--abuse)) and the six credential endpoints have always been, but everything else that writes — `POST /api/v1/orgs`, membership and invitation mutations, `PATCH /api/v1/admin/settings`, notification mark-read, token minting — passes through with no bucket at all; the only bound is the D8 concurrency shed, which is a ceiling on *concurrency*, not on rate. An authenticated account can therefore issue writes as fast as the instance answers. Two of these already have normative numbers nobody implemented: S-24's "invitations ≤20/day/org with per-actor caps" (also named in Phase 2 item 7) and the per-org storage quota of [S-20](security.md#4-supply-chain--registry-integrity)/[D21](#). The wave that added the read buckets deliberately did not widen to writes — the identity model it introduces is what a write bucket would key on, so the mechanism is now in place and the policy is not. **Exit:** a mutation bucket keyed on the same [`ReadIdentity`](#) classes, with the invitation cap expressed through it rather than as a second mechanism, and a decision recording which mutations fail open and which fail closed.
- **D58** **An authenticated read verifies its access token twice.** `guard::read_identity` verifies the JWT to derive `usr:{sub}` for the bucket, and `AuthContext::from_request_parts` verifies the same token again a few layers later. Verification is local Ed25519 with no I/O — tens of microseconds against a read that issues 5–7 queries — so this is a cost, not a defect, and it was taken deliberately: the alternative on the table was keying the bucket on an *unverified* `sub`, which would let anyone drain a chosen victim's read budget. **Exit:** the guard stashes the verified `Claims` in the request extensions and the extractor reuses them when present. Deliberately not done in the wave that introduced it: the change touches the auth extractor, which is a "cannot repair after the fact" surface, and it belongs in a pass that can give it the same review weight as the limiter itself rather than riding along as an optimization.
- **D56** **SQLite never gathers table statistics, and the obvious remedy is itself unmeasured.** `db-sqlite/src/lib.rs:84-97` sets four connection knobs (WAL, `synchronous=NORMAL`, foreign keys, busy timeout) and nothing else; there is no `after_connect` hook and no `ANALYZE` or `PRAGMA optimize` anywhere in `server/crates` — the only `ANALYZE` in the tree is inside a Postgres test. So `sqlite_stat1` never exists on the default deployment backend, and index choice on `package_search` (5 indexes), `job_queue` (5) and `audit_log` (3) is decided by fixed heuristics for the life of the instance. This is *not* the cause of the wave's measured 1000x claim regression — that was the statement, fixed structurally in `48ed1bc`, with `ANALYZE` (which would have let SQLite recover the plan by skip-scan) the rejected alternative. The debt is the untested asymmetry it leaves behind: measured on a migrated database with 50 000 `package_search` rows, three of the four browse shapes plan identically with and without statistics, but the fourth (`format` filter + `ORDER BY name`) *degrades* under `ANALYZE` — the planner abandons `package_search_name_idx` for a full temp B-tree over 45 000 rows, ~20x slower on the `LIMIT 21` page. Adding `PRAGMA optimize` on SQLite's documented schedule is therefore a change that can silently regress the package browse, and nothing would catch it: the only SQLite plan test runs against an empty `:memory:` database and covers five queue statements. Exit: decide the question with numbers rather than folklore — extend the plan test to load a realistic `package_search` backlog and assert the browse seeks, then either adopt `PRAGMA optimize` (with the plan tests running against a database that has statistics, so tests and production agree) or record in [rules/migrations.md](rules/migrations.md) that pub deliberately runs stats-free and that every index is chosen to be selective without them.

## Working agreements for the phases ahead

- **The decision log stays normative.** Anything in this roadmap that changes a decision gets recorded there first; decisions 16 (proposed) and 18 (tbd) are resolved in Phase 1.
- **The review's own fixes get reviewed.** Added 2026-08-08, because the third wave's fix pass introduced a *worse* defect than one it closed: a "belt and braces" credential guard that could never fire on the attack it named, and that turned a legal, documented operator configuration into an instance-wide mail outage. It came from an over-specified clause the **orchestrator** wrote into the decision log, so no implementer was in a position to question it, and the fix pass's own green tests could not see it — the integration harness had no option to boot the configuration it broke. Two lenses found it independently on re-entry. A fix touching auth, credentials or a delivery path is a change like any other and gets the same gate.
- **A decision clause that adds a guard must name what the guard catches that nothing else does.** The same failure again, stated as a rule: "belt and braces" is not a justification. If the primary mechanism already refuses the attack, a second guard only has reachable behaviour on inputs the primary mechanism *allows* — which is, by construction, the legitimate ones.
- **A comment is an unasserted claim, and it drifts exactly like an untested one.** Added 2026-08-14, after wave 3a's review found three: a handler comment claiming a malformed cursor cost a 400 when the parse ran after the response head was committed, a migration comment claiming a pinned `search_path` stopped relation shadowing when Postgres searches `pg_temp` first, and a constant's doc claiming a budget bounded cost when it bounded starts. All three were written by the implementer, all three described the *intent*, and all three read convincingly because of it. When a comment states a property — "this cannot happen", "this is checked first", "this bounds X" — either a test asserts it or the comment says what the code does instead of what it was for.
- **An index test that asserts a name proves nothing.** Assert the seek's usable columns for the exact statement production emits, or a plan test passes while the statement scans. The wave shipped a claim that left `priority` unconstrained (`ORDER BY priority, id` across both lanes), so the seek into `job_queue_claim_prio_idx (kind, priority, run_after, id)` stopped at the `kind` prefix and `run_after <= ?` degraded to a post-filter: 6.59 ms against 0.006 ms per lane on a 200k-row backed-off backlog, inside a write statement that runs up to 64 times a tick, with the name-asserting test green throughout. **The index was correct** — the fix was per-lane claiming (`priority = ?` over `NewQueuedJob::LEVELS` in order, `(run_after, id)` inside a lane), not a migration; migration 0011 is unchanged in both dialects. The durable rule: a multi-lane index is only seekable if the statement constrains the lane, so the query and the index are designed as one unit, and the plan test asserts the seek's usable columns (see also D56 — the plan tests currently EXPLAIN hand-copied SQL rather than the repositories' own).
- **Every phase ends with an adversarial review**, not only tests — the reviews in Phases 1–4 of the build so far found the archive-smuggling hole, the non-atomic OTP budget, the trusted `X-Forwarded-For`, the cross-org version oracle and the browser-only `Content-Type` defect, none of which the building agent's own tests caught.
- **External arbiters over self-reports**: the real `dart pub` client, the real pub.dev, a real browser, a real Postgres. Every claim in this document that says "verified" means one of those was involved.
- **Debt is written down where it lives.** A deviation with a documented reason and an exit condition is acceptable; an undocumented one is a defect.
- **Decisions before code, always.** Anything that changes normative behaviour is recorded in `docs/decisions.md` (and the relevant `S-xx`) *before* implementation — this is what keeps parallel agents from inventing policy and drifting. Genuinely open product forks go to the owner, not to a default.
- **Cadence that has worked twice now:** scout read-only (Explore agents map the exact code before any edit) → record the decision → fan out implementation across non-overlapping file ownership → adversarial review (independent verifiers prompted to *refute*, each finding re-verified) → fix the confirmed → validate on the final state → bookkeeping → commit. The review is a hard gate, not an optional pass: green tests from the building agent are necessary, never sufficient.
- **Model and effort are calibrated to the stakes, not applied uniformly.** Orchestration (this loop) and anything touching auth, the pub protocol, concurrency, distributed locking, or byte-stability run on the strongest available model at `xhigh`+ with a mandatory adversarial pass — these are the "cannot repair after the fact" properties. Ordinary feature work behind the existing traits runs a tier down at `high`; mechanical work (dependency bumps, doc/codegen regeneration, formatting, metrics wiring) runs cheaper at `low`–`medium`. In a workflow this is set per stage (`agent(..., {model, effort})`): cheap finders and mechanical stages low, `verify`/`judge` stages and auth-lens reviewers at the top tier. Reach for a workflow on find→verify and multi-file fan-out; stay solo on conversational and trivially-mechanical turns.
