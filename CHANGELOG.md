# Changelog

All notable changes to this project. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning: SemVer per component — server crate and web package are versioned independently. Entries are tagged `(server)`, `(web)`, `(infra)`, `(docs)`.

## 2026-08-14 — Phase 2 wave 3b: the byte collectors, one that runs by default and one that can finally be turned on (D22, D23)

Roadmap Phase 2 item 6, second half — the blob side of the lifecycle work, split from wave 3a deliberately because it touches the `BlobStore` trait and `object_store` rather than the repositories, and because it is the half that deletes **bytes** rather than rows. [Decision 31](docs/decisions.md#31--blob-lifecycle-staged-uploads-swept-by-default-and-an-archive-gc-that-streams-batches-and-resumes) was recorded before any code.

Two defects, one surface, pulling in opposite directions. Abandoned staged uploads were swept by a *phase inside* the unreferenced-archive collector, which ships disabled and dry-run — so a default install never deleted them, and the only bound on the pile was the S-24 publish budget times the archive cap, 30 x 100 MB per org per hour ([D22](docs/roadmap.md)). Meanwhile that same collector could not safely be switched on at scale: it materialized the entire key space in memory, spent two database round trips **per object**, had no wall-clock budget and no cursor, and held a flat 300 s lock a long pass simply outlived ([D23](docs/roadmap.md)). One knob gated both "delete bytes nothing can ever reference again" and "delete bytes a `pubspec.lock` may pin". They are now two jobs.

### Added

- (server) **`staging-sweep`, a new leader-locked job that is on by default** (`[jobs.staging]`, hourly, deletes for real, two-hour grace — closes D22). It collects abandoned staged uploads under `uploads/<format>/<session>.tar.gz`: publishes that were started and never finished. It can be on by default because its liveness test needs no judgement — the session's KV record expires an hour after the upload, after which `newUploadFinish` answers "expired or already finalized" and nothing can reach those bytes: no row, no URL, no client. It asks the database nothing at all.
- (server) **A strict key check on the staging side**, which the sweep it replaces did not have: only `uploads/<format>/<32 lowercase hex>.tar.gz` is ever a deletion candidate. The predecessor deleted *anything* under `uploads/` on age alone, which is a job that would happily eat whatever a future feature — or an operator with a shared bucket — put there.
- (server) **Three new `BlobStore` methods**: `list_stream` (the enumeration path, streamed), `list_prefixes` (one delimited level: the shards to walk, plus whatever sits outside them) and `head` (the re-read before a delete). The rule for a backend that cannot answer them is unchanged: not swept — "cannot enumerate" and "cannot report an age" both mean the collector refuses to guess, and now "cannot re-read one object" joins them.
- (server) **Batch reference queries** — `PackageRepo::live_sha256s` and `UpstreamRepo::cached_sha256s`, contract-tested on both dialects — plus **migration 0013**, the partial index on `upstream_versions (archive_sha256) WHERE cached` that the second of them needs. That table had no index on the column at all, because until now it was asked one hash at a time by a job that shipped disabled; on a mirror it is the largest table in the schema, so batching without the index would have moved the same cost one layer down.
- (server) **Five catalogued metrics**: `blob_gc_shards_total`, `blob_gc_sweep_converged`, and `staging_sweep_{scanned,deleted,bytes}_total`.
- (docs) **[ops/monitoring.md](docs/ops/monitoring.md) gains "what deletes bytes"** — the two jobs side by side with their opposite defaults, why each default is what it is, how to read a pass that stopped on its budget, and why a non-zero `contested` count is a busy registry rather than a fault.

### Changed

- (server) **The archive collector streams, batches, and resumes** (closes the blob half of D23). The key space is walked one **shard** at a time (`pub/ab/...`) from a durable `(format, shard)` cursor; each shard is streamed rather than collected into a `Vec`; references are resolved two queries per **batch** (`jobs.blob_gc.batch`, default 256) instead of two per object; and `jobs.blob_gc.budget_secs` (default 300) stops a pass where it stands, recording where the next one resumes. Coverage therefore *rotates* — a bucket too large to sweep in one budget is covered across passes, instead of the head being collected forever and the tail never. The cursor is a shard rather than a key because **`object_store` guarantees no listing order**, so every "resume after the last key I saw" design is unsound on this seam: an unordered backend would skip objects permanently rather than late.
- (server) **A delete is decided on a re-read, not on the listing that found the key.** `put` on a content-addressed key is an idempotent overwrite, so a republish of byte-identical content refreshes an object while a pass is holding a listing that called it old and unreferenced — and the version row commits right after. Both collectors now `head` the key immediately before deleting it and skip anything that got younger or vanished. This narrows the window from the width of a sweep to the width of one round trip; it does not close it, and the decision says so rather than claiming otherwise — there is no conditional delete on this seam.
- (server) **Both byte collectors' lock TTLs come off their budgets** (`max(300 s, 2 x budget)`), the rule decision 30 introduced for the retention pass. A flat 300 s over a sweep that may legitimately run longer is a lock a second instance can take while the first is still deleting.
- (server) **`blob-gc` no longer touches `uploads/`**, and its report loses `staged` while gaining `contested`, `shards`, `converged` and `resumes_at`. Its own defaults are unchanged and deliberately so: off, dry-run, 24-hour grace.
- (docs) **[S-20.a](docs/security.md#4-supply-chain--registry-integrity) is amended**: the abandoned-upload sweep is described as what it now is — its own job, on by default, strict about key shape — and the paragraph states plainly that until this wave it rode a collector that ships disabled, so on a default install those bytes were never collected at all.
- (docs) **[architecture.md](docs/architecture.md)** describes seven jobs rather than six, with the two byte collectors and their opposite defaults; **[ops/backup-restore.md](docs/ops/backup-restore.md)** says why the staged sweep needs no pausing around a backup while the archive collector does.

### Fixed

- (server) **The wall-clock budget bounded deletions, not the walk** — found while re-reading the first cut of this wave, in both new collectors. The check sat after a delete (staging) and after a batch flush (archive), so a shard or namespace whose keys are all too young, all foreign, or all still referenced never reached it: exactly the key spaces that are expensive to walk and that delete nothing, walked to the end under the job's lock. The check is per object now, with a test for each collector that fails on the old placement.

### Not closed

- **D23's second clause stays open.** The search indexer still walks every version of a package on every publish (`build_document` pages through them for `versions_count`). It is a search-surface change needing a repository method of its own, and closing half a defect quietly is how the other half gets forgotten — so it is written down in [decision 31](docs/decisions.md#31--blob-lifecycle-staged-uploads-swept-by-default-and-an-archive-gc-that-streams-batches-and-resumes) and in the roadmap rather than folded into this entry.

### Tests

- (server) 13 collector tests and 8 staging-sweep tests over a real migrated database and a real object store, most of them about something that must **not** be deleted: shared content hashes, proxied archives, objects inside the grace period, keys rewritten mid-sweep, foreign keys and foreign prefixes, and the other job's namespace. Plus the bounded-pass properties: a spent budget records where it stopped, a resumed pass skips what is done and clears the cursor when it reaches the end, an unreadable cursor restarts the rotation rather than stalling it, and a batch smaller than the shard still decides every key (five payloads picked to share one shard, so the batch boundary is actually crossed).
- (server) **Query-plan tests on both dialects**, because a missing index is green forever otherwise: `EXPLAIN QUERY PLAN` on SQLite for both halves of the reference check, and `EXPLAIN (ANALYZE, BUFFERS)` on Postgres against 20 000 loaded rows. The Postgres one was verified to fail without migration 0013 — the same query is a sequential scan there and an index-only scan with it.

## 2026-08-14 — Phase 2 wave 3a: nothing grows forever, and every delete is bounded (D12, D46, D47, D48)

Roadmap Phase 2 item 6, first half. Six tables grew without a bound and one of them — `audit_log` — is the table a documented hardening step forbids the application from deleting from, so the feature and the security requirement collided head-on. [Decision 30](docs/decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature) was recorded before any code and resolves that collision without giving up either side. The constraint that shaped every clause: retention has to work **automatically on a default install**, configured by "how long to keep" and nothing else.

### Added

- (server) **S-23 retention, on by default** ([decision 30](docs/decisions.md#30--retention-one-window-per-table-a-delete-that-stays-bounded-and-a-privilege-that-survives-the-feature), closes the data half of D12): a new leader-locked `lifecycle-purge` job — **the only job in the instance that deletes rows** — running every 15 minutes over `[jobs.lifecycle]`. One window per table in days, `0` meaning keep forever: audit **730** (≈24 months), sessions **30**, invitations **30**, notifications **180**, download stats **off**. On by default is the decision, not an oversight: a default install whose tables only grow is not a default.
- (server) **Predicates that are safe by construction rather than by configuration.** A session ages from `last_seen_at`, so a purged row is one that had already fallen out of the idle window and could no longer authenticate (and the validator refuses a window below `auth.refresh_idle_days`). An invitation ages from `COALESCE(accepted_at, revoked_at, expires_at)` — whenever it *settled* — which makes a live pending invitation undeletable at **any** window, instead of relying on an operator keeping the retention longer than the seven-day invitation TTL.
- (server) **`GET /api/v1/admin/audit/export`** — the cursor-paginated export S-23 has always specified. One request streams the whole filtered log as NDJSON over a keyset walk, writing each page to the wire before reading the next. It ends with an explicit `{"done":true,"count":N}` line, because once the response head is sent there is no status code left to report a failure and a silently truncated compliance export is worse than a failed one. Resumable by cursor, and **step-up gated** ([S-06.c](docs/security.md#1-authentication)) — the one exception to "S-06 is about escalation", since a single request hands the caller every actor id, IP and user agent the instance has recorded. The paginated viewer beside it stays ungated: the line is bulk, not sensitivity. The request itself is audited as `audit.export`, before a row leaves.
- (server) **`pub_audit_prune`** (migration 0012, Postgres): a `SECURITY DEFINER` function with a pinned `search_path` that refuses any cutoff newer than thirty days and any non-positive batch. This is how retention deletes audit rows *without the app role ever holding `DELETE`* — see below.
- (docs) **[ops/monitoring.md](docs/ops/monitoring.md) gains "what deletes rows, and what it needs"** — the window table, the one Postgres grant, how to read a pass, and why a backlog is normal — plus two alert rules (`PubRetentionRefused`, `PubRetentionBacklog`) and three catalogued metrics.

### Changed

- (server) **The S-22 INSERT-only grant survives the feature that needed to delete** (closes D46, [S-22.a](docs/security.md#5-audit--abuse)). The Postgres provisioning template's `REVOKE UPDATE, DELETE, TRUNCATE ON audit_log` **stands unchanged**; the app role gets `EXECUTE` on a function it does not own instead of a widened grant. The reachable capability is therefore "delete audit rows older than a month, one bounded batch at a time" rather than "delete audit rows" — which matters because evidence of an attack is *recent*, and a blanket grant hands a code regression or an injection exactly the rows worth erasing. Postgres grants `EXECUTE` on new functions to `PUBLIC`, so an instance provisioned from the pre-0012 template needs no action. A refused prune disables that one table **loudly** (a named log line, a gauge, a durable job failure) and the pass still sweeps everything else.
- (server) **Queue retention left the drain's five-second tick** (closes D47). It ran there as three *unbounded* `DELETE`s, outside the drain's own wall-clock budget — harmless in steady state and a lock-up the moment an ordinary operator action released a backlog (lowering a window, restoring a backup, a forward clock correction). Every retention delete is now `DELETE … WHERE id IN (SELECT id … LIMIT :batch)` in both dialects, and the caller loops until a pass comes back short or the budget is spent. On SQLite that bound is the load-bearing part: one unbounded delete holds the process's single writer for its whole duration, and a hold past the busy timeout turns a concurrent publish-finalize or sign-in into an error rather than a wait. The drain delivers; the lifecycle job deletes.
- (server) **The job lock's lifetime is per registered job** (closes D48). The scheduler applied one global TTL to *every* job — derived, since the last wave, from `jobs.queue.lease_secs`, so a queue lease silently set the lock lifetime of mirror sync, reindex, blob GC and the download rollup — while the manual-run registry used its own hardcoded 300 s. Both paths take the same lock under the same name, so two different answers to "how long may this job hold it" made the invariant that name carries false. One `JobLockTtls` table now feeds both.
- (docs) **S-23 is rewritten** ([S-23.a](docs/security.md#5-audit--abuse)): one uniform window across every audit action, replacing the original three (auth 12 mo, admin/role 24 mo, publish = package lifetime). Three windows over one table mean one viewer whose history depth silently depends on which action you filtered for. It is safe because provenance is **not** in the audit log — publisher, token and timestamp are columns on the version row (S-21) — so purging an old `package.publish` event drops the access record and never the provenance.
- (docs) **[architecture.md](docs/architecture.md)** and **[rules/migrations.md](docs/rules/migrations.md)** describe the retention job, the per-job lock TTL, and the `SECURITY DEFINER` shape to copy when a future feature needs a privileged write on a table the app role is deliberately restricted from.

### Review

The wave's adversarial pass ran five independent lenses, each prompted to refute rather than confirm. It found **nine defects that 1 100+ green tests did not**, and three of them were comments and documents asserting the opposite of what the code did. The corrections are folded into the entries above; what they were:

- **`jobs.lifecycle.enabled = false` also switched off the queue's three windows** — configured in a *different* section, validated greater than zero there, and including the one-hour `suppressed` window that holds addresses typed at the login form by unauthenticated callers. Before this wave that purge rode the drain, which deliberately has no `enabled` key at all; moving the executor quietly gave it one. **The key is gone** — every window is already its own switch (`0` = keep forever), so a job-level flag was a second and coarser way to say the same thing.
- **`SECURITY DEFINER` with a pinned `search_path` does not stop relation shadowing** — Postgres searches an implicit `pg_temp` **first** unless it is listed explicitly. Demonstrated live: a caller's `CREATE TEMP TABLE audit_log (…)` made the prune delete the decoy, return a plausible row count, and leave the real log intact while the job reported a converged sweep. The migration's own comment claimed this was handled. Fixed with both defences (`pg_temp` demoted, references `public.`-qualified). The direction was fail-safe for S-22 — evidence preserved, not destroyed — and not an escalation route, but it is a silent no-op on the one job whose promise is that it is never silent.
- **`retain_audit_days = 30` was a legal configuration that fails every pass on Postgres.** `INTERVAL '30 days'` is calendar arithmetic; `Duration::days(30)` is exactly 720 h. Across an autumn DST transition, or under any clock skew between the application and database hosts, the backstop refused the primary's own cutoff — and the log line blamed a missing grant the operator already had. The database's floor now sits a day looser than the application's, which is what a backstop is for.
- **`EXECUTE` on the prune was left granted to `PUBLIC`** (Postgres' default for new functions). Presented as a convenience — "no operator action required" — it also handed every role on a shared cluster the prune capability over this instance's audit log. Revoked; the explicit grant is now the one documented deployment step, which the loud missing-grant path already existed to support.
- **A malformed export cursor was a post-head failure.** `AuditFilter` carries no cursor, so the handler's own comment — "the filter is parsed before the budget is spent, so a typo'd cursor costs a 400" — was false: the parse happened inside the spawned walker, after `200 OK`, after a budget slot was spent, and after an `audit.export` row recorded a success that delivered nothing. Worse, the caller saw exactly the signal reserved for a genuine mid-walk failure, whose prescribed response is to retry from the same cursor.
- **The export's defensive branch emitted the terminator.** A page claiming more rows with no cursor ended the walk — via `Terminate`, which writes `{"done":true}`: a truncated export declaring itself whole, the one outcome this design forbids.
- **The export's budget bounded starts, not cost.** The window is fixed and aligned, so twelve at the end of one hour plus twelve at the start of the next is twenty-four walks in seconds — and a walk outlives the response head that releases its D8 concurrency permit and D13 deadline, so nothing else bounded it either. Against a five-connection SQLite pool that is a self-inflicted outage reachable by one administrator. Bounded now by a per-instance semaphore held by the walker for the whole walk.
- **`RetentionPolicy::cutoff` panicked on a window the validator accepts.** Windows are bounded from below only; `chrono`'s subtraction panics on overflow, inside a spawned scheduler task, killing retention for the life of the process and leaving the durable job state at "running". Saturating now — the same shape the SQLite repository already used and this code did not reuse.
- **Seven mutation-testing gaps**, the class [D51/D52/D55](docs/roadmap.md) are about. The batch bound was unasserted for four of six tables — including `job_queue`, the table D47 was filed about — because every fixture had one row per state; the session predicate could be moved from `last_seen_at` to `created_at` and stay green, because `create` writes the same stamp to both; the export could be truncated to its first page with all four S-23 tests passing, because `EXPORT_PAGE` is 200 and no fixture reached it; the manual-run lock TTL test asserted the lookup table rather than the registry; the dead-letter deletion lost its "never silent" assertion in the move; only a *zero* budget was ever tested, so a pass could scale its own budget or under-report what it deleted; and the query-plan test still ran `EXPLAIN` on a statement this wave had replaced. All closed, and the queue now reports its three terminal states as three report lines, so the dead-letter deletion is visible where an operator reads rather than only in a metric label.

### Tests

- (server) **The Postgres test that D46 said nobody would write.** Every other Postgres test in the suite — and compose, and CI — connects as the **database owner**, which can delete from any table, so a retention job that quietly needed `DELETE ON audit_log` would have passed all of them and failed only on the deployments that followed the documented hardening. A new test provisions a role from the 0002 template *for real* (including its `REVOKE` line), connects as it, and asserts both halves: a direct `DELETE FROM audit_log` is refused with a privilege error, and the prune through the function still works. It also calls the function directly with the Rust guard bypassed, to prove the floor and the negative-batch guard hold below the application.
- (server) A cross-dialect `retention` contract function (both dialects), 11 lifecycle integration tests over a real migrated database, and 3 export tests. The batch bound is asserted as *real SQL* — a backend that accepted the parameter and ignored it returns the whole backlog in one statement, which is the defect D47 is about.

## 2026-08-14 — Phase 2 wave 2: limits that name who they bound, and an instance that can be watched (D9, D14, D41, D43, D53, D54)

The second wave of roadmap Phase 2. Three decisions were recorded before any code — [27](docs/decisions.md#27--rate-limit-identity-what-a-bucket-is-keyed-on-and-what-happens-when-the-kv-is-down) (rate-limit identity), [28](docs/decisions.md#28--the-observability-plane-its-own-listener-bounded-labels-and-timing-that-stays-opt-in) (the observability plane) and [29](docs/decisions.md#29--a-mail-plane-that-cannot-hide-and-an-offline-way-back-in) (the mail plane) — including the one that had to exist *before* the feature it constrains: [S-04.d](docs/security.md#1-authentication), which bans `Server-Timing` on the authentication family, was written down before the header was implemented, because three separate documents had told an implementer to emit it and none of them qualified it.

### Added

- (server) **Read-path rate limiting on both planes** ([S-24.f](docs/security.md#5-audit--abuse), [decision 27](docs/decisions.md#27--rate-limit-identity-what-a-bucket-is-keyed-on-and-what-happens-when-the-kv-is-down), closes D14): every `GET`/`HEAD` on the app API *and* the pub protocol now spends a bucket keyed on **who is asking** — a CLI token, a verified session, or the client IP — resolved from the request alone with no database read on the hot path of `dart pub get`. Two numbers rather than one per surface (`read_per_ip_minute` 600, `read_per_identity_minute` 3000, both runtime-changeable), because a CI fleet behind one NAT is one IP and many tokens while a scraper is one IP and no credential. It fails **open**: a KV outage lifts the quota rather than taking package resolution down for every client.
- (server) **A token is a rate-limit identity of its own** ([S-13.b](docs/security.md#3-cliapi-tokens)): S-13 has always promised "per-token rate limits" and, until now, described nothing that existed. The bucket key is sixteen hex characters of the token's SHA-256 — never the secret, and never a credential-equivalent value in a second store.
- (server) **The in-process fallback limiter S-24 has always promised** ([S-24.e](docs/security.md#5-audit--abuse), closes D41): a KV outage no longer answers 503 and takes sign-in down instance-wide. Auth-abuse buckets fall back to a fixed table of atomic slots — bounded *by construction* rather than by an eviction policy, because bucket keys carry attacker-supplied addresses and a map would turn an outage into a memory-exhaustion primitive. Slot collisions merge budgets, which can only refuse more. The honest cost is written into the requirement: N replicas count separately, so an outage lifts the aggregate budget to N × the limit.
- (server) **A Prometheus exposition that can actually be scraped** ([decision 28](docs/decisions.md#28--the-observability-plane-its-own-listener-bounded-labels-and-timing-that-stays-opt-in), closes D9): the recorder's handle had been built and consumed by nothing, leaving 21 emitted instruments unreachable. `/metrics` now has a **separate listener** (`telemetry.metrics_listen`, default loopback) — not a route on the application port, which sheds load under saturation and would have taken the scrape dark exactly when it matters. HTTP RED metrics arrive with it, including the first histogram, which is why the recorder finally gets an upkeep task. The `route` label is the matched path or one of three constants, never the raw URI: both routers' fallbacks leave `MatchedPath` unset, so the textbook derivation would have let any anonymous caller mint unbounded label values.
- (server) **`telemetry.log_format`** (`pretty` | `json`) — JSON log output existed in the code and was unreachable, hard-coded at the call site.
- (server) **`telemetry.server_timing`**, off by default and **never** emitted on `/api/v1/auth/*` ([S-04.d](docs/security.md#1-authentication)).
- (server) **`pubd reset-smtp`** ([decision 29](docs/decisions.md#29--a-mail-plane-that-cannot-hide-and-an-offline-way-back-in), closes D43): the supported offline way back into an instance whose mail plane is what blocks sign-in. It deletes the stored `smtp` section so the boot `[smtp]` is authoritative again — needed because a stored section *replaces* the boot one wholesale, so correcting the config file and restarting did nothing. Reads the instance's normal configuration and touches only the settings table; a running instance picks the change up through the settings version poll with no restart. This required a `SettingsRepo::delete` the trait did not have, contract-tested on both dialects and reachable from nowhere else: "no stored decision" and "stored as empty" are different instances, and only the offline path may produce the first.
- (server) **A mail failure is visible in two minutes instead of twenty-one** (decision 29): `mail_transport_unusable` is set on the boot resolve error and on the first failed delivery, and an audit row (`mail.delivery_failed` / `mail.delivery_recovered`) records the **edge**, not the attempt — a row per attempt would be eight per message for as long as the relay is down. Neither signal needs a session, which was the whole problem: on an OTP-only instance a dead mail plane is precisely what prevents obtaining one.
- (docs) **[ops/monitoring.md](docs/ops/monitoring.md)** — scrape setup, shipped alert rules for the mail plane and the supply-chain signals, a starting dashboard, and "when the mail plane is down"; **[ops/metrics.md](docs/ops/metrics.md)**, generated from the exporter's catalogue and byte-compared, like the configuration reference. A break-glass entry for "nobody can sign in and mail is the reason" (closes D53's runbook gap).
- (web) **The admin jobs table renders the job phase**, which is where the drain reports its standing dead-letter count — the number the API already returned and the table dropped. Plus the two new read limits in the settings form.

### Changed

- (server) **A throttle trip is audited once per bucket per window, not once per refused request.** With the read path bucketed, one row per refusal would make every limiter a cheaper way to fill `audit_log` — a table with no retention yet — than the traffic it refuses; the attacker would choose the row count. Volume moved to `rate_limit_trips_total`. This applies to the pre-existing auth and publish buckets too.
- (server) **`/healthz` memoizes its backend probes for one second.** S-24 exempts health checks from rate limits and that stands; what changes is the cost of the exemption, which was three backend round trips per unauthenticated request.
- (server) **`publishes_total` is emitted.** It was in the documented catalogue and in no code path.
- (docs) **[architecture.md](docs/architecture.md) describes the system that exists** (closes D54): the string `job_queue` did not appear in it at all, the bus diagram still drew fan-out straight off the bus, and "two jobs exist today, both off by default" headed a list of four while five ship and one — the drain — deliberately has no `enabled` key. Its hand-maintained metric list, which had drifted to 11 names against 21 emitted, is replaced by a link to the generated reference.

### Removed

- (server) **`telemetry.otlp`** ([decision 23 amendment](docs/decisions.md#23--monitoring-is-optional)). Its only behaviour was a startup warning. A config key naming a capability the binary does not have is worse than its absence: it survives into an operator's file, their template and their expectations. Trace export returns as its own decision when it is built; until then the honest statement is that this product exports metrics and logs.

### Fixed

- (docs) **Two operator sentences that had become false** (D53): `install.md` still said the admin-UI SMTP settings "do not yet rebuild the mailer", which D10's closure made wrong; `backup-restore.md` still claimed a web sign-in proves SMTP, which is true only after a drain tick. Both KEK inventories now name **queued mail bodies** — sealed under the same key, and dead-lettering on the *first* attempt rather than after eight, so a restore under a different KEK silently discards every in-flight message.

## 2026-08-08 — Phase 2 wave 1: work leaves the request path (D2, D3, D10, D20, D31)

The first wave of roadmap Phase 2 — "make the claims true" — closing both of the phase's Critical debts and everything that rode the same paths. Decisions were recorded before the code, as always; the wave then ended in an adversarial review (six refutation lenses, every finding attacked by two independent refuters) which **confirmed six blocking defects that the authors' 72 new green tests did not see**, including a live sign-in code stored in the clear as a queued mail subject and a misconfigured SMTP section that silently discarded every message while the queue reported delivery. All are fixed below; the review's own decision amendments are in [decision 09](docs/decisions.md#09--always-compiled-backends-runtime-config-selection), [26](docs/decisions.md#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path) and [S-26.b](docs/security.md#6-secrets--configuration). Two forks were left to the owner rather than decided by an implementer, recorded as D41 and D42.

### Added

- (server) **A durable job queue** ([decision 26](docs/decisions.md#26--durable-job-queue-async-fan-out-and-outbound-mail-off-the-request-path), closes D2): a database-backed `job_queue` (migration 0010, both dialects; Postgres claims with `FOR UPDATE SKIP LOCKED`, SQLite with a single-writer `UPDATE … RETURNING`) carrying one row per *event* for notification fan-out and one per *message* for mail. Exactly-once fan-out is enforced by a uniqueness constraint on `(user_id, event_id)` — the invariant migration 0009's own header already claimed — so a re-run after a crash converges instead of duplicating. Mail is at-least-once by its `mail:{event}:{recipient}` dedupe key, which is harmless because [S-03](docs/security.md#1-authentication) makes a duplicate sign-in code single-use anyway. The drain is leader-locked, on unconditionally (an operator who could disable it could not sign in to re-enable it), bounded by its own lease, and prunes after itself. This is the mechanism S-33 webhooks will reuse as one more job kind.
- (server) **Queue priority**: interactive mail (sign-in, invitations) is claimed ahead of bulk notification broadcasts. Without it a CI pipeline publishing into a large org files thousands of rows ahead of the next sign-in code, and the code arrives after its ten-minute TTL — unrelated traffic taking sign-in down instance-wide.
- (server) **`POST /api/v1/admin/settings/smtp/test`** ([decision 09 amendment](docs/decisions.md#09--always-compiled-backends-runtime-config-selection)): sends a test message to the acting administrator's own verified address (no recipient field, so there is no mail-bomb vector and no new rate-limit bucket). A delivery failure answers `200 {"delivered": false, detail}` — a wrong SMTP config is not a server fault — and both outcomes are audited without ever recording a credential.
- (server) **A sixth `registry` settings section** carrying `require_auth_for_read` ([decision 05 amendment](docs/decisions.md#05--anonymous-read-configurable-default-allowed), closes half of D31): the flag flips at runtime as its addendum promised two waves ago, with boot config remaining its default. The pub-protocol extractor still judges credentials before the org lookup, so an unknown org slug cannot be distinguished from a known one.
- (web) **Admin settings**: a "send test mail" button rendering the delivered/failed detail, and a registry card with the anonymous-read toggle.

### Changed

- (server) **Every rate-limit window is now spent atomically** ([decision 03 amendment](docs/decisions.md#03--sessions-jwt-access--refresh-sessions-kv-backed-revocation), [S-24.d](docs/security.md#5-audit--abuse), closes D3): `hit` is one `Kv::incr` whose returned count decides, so a burst of N concurrent requests no longer costs one unit of budget. Every windowed bucket — OTP per email and per IP, login per IP, token-auth failures, the publish budget — was bypassable by concurrency; a test that fires 32 parallel requests against a budget of 5 previously admitted 15. The window now lives in the key (both KV backends re-arm a TTL on every increment, so a TTL cannot carry one), which makes windows **aligned and tumbling**: `Retry-After` is the time to the next boundary rather than to a first-hit anchor. Per-bucket outage stances are unchanged — auth fails closed, publish still fails open per S-24.c.
- (server) **A publish finalize now does constant work regardless of audience size** (closes D2's bill): fan-out to 200 recipients used to run ~400 queries and up to 200 blocking SMTP sessions *inside* a request the pub client retries seven times. The emitting request writes one row; the worker resolves the audience, files every recipient in one batch, and publishes `UserNotified` only after that commits, so a client acting on an event still finds the row it names.
- (server) **Runtime SMTP settings take effect** ([decision 09 amendment](docs/decisions.md#09--always-compiled-backends-runtime-config-selection), closes D10): the mailer resolves per send from the settings cache behind a memo keyed on a fingerprint of the *sealed* section, so a password rotation is noticed without unsealing anything on the hot path. Previously the admin surface accepted, sealed and audited SMTP settings that nothing ever read — an operator who configured SMTP only in the UI got an instance that delivered no mail while the UI reported `password_set: true`.
- (server) **Notification email is branded at send time** ([decision 17 amendment](docs/decisions.md#17--branding-default-pub-white-label-token-prefix-pub_), closes the rest of D31): a renamed instance no longer sends mail carrying its old name until the next restart — the one place stale branding was visible outside the instance.

### Fixed

- (server) **The S-04 sign-in timing oracle is gone** ([S-04.a](docs/security.md#1-authentication), closes D20): a deliverable address paid an SMTP round trip and answered **500** when the relay was down, while a policy-blocked one answered 200 instantly — an existence oracle you could trigger by taking the mail server offline. Both branches now perform one identical enqueue differing only in the row's state, so SMTP can no longer fail a sign-in request at all.
- (server) **A live sign-in code was stored in the clear** ([S-26.b](docs/security.md#6-secrets--configuration)): the mail body was sealed under the KEK as required, but the subject rendered as `"{code} is your sign-in code"` and subjects are not sealed — so every queued row carried the redeemable code beside the address it belonged to, readable in a dump, a replica or a backup for 24 hours. The subject is now code-free, and the regression test builds its payload from the production renderer rather than a literal, because all seven test construction sites had hard-coded a benign subject and were structurally blind to it.
- (server) **A misconfigured SMTP section no longer discards mail silently**: when the configured transport could not be built and none was memoized — every send after a restart — the mailer fell back to an in-process sink that accepted and dropped the message, while the queue marked it delivered, the counters reported success and nothing dead-lettered. An admin typing an unparseable `from` was enough. The sink now covers the no-host case only; a configured-but-unbuildable section fails the send so the queue retries and then dead-letters it, and such a section is refused at the write instead.
- (server) **The test-mail action told the truth**: it derived `delivered` from the stored settings and a sink that always succeeds, so it answered `delivered: true` for a host it had never contacted — in exactly the case it exists to diagnose.
- (server) **An instance admin could redirect the operator's SMTP credential onto a plaintext transport** ([decision 09 amendment](docs/decisions.md#09--always-compiled-backends-runtime-config-selection)): the boot-password gate compared host, port and username, so flipping only `security` to `none` kept the fallback alive and put `AUTH PLAIN` with the operator's password on the wire in the clear. Transport security joined the gate, and a boot-provenance credential is never attached to an unencrypted transport.
- (server) **A refused settings PATCH no longer half-applies**: six sections were written by six independent calls with early returns between them, so a 400 naming SMTP had already committed the sections ahead of it — including the anonymous-read flag. Validation now runs entirely ahead of the writes.
- (server) **A hung SMTP relay could make the drain duplicate deliveries**: one tick reused a single timestamp for every claim, so leases were minted in the past and the retry backoff collapsed to "retry immediately"; the drain could then outlive the scheduler's lock, letting a second drain reap and re-send its in-flight messages. The drain re-reads the clock per pass, stops inside its own lease, and the job lock is released only by the holder that took it.
- (server) **An operator's own unencrypted relay sends again**: hardening the credential gate above, the first cut also refused to attach a boot-configured password to a `security = "none"` transport. A verification pass found that guard was dead code against the attack — the endpoint gate already refuses a runtime downgrade with a 400 — and live code against the operator: `security = "none"` with a password is a legal, validated and documented configuration for a local relay, and refusing to build it turned that deployment into a total mail outage where every message dead-lettered and nobody could sign in. The endpoint gate is the whole mechanism; the second guard is gone.
- (server) **The queue claim seeks instead of scanning.** Ordering one statement by `priority, id` demoted `run_after <= now` from a seek bound to a post-filter, so every claim read the whole pending partition — measured at **6.59 ms against 0.006 ms** on a 200k-row backed-off backlog, on a write statement that holds SQLite's single write lock up to 64 times per tick, with Postgres abandoning the index for a sequential scan. The claim now drains one priority lane at a time, which restores the seek and is stronger fairness than ordering within a batch: the interactive lane empties before the bulk lane is touched.
- (server) **`job_queue` was pruned in one of its five states**: `suppressed` rows — one per policy-rejected sign-in attempt, each carrying the attempted address, driven by an unauthenticated endpoint — and `dead` rows accumulated forever, and neither the retention nor the depth query had an index, so every five-second tick full-scanned a table that only grew.

## 2026-08-07 — authority changes reach the token plane, and grants gain a ceiling (D37, D39)

Two owner-decided authorization rules, each recorded in the decision log before a line of code and each hardened by an adversarial review (three lenses, every substantive finding re-verified; the one real defect — a token sweep that could abort the session revocation it should follow — fixed by reordering and making the sweep best-effort).

### Added

- (server) **Role-grant ceiling** ([decision 19 addendum](docs/decisions.md#19--rbac-cumulative-role-levels-with-a-single-authorize-chokepoint), closes D39): a non-Owner manages only role levels **strictly below their own** — both the level granted and the level the target currently holds — so an Admin can no longer appoint, promote to, demote, or remove an Owner or another Admin. Owners are exempt; **self-directed reduction** (demote or remove yourself) is always allowed, which is how an Admin leaves an org. The check lives in the org service, so add/change/remove/invite all inherit it; denials are a `403 forbidden` naming role names. The ≥1-Owner invariant is unchanged.
- (server) **Authority changes reach the token plane** ([decision 13 addendum](docs/decisions.md#13--cliapi-token-format), [S-13.a](docs/security.md#3-cliapi-tokens), closes D37): a lowered role or a withdrawal now **revokes the member's org tokens whose scopes exceed the new level** (a removal takes all of them; a raise takes none), using the mint gate's scope→level map — moved into `core` as `TokenScope::required_action` so it has one home. **Suspension gates the credential plane**: `find_active_by_hash` answers only tokens of active users, so suspending an account stops its CLI tokens within ≤60 s and unsuspending restores them — reversible, and the reason the S-27 break-glass answer is now real. One `token.revoked` audit row per sweep, best-effort, ordered after the S-09 session revocation so it can never block it.
- (web) **Warning UX for privileged transitions** (decision 19 addendum): role pickers offer only levels the caller may grant, members at or above the caller's level render read-only, and granting/ demoting/ removing an Admin or Owner confirms through a dialog first. The member-role select no longer fires a mutation straight from `onChange` — a warn-worthy pick opens the dialog and snaps back, and any failed change re-reads the row so the select never shows a role the server did not apply. A follow-up toast reports revoked CLI tokens.

### Fixed

- (web) **D32, in passing**: `revokeInvitation` is now wrapped in `withStepUp` (it silently failed the step-up prompt before), and gained the in-flight guard every other mutation on the screen already had.

## 2026-08-07 — SQLite fit for the default deployment, configurable DB pools

Roadmap Phase 1.4, closing debt items D4 and D24. The documented `docker run` minimum runs on a SQLite file, and that file now gets the write-concurrency posture a production default needs; both database backends stop hard-coding their pool.

**WAL, `synchronous = NORMAL`, and an explicit busy timeout.** File-backed SQLite databases now open in WAL mode: readers stop blocking the writer (and vice versa), so concurrent write transactions queue on the WAL write lock and resolve within the 5 s busy timeout instead of surfacing `SQLITE_BUSY` as a 500 (D4). `synchronous` drops from FULL to NORMAL — in WAL mode NORMAL still guarantees a consistent database after a crash; FULL would only buy back the last-committed-transactions tail with an fsync per commit paid by the single writer. Foreign keys stay explicitly on. `:memory:` databases keep their single pinned connection and are now exempt from idle/lifetime reaping, because closing that sole connection would drop the database itself.

**The pool is configuration, not a constant.** A new `[database.pool]` section (`PUB_DATABASE__POOL__*`) tunes both dialects: `max_connections` (unset = per-dialect default — 5 for SQLite, where connections beyond "readers + the writer" only queue on the write lock; 10 for PostgreSQL), `acquire_timeout_secs` (30), `idle_timeout_secs` (600), and `max_lifetime_secs` (1800) — the timeout defaults are sqlx's own, restated so they are visible, validated, and tunable (D24). Zero values and a lifetime below the idle timeout are startup errors with messages that name the key and the fix; the effective pool is listed in the startup summary.

### Added

- (server) **`[database.pool]` config section** ([config](server/crates/config/src/lib.rs)): `max_connections`, `acquire_timeout_secs`, `idle_timeout_secs`, `max_lifetime_secs`, applied to whichever backend `database.kind` selects, with per-dialect ceiling defaults, fail-fast validation, and a `database.pool` line in the effective-config summary.
- (server) Concurrency tests over a real file-backed SQLite database ([db-sqlite](server/crates/db-sqlite/src/lib.rs)): four writers committing in parallel never see `SQLITE_BUSY`, and writers proceed while a read transaction stays open — the second one fails within the busy timeout if WAL is ever switched off.

### Changed

- (server) **File-backed SQLite runs WAL with `synchronous = NORMAL` and a 5 s busy timeout** ([db-sqlite](server/crates/db-sqlite/src/lib.rs)); `:memory:` keeps one pinned connection and is never reaped. Both [db-sqlite](server/crates/db-sqlite/src/lib.rs) and [db-postgres](server/crates/db-postgres/src/lib.rs) build their pools from `database.pool` instead of a hard-coded 5-connection pool — the PostgreSQL default ceiling rises to 10.

## 2026-08-07 — the first end-to-end pass: one binary, a real browser, the real `dart pub` client

The frontend and the backend were built against each other's documentation; this is the first time they were run against each other. The Astro build was embedded into `pubd`, the binary was started on the documented `docker run` minimum (SQLite + filesystem blobs + in-memory KV) with a local SMTP sink, and every v1 flow was driven through Chrome and through the real Dart SDK 3.12.2 client. Five defects fell out — one of them fatal to the whole deployment shape — and all five are fixed.

**`/app/search` served the landing page.** [Decision 04](docs/decisions.md#04--single-binary-now-optional-split-later) promises one binary serving the SPA and the API on one origin, and the app page says in a comment that unknown `/app/*` paths are "served by the embedded-asset service on the server, which falls back to this same shell". The service did no such thing: it tried the literal request path against `rust-embed` and, on a miss, answered the **root** `index.html`. Astro emits directory-style routes (`app/search/index.html`) and one prerendered island shell (`app/index.html`), so every deep link and every reload of an app route returned the marketing page — whose only island is the theme toggle. The SPA simply did not boot. The resolver now walks a real ladder (exact file → directory index → `.html` sibling → the app shell for `/app/**` → `404.html` with a **404**), and the committed placeholder tree grew the two documents that make the contract testable.

**A grant is invisible until the token rotates.** [S-09.a](docs/security.md#2-sessions--web-plane) deliberately does *not* revoke sessions when a membership is **created** — nothing stale can spend authority that did not exist yet. The consequence nobody had drawn: the access token keeps its old `orgs` claim, so for up to one access TTL the user who just created an organization gets 404 on its own private packages, 403 on its member list, zero results in search, and no events for it. Creating an org and accepting an invitation now rotate the pair on the spot, through the interceptor's own single-flight so the rotation cannot race an automatic refresh into the S-08 reuse detector.

**An invitation had nowhere to go.** Administrators could mint invitations and the API had `POST /api/v1/invitations/accept`, but no screen called it — the invited colleague received a code and the product had no field to type it into. `/app/orgs` now has one.

## 2026-08-07 — the registry-facing screens, generated API types, and the live event stream

Every "coming soon" card is gone. Home, search, package pages, org profiles, the notification center, package management, and the admin panel are built against the committed app API, and the wire types behind them are **generated from the server's OpenAPI document** instead of hand-written. The island is now route-split, so a session that never opens the admin panel never downloads it.

**The types come from the server, or they are wrong.** `packages/api/openapi.json` is the utoipa document fetched from a running `pubd`, checked in so a frontend build never needs a backend, and `bun run gen:api` runs `openapi-typescript` over it into a committed, Biome-excluded module ([decision 14](docs/decisions.md#14--frontend-shape)). `types.ts` is now aliases into that module; what stays hand-written is stated and justified in one comment — the `ListDto<T>` generic utoipa monomorphizes away, the value-level vocabularies the wire carries as plain strings, and the query-parameter bags (see *Notes*).

**A search cursor is bound to its ordering, so the URL state enforces it.** Presenting a cursor under a different `sort` is a 400, not a reshuffled page ([decision 11](docs/decisions.md#11--search-behind-a-trait)). Rather than remembering that at four call sites, the transitions live in [`search-query.ts`](web/apps/site/src/app/search-query.ts): changing the sort, the query text, or a facet chip *is* the operation that drops the cursor, and only "next page" keeps it. `?q=&sort=&cursor=` round-trips through the address bar, so a results page is linkable and the back button walks searches rather than keystrokes.

**Fetch-streaming, because `EventSource` cannot present a bearer.** The SSE client ([events.ts](web/packages/api/src/events.ts)) is a `fetch` body reader plus a hand-written frame decoder that buffers across chunk boundaries — a network read has nothing to do with a frame boundary. Reconnects are exponential with subtractive jitter (so the ceiling is a real ceiling) and the backoff **resets on a healthy connection**, or a stream that lived an hour would come back an hour later. `Last-Event-ID` survives the reconnect; the token is re-read at connect time, so a reconnect after a refresh presents the new one. A 401 or a 429 is **terminal**: the access token is repaired by the API client, and looping against a revoked session is a client turning its own logout into a denial of service.

**The one `innerHTML` in the product, and the contract that makes it safe.** [`Prose`](web/apps/site/src/app/prose.tsx) renders `readme_html`/`changelog_html` and nothing else. It is safe entirely because of the server: rendered once at publish time onto the immutable version row, comrak with raw HTML escaped, then ammonia's allowlist forcing `rel="nofollow ugc noopener"`, http/https/mailto only, and no relative URLs ([S-11](docs/security.md#2-sessions--web-plane)).

## 2026-08-07 — the web application: real API client, app shell, and the auth/account/token/org screens

The frontend stops being a skeleton. `packages/api` grows into the client the app actually needs (bearer injection, proactive and reactive refresh, a denial latch, typed modules per area), module-level Solid stores replace the placeholder island, and the screens whose endpoints are already committed are built end to end. Everything the app API has not shipped yet is a visibly marked placeholder, not fake data.

**One refresh, or the reuse detector eats the session.** A page that loads six things in parallel used to be a design problem waiting to happen: six 401s, six refreshes, five of them presenting a rotated-out token, and [S-08](docs/security.md#2-sessions--web-plane)'s reuse detection killing the family as a direct consequence of loading a page. Refresh is therefore single-flight — proactively (the access token's `exp` is decoded and refreshed inside a 60 s skew window, so the cost lands before the user's click rather than during it) and reactively (concurrent 401s share one promise, and each request is cloned *before* its body is consumed so the retry is intact). A refusal closes a **denial latch**, so a dead session costs one request instead of one per click.

**A tunnel is not a logout.** `NetworkError` and `ApiError` were already distinct types; the interceptor is where that distinction earns its keep. A transport failure during refresh propagates untouched: the latch stays open, the stored pair stays, and `onAuthLost` is never called. Only a *refusal* clears storage and signs the user out — asserted from both the proactive and reactive paths, including recovery once connectivity returns.

**The step-up gate is split between the layer that sees it and the layer that can act on it.** An interceptor spots the distinct `step_up_required` 403 ([S-06.a](docs/security.md#1-authentication)) and opens the prompt, because it sees every response; the *caller* owns the retry, because only it knows whether the action is still wanted after the user has typed a code. One shared prompt, many waiters, no stacked dialogs — `withStepUp(() => …)` at each gated call site.

**A QR code without a dependency.** 2FA enrollment shows a real scannable code from a ~350-line byte-mode encoder (level M, versions 1–9, Reed–Solomon over GF(256), all eight masks scored) rather than pulling a library into a security screen. It is validated by *decoding its own output* with an independently written reader, plus the published format/version-information tables — a transposed coordinate or a mis-sized block split fails the round trip. Payloads too long to encode fall back to manual secret entry.

## 2026-08-07 — realtime layer, and an adversarial review of the whole app API

The event bus of [decision 22](docs/decisions.md#22--domain-event-bus-webhooks-and-integrations-on-top) is real, and two consumers hang off it: the SSE stream of [decision 20](docs/decisions.md#20--realtime-sse-event-stream--notification-center) and the notification center. Migration **0009** adds `notifications` and `notification_prefs` to both backends. The second half of the slice is a fresh-eyes pass over every route the app API exposes, phases 1–2 included.

**One bus, and the fan-out order is the design.** Domain services emit into `EventBus` (new crate [`pub-events`](server/crates/events)); it broadcasts in-process, republishes to the KV broker topic so any instance can serve any client's stream, and then runs its consumers. Consumers run **only on the emitting instance** — a peer feeds an inbound event to its stream and to nothing else, or N replicas would file N notification rows for one event. Consumer output (one `UserNotified` per recipient) re-enters the stream but never the consumers, so there is no cycle to bound. The audit log is deliberately *not* a consumer: it is durable truth under S-22, while the bus is a hint channel whose consumers may fail silently.

**The stream's audience is a property of the event.** `DomainEvent::audience()` answers `Org` | `Instance` | `User`, and the SSE filter consults nothing else — no package flags, no per-variant special case — through the same `authorize()` chokepoint the REST paths use. Adding an event variant without deciding its audience does not compile. Replay applies the identical filter, so reconnecting with a `Last-Event-ID` cannot widen what a principal sees.

**"Terminate within one access TTL" is enforced at startup.** The heartbeat is where a stream re-checks the revoked-`sid` blocklist and re-reads the account row, so the config validator refuses `realtime.heartbeat_secs >= auth.access_ttl_minutes`. A KV failure during the re-check closes the stream, and the stream ends at the token's own `exp` regardless.

### Added

- (server) **`GET /api/v1/events`** — the SSE stream (S-32). Access-JWT authenticated through the same extractor as every REST route (fetch-streaming, because `EventSource` cannot set `Authorization`), heartbeats that re-check revocation and the instance-admin flag, an RAII per-user connection cap answering `429 + Retry-After`, authorization filtering, and best-effort `Last-Event-ID` replay from a bounded per-instance ring. Frames carry `id:`, `event:` (the dot-namespaced type), and a `StreamEvent` document that is in the OpenAPI spec like every other payload.
- (server) **The notification center** — `GET /api/v1/notifications` (cursor + unread badge), `POST /api/v1/notifications/read` (ids or all), and `GET`/`PATCH /api/v1/notifications/preferences`. Three categories (`package`, `org`, `security`) with the event→category map on the event itself; `org` and `security` are the high-importance tier and reach a mailbox through the existing `Mailer` unless the user turns them off. Fan-out is at write time, one row per recipient, bounded by `realtime.max_notification_recipients`.
- (server) **`pub-events`** — `EventBus` (broadcast + broker bridge + replay ring + connection budget) and `NotificationCenter`, behind the `EventConsumer` seam an outbound-webhook worker will implement unchanged (v1.1).

The generated OpenAPI document must match a hand-maintained list of every `(method, path)` **exactly**, every authenticated route must declare the bearer scheme, every mutation must refuse an anonymous caller *and* demand the S-12 header, every paginated route must answer a tampered cursor with one clean 400, and no schema may carry a credential-shaped field outside a named allow-list.

### Fixed

- (server) **The package page walked every version of a package.** `GET /api/v1/packages/{name}` loaded the complete version list — one query per hundred versions, on an anonymous-reachable route — to compute three fields. It now derives `latest` from a bounded newest-first scan that terminates at the first live stable release (one query for essentially every package) and takes `versions_count` from a new `PackageRepo::count_versions` aggregate.

The filter is `(actor, actor_kind)` now, `user` by default, and an unknown kind is a 400.

### Notes

- **Deleting an organization notifies nobody.** `OrgDeleted` is org-scoped and the deletion has already removed every membership by the time it fires, so the audience resolves empty. The affected members do get their sessions revoked, which is the signal they act on; closing it properly needs a recipient list on the event and lands with webhooks.
- **Org member listings are still single-page.** Truncating them is worse than not paginating them (an Owner could vanish from the table), so they stay unbounded in row count while the account lookups behind them are batched and chunked. Cursor pagination lands with per-package grants, which is when an org is expected to be large.
- **The stream's org roles come from the access token**, like every other read path. They cannot be stale-high — any role change revokes the session and the next heartbeat kills the stream — only stale-low, which fails closed.

## 2026-08-07 — management and administration surface

Everything a human changes: the org danger zone, package moderation, and the instance-admin panel. Migration **0008** adds `users.is_instance_admin`, `orgs.description`, and `orgs.archived_at` to both backends, plus the indexes the new listings and gates read.

Three rules shape the slice, and each of them lives one layer below the routes so a handler cannot forget it.

**S-09 is a service, not a checklist.** Every membership mutation is classified as a grant, a redefinition, or a withdrawal ([`AuthorityChange`](server/crates/admin/src/orgs.rs)), and the last two revoke every session of the affected user before the call returns. `OrgRepo`'s membership mutators have exactly one caller each — `OrgService` — so "no route can forget" is structural. A pure **grant** deliberately does not revoke: a token issued before it carries no claim for the org and fails closed, and logging somebody out of every device the instant they accept an invitation costs UX for no security. The rule and its table are in [S-09.a](docs/security.md#2-sessions--web-plane).

**Deleting an org that owns packages archives it.** Name claims and version rows are exactly what [decision 06](docs/decisions.md#06--retract--admin-only-hard-delete-with-tombstone) keeps forever, and both hang off the org row — so erasing it would un-burn a package name. `DELETE /api/v1/orgs/{slug}` refuses with 409 while packages exist; `force: true` stamps `archived_at`, strips members, invitations, and tokens, and flips every package private + unlisted + discontinued *through the registry service* so the search index follows. An org with nothing durable behind it is erased outright.

**Runtime settings actually take effect.** Registration mode, the S-31 domain allowlist, the S-24 rate limits, branding, and the instance upstream switch moved out of boot config into the `settings` table, read per request from an `ArcSwap` cache whose defaults *are* the boot config. A write goes repository → local reload → broker publish, with a 45 s version poll as the reconciliation fallback for messages a reconnect drops.

- (server) **Org management** — `PATCH /api/v1/orgs/{slug}` (name, description, upstream policy; the slug is immutable because it is the virtual registry base), members list/add/update-role/remove, invitations create/list/revoke/accept, and `DELETE /api/v1/orgs/{slug}`. The ≥1-Owner invariant surfaces as a clean `409 last_owner` from the transactional repository check. Invitations are budgeted at ≤20/day/org (S-24) and return their token once, so an instance with no SMTP configured can still onboard people.

## 2026-08-07 — search backend and the public read model

[Decision 11](docs/decisions.md#11--search-behind-a-trait) in both dialects, and the seven `GET` routes the web UI is built on. Migration **0007** (numbered after `0006_jobs_and_supply_chain`, which already existed) adds `package_search`, `package_tags`, and `download_stats` to each backend, dialect-idiomatic: a Postgres `tsvector` generated column with a GIN index plus a `pg_trgm` index on the name; a SQLite FTS5 external-content table kept in step by sync triggers.

The rule the whole slice is built around: **visibility is enforced inside the search implementation, through the chokepoint that already exists.** Every read takes a `SearchView` — the orgs in which `authorize(actor, ReadPackages, …)` succeeds, computed by *calling* that function — and each backend emits `visibility = 'public' OR org_id ∈ view` before anything a query string can influence. That covers the surfaces the pub protocol never had: a facet bucket, an instance counter, and a reverse-dependency edge disclose a private name just as effectively as a status code, so they run the same predicate and are asserted to agree with the listing ([S-04.d](docs/security.md#1-authentication)).

### Added

- (server) **`PackageSearch` per backend** ([db-postgres](server/crates/db-postgres/src/repo/search.rs), [db-sqlite](server/crates/db-sqlite/src/repo/search.rs)) behind the existing core trait, over a denormalized `package_search` document per package that has a live version. `package_tags` carries the exact-match dimensions (`topic:`, `dependency:`) and, with them, the reverse dependency graph read from stored pubspecs. Postgres additionally does fuzzy name matching through `pg_trgm` (`blok` finds `flutter_bloc`), which a lexeme index structurally cannot; SQLite gets prefix matching. The backends may differ in recall, never in visibility.
- (server) **A hand-written query parser** ([core/src/search.rs](server/crates/core/src/search.rs)) over the tag vocabulary that applies to us: `format:` `org:` `topic:` `dependency:` `is:private|public|discontinued|unlisted|retracted-latest` `sort:`, quoted phrases, and a leading `-` to negate any filter. It **never fails** — unparseable tokens are collected into `unknown_filters` and echoed back, so a search box cannot produce an error page and a malformed filter is indistinguishable from one that matched nothing. Untrusted text never becomes engine syntax: every term is quoted (FTS5 `"…"`, tsquery `'…'`), so `OR`, `NEAR`, `&`, `!`, `<->` and `:` inside a term are matched literally.

Counting a served archive costs **no I/O** — one mutex-guarded map increment — and the rollup job drains the buffer into `download_stats` with an additive upsert, then writes the totals back onto the search index so `sort:downloads` reads one indexed column. **`HEAD` never counts**: the pub client HEADs before every GET and axum routes HEAD to the GET handler, so without the explicit check every number would be roughly double.

Contract functions `package_search`, `search_visibility`, and `download_stats` run on **both** backends (the Postgres leg against a throwaway `postgres:17-alpine`), covering relevance ordering, the whole filter vocabulary with negation, injection attempts as data, keyset pagination, ordering-bound cursors, additive rollups, and a 3-visibility × 4-principal matrix asserted on listings, text queries, `is:` probes, by-name lookups, facet totals, and counters. ## 2026-08-07 — proxy adversarial review, arbitrated by the real client against the real pub.dev

An attack pass over the upstream proxy surface, with the **real `dart pub` client** (Dart SDK 3.12.2) driving a live `pubd` (SQLite + filesystem blobs + in-memory KV) whose upstream is the **real pub.dev** — every upstream connection routed through a local counting proxy, so "was upstream asked?" is an exact number rather than an impression. Four defects fixed, three structural residues recorded in [docs/security.md](docs/security.md) (S-04.c, S-16.b, and S-19.a's new rules).

**The arbiter run.** `dart pub get` resolved an 11-package graph (`http` and its transitive closure) through `/o/acme/pub`, wrote **our** URL and **pub.dev's own** `archive_sha256` into `pubspec.lock` for all 11 (checked against pub.dev's live listings), and the resolved code ran; the proxied `collection-1.19.1.tar.gz` is byte-identical to pub.dev's. A second resolve with `PUB_CACHE` wiped opened **zero** upstream connections against eleven for the cold one. With pub.dev made genuinely unreachable and the listing TTL forced to 0, the same graph still resolved from cache while an uncached name answered one clean `could not find package args` — no retry storm. Then the **dependency-confusion demonstration**: `path` (a real pub.dev package, at that point cached here with all 76 of its upstream versions) published locally as `9.9.9`; a fresh consumer resolved `path 9.9.9`, locked our hash, ran code only the local package defines, and never touched upstream — while the same name stays a `404` for anyone who cannot read it, rather than falling through to pub.dev's namesake. Full transcript in [docs/protocol.md](docs/protocol.md#conformance-testing).

### Fixed

- (server) **The SSRF guard blocked private *addresses* but not the *names* for them** ([registry/src/upstream/http.rs](server/crates/registry/src/upstream/http.rs)). The check runs before DNS, so `169.254.169.254` was refused while `metadata.google.internal` — one upstream-supplied `archive_url` or redirect away — was not. Names reserved for loopback and private use are now refused for hosts **upstream** picks: `localhost`/`*.localhost` (RFC 6761), `*.local` (RFC 6762), `*.internal` (ICANN's private-use TLD, home of GCP's metadata server) and `metadata.goog`, `home.arpa` (RFC 8375). The *configured* host stays exempt, so `https://packages.corp.internal` remains a supported mirror. Numeric-notation dodges (`https://2130706433/`, `0x7f000001`, `127.1`) were already covered by WHATWG host parsing — now pinned by a test, since it is a dependency's property rather than ours.
- (server) **One bad package could close the proxy for every package** ([registry/src/upstream.rs](server/crates/registry/src/upstream.rs)). The instance-wide circuit breaker counted every non-404 failure, so a listing our own validator refuses — or one past `max_listing_bytes` — was indistinguishable from an outage. The pub client re-fetches a listing before *every* resolve, so a single CI job on a single such package would have opened the circuit repeatedly, degrading everything else to stale-or-404. Only **reachability** failures now count; an unusable document is recorded as `upstream_fetch_total{outcome="unusable"}` and nothing more. Symmetrically the **archive** path now feeds the breaker on transport failures: with a warm listing cache and a dead archive host it was the only branch still going out, and the one the breaker could not see, so every download paid its full retry budget and timeout with no circuit ever opening.
- (server) **A truncated download was reported as tampering.** Hash-before-store already made short bytes harmless — they hash to something else and are never stored — but the conclusion arrived through the hash check, which filed a dropped connection in the S-19 quarantine register as upstream substitution and emitted a `security`-category alarm for a network hiccup. A body that stops short of its own `Content-Length` is now named as the transport failure it is; the version stays ingestible, so the next honest answer caches normally.
- (server) **Upstream's `Content-Length` could size an allocation.** The archive buffer was pre-reserved from the advertised length, so an upstream announcing `max_archive_bytes` and then sending nothing cost 100 MB of resident memory per in-flight fetch (× `max_concurrent_fetches`) for as long as the archive timeout allowed. The hint is clamped to 1 MiB and `Vec` growth pays for real archives.

### Added

- (server) **10 tests** for the above: SSRF refusal of special-use hostnames and of every numeric loopback notation; an unusable listing and an oversized one leaving the circuit closed for other packages; a dead archive host opening the circuit behind a warm listing cache; a successful download clearing the failure count; a truncated body storing nothing, quarantining nothing, and staying ingestible; the buffer clamp; plus two proxy conformance tests — a **proxied** response gzips its listing and answers `HEAD` exactly as it answers `GET` (the client HEADs before it downloads, and the proxied path builds its body somewhere else than the local one), and a hostile upstream document changes what our fields *say* and never what fields *exist*: extra top-level and per-version keys are dropped, a wrong-typed `isDiscontinued`/`retracted` collapses to our default rather than travelling through, a non-string `replacedBy` is dropped, and `latest` is recomputed so upstream cannot name a version we do not serve.

### Changed

- (docs) [S-04.c](docs/security.md#1-authentication) records the residue this review could **not** close, with measurements: an unclaimed-name miss costs an upstream round trip and a claimed-but-unreadable name costs two indexed reads, so two byte-identical 404s differ by 0.34 ms vs 219 ms and an anonymous prober can decide whether a name is claimed on the instance by timing alone. Every uniform-latency alternative is worse than the leak; `registry.require_auth_for_read = true` is what closes it, and that is now the documented reason the flag exists. [S-16.b](docs/security.md#4-supply-chain--registry-integrity) records that `upstream_policy = block` binds to the org's **base**, not its members — the same token resolves upstream packages through the public root — and [S-19.a](docs/security.md#4-supply-chain--registry-integrity) gains the four rules above. Decision 07 carries the breaker rule; architecture.md and protocol.md carry the verification.

## 2026-08-07 — mirror mode and supply-chain guards

The second half of [decision 07](docs/decisions.md#07--upstream-proxy-read-through-cache-and-mirror-mode): a leader-locked worker that warms the read-through pipeline instead of duplicating it, the [S-17](docs/security.md#4-supply-chain--registry-integrity) shadowing alarm the mirror makes detectable, and the unreferenced-blob GC that finally closes [S-20.a](docs/security.md#4-supply-chain--registry-integrity)'s staged-upload gap. Everything new is **off by default**. Design refinements recorded in [docs/decisions.md](docs/decisions.md) (decision 06 and 07 addenda) and as amendment S-17.a in [docs/security.md](docs/security.md).

**Verified against the real pub.dev**: a `full` sweep over its 86 642-name index mirrored metadata and archives, was killed mid-sweep, and resumed at the stored offset with zero upstream requests for the packages the interrupted tick had already saved; a locally claimed name pub.dev also carries raised exactly one S-17 alarm and was never mirrored; a GC dry run enumerated the resulting 58 objects and found every one referenced.

### Added

- (server) **Mirror sync worker** ([jobs/src/mirror.rs](server/crates/jobs/src/mirror.rs)) in three modes from `[upstream.mirror] mode`: `off` (default), `recent` (re-poll the packages this instance already caches, oldest snapshot first), `full` (enumerate upstream's `/api/package-names` once, then behave like `recent` until `resweep_after` starts the next enumeration). It drives `UpstreamService::refresh` — the read-through pipeline with the read TTL replaced by a caller-supplied freshness floor — so there is **no second ingest path**: same pubspec validator (S-20), same hash-before-store rule (S-19), same byte-drift freeze, same circuit breaker, semaphore, and single-flight guard. Chunked (`chunk` bounds one tick's hold on the leader lock, `concurrency` bounds our in-flight refreshes while the service's semaphore still bounds upstream's), and an open circuit skips the whole tick rather than spending the half-open probe on the first name of a chunk.
- (server) **A sweep that survives restarts.** `jobs.cursor` holds `{page, offset, completed_at}`, so a pod rescheduled 30 000 names into the index resumes there instead of at zero; `refresh` answers `Fresh` without asking upstream for anything inside the floor, which makes re-walking already-covered names one indexed read each. The fetched index page is cached in-process purely to avoid re-downloading megabytes per tick — losing it costs one fetch, never progress. **Enumeration repeats** (`resweep_after`, default 24 h): it is decision 07's drift repair *and* the only channel through which this instance can learn that upstream has started carrying a name we claim, since the read path structurally never asks upstream about a claimed name (S-16).
- (server) **S-17 shadowing alarms** ([registry/src/shadow.rs](server/crates/registry/src/shadow.rs)): one implementation, two callers, because the condition has two arrival orders — a publish claiming a name the proxy already caches (detected in the publish pipeline, on the first publish of that name) and upstream starting to carry a name we already claim (detected only on the mirror sweep). The local package keeps winning, before and after; the alarm is a notification register (`shadowing_alarms`, one row per name, `org_id` = the claim holder = the audience) with a `upstream.shadowing` audit event and a `PackageShadowed` domain event in the `security` notification category. Raised **once per incident** and counted thereafter — an hourly sweep must not re-page the same admins — and a sighting after an acknowledgement is a new incident. A shadowed name is observed and then skipped: mirroring it would store bytes resolution can never serve.
- (server) **Unreferenced-blob GC** ([jobs/src/gc.rs](server/crates/jobs/src/gc.rs)), disabled and dry-run by default. A content-addressed key is collectable only when **both** registers agree nothing live points at it — live `versions` *and* cached `upstream_versions`, because the proxy stores archives under the same keys a local publish does — and only outside a grace period (`min_age`, default 24 h, validated to exceed the 1-hour staged-upload TTL), since publish writes bytes before the version row and a staged upload is finalizable with nothing referencing it. Keys the job does not fully recognize are left strictly alone; a backend that cannot enumerate fails the job instead of deleting on incomplete information. Abandoned staged uploads are swept by age, closing the second half of S-20.a.
- (server) **`JobRepo` and migration 0006** in both dialects: `jobs` (opaque cursor, phase, run/success timestamps, last error, additive counters), `upstream_quarantine` (S-19 refusals, one row per `(name, version)` with an occurrence counter), `shadowing_alarms` (S-17, with acknowledgement). Counters are added to rather than written, so a run that dies between checkpoints leaves its partial progress recorded — and `begin_run` handing back the stored cursor is what makes a leader change resume rather than restart.
- (server) **Admin read model** (repo + service functions, no HTTP routes yet): `UpstreamService::cached_packages` (per-package version counts and the bytes we actually hold, keyset-paginated), `quarantined`, `shadowing_alarms`, `acknowledge_shadowing`, plus `MirrorWorker::status` / `BlobGc::status` for job state. `UpstreamRepo` gained `list_stale`, `list_cached`, `count_cached_with_sha256`, and the two registers' writers; `BlobStore` gained `list` (with sizes and ages — the age is what makes GC safe).
- (server) **Metrics** (decision 23; the counters are always maintained, the exporter stays config-gated and off): `upstream_fetch_total{kind,outcome}` replacing the two per-endpoint counters, `cache_hit_ratio`, `upstream_sync_lag_seconds`, `quarantine_total`, `shadowing_alarms_total`, `blob_gc_{scanned,deleted,bytes}_total`.
- (server) **`[upstream.mirror]` and `[jobs.blob_gc]` config**: mode, interval, chunk, concurrency, `refresh_after_secs`, `resweep_after_secs`, `archives` + `archive_versions`; GC `enabled`, `interval_secs`, `dry_run`, `min_age_secs`. Validated at startup — a mirror with `upstream.enabled = false` is refused (a worker fetching packages resolution can never serve looks like a working mirror from outside), as is a GC grace period below the staged-upload TTL — and shown in the effective-config summary. `pubd` registers only the enabled jobs, so a disabled job cannot tick at all.
- (server) **43 tests**: 16 job integration tests over a real database and blob store with only the network scripted — two replicas under one lock never running a tick concurrently (proved by the peak number of simultaneous upstream fetches, not by inspection), `recent` picking up a new upstream version and leaving fresh snapshots alone, archive warm-up, a chunked `full` sweep resuming across a simulated restart and re-enumerating after its window, an S-17 alarm raised once and never mirrored, an open circuit skipping the tick, GC keeping bytes shared with a live version *and* with a cached upstream version, dry-run, grace period, unrecognized keys, abandoned staged uploads, and a blind backend failing the job; 2 proxy conformance tests for the publish-side shadowing order; 3 repository contract functions running against **both** backends (`upstream_mirror_reads`, `supply_chain_registers`, `job_repo`); plus refresh/quarantine-register/cache-inventory/hit-ratio/breaker-peek unit tests and config tests.

### Fixed

- (server) **`/api/package-names` needs `Accept-Encoding: gzip`.** pub.dev answers `406 NotAcceptable` on that endpoint without it ("Client must accept gzip content"), so a full sweep against the real upstream would have failed permanently — found by running the worker against the live service. The header now rides both JSON endpoints and gzip is decoded **by hand** (flate2, with the size cap applied to the *decoded* document, so a few compressed kilobytes cannot decide how much memory the process allocates). The HTTP client is deliberately left without transparent content decoding: a client that silently decodes response bodies would also decode an archive body, and "the bytes we hash and store are the bytes that arrived" is the proxy's core promise ([sharp edge 3](docs/protocol.md#sharp-edges-violate--break-clients), S-19).

### Changed

- (server) `Repositories` gained a `jobs` handle and `BlobStore` a provided `list` (default: `Unimplemented`, because a store that cannot enumerate is not broken — it just cannot be swept). `DomainEvent` gained `PackageShadowed` and `notification_category()`, so the notification center routes by the event's own contract rather than by a lookup table. The Postgres cache-inventory aggregate casts `SUM()` to `bigint` — it answers `NUMERIC` otherwise, which would have made the two backends disagree on the row type.
- (docs) Decision 07 gained the mirror addendum (six decisions the "periodic sync worker" sentence left open), decision 06 the GC addendum, S-19 the quarantine register, S-20.a the closed staged-upload gap, and protocol.md the distinction between consuming upstream's `/api/package-names` and serving one of our own.

## 2026-08-07 — pub.dev read-through proxy

The first half of [decision 07](docs/decisions.md#07--upstream-proxy-read-through-cache-and-mirror-mode): unclaimed package names resolve through pub.dev, cached forever, verified before they are stored. No mirror worker yet — but the ingest pipeline the worker will warm is the one that ships here. Design refinements recorded in [docs/decisions.md](docs/decisions.md) (decision 01 and 07 addenda) and as amendments S-16.a and S-19.a in [docs/security.md](docs/security.md).

### Added

- (server) **Upstream ingest pipeline** ([registry/src/upstream.rs](server/crates/registry/src/upstream.rs)) shared by the read-through path and the future mirror worker: fetch listing → validate every version's pubspec with the **publish** validator (S-20) → snapshot upstream state verbatim (`retracted`, `isDiscontinued`, `replacedBy`, `advisoriesUpdated`, full pubspec JSON, `archive_sha256`) → on an archive miss, fetch, **verify the advertised sha256 before anything is stored** (S-19), then store byte-identical and content-addressed under the same `<format>/<shard>/<sha>.tar.gz` key a local publish uses. Archives are never re-tarred or re-gzipped: the hash in a user's `pubspec.lock` is the hash of upstream's exact bytes.
- (server) **Integrity refusals that are events, not log lines** (S-19): a hash mismatch is a **quarantine** — never stored, never served, audited as `upstream.quarantine` with both hashes and emitted as a domain event, answered to the client as a permanent 404. Upstream advertising a *different* hash for a version we already hold is **byte-drift**: the cached bytes keep being served, the change is audited as `upstream.drift` and alarmed, and nothing is overwritten. The freeze is enforced twice on purpose — the service computes the preserved value and both repositories' upsert independently keeps it (`CASE WHEN cached THEN … END`), so a future caller cannot reintroduce the overwrite.
- (server) **`UpstreamClient` behind a trait** with a real implementation over reqwest + rustls ([registry/src/upstream/http.rs](server/crates/registry/src/upstream/http.rs)): timeouts, exponential-backoff retries on transient failures only, an optional bearer credential for authenticated mirrors, bodies bounded *while* they arrive, and an SSRF guard on every URL upstream chooses — https only, no user-info, no loopback/private/link-local/CGNAT destination (`169.254.169.254` included), redirects capped and re-checked, and a configured token never following a cross-host hop. Every proxy behaviour worth asserting is defined by upstream *misbehaving*, so no test in the workspace opens a socket.
- (server) **Degradation that never becomes a retry storm**: an unreachable upstream or an open circuit serves the cached listing/archive with a staleness marker in tracing and metrics, and anything never cached answers **404**, never 5xx — the client retries 5xx up to seven times ([sharp edge 2](docs/protocol.md#sharp-edges-violate--break-clients)). A per-instance circuit breaker (half-open admits one probe with its budget already spent), a per-upstream concurrency semaphore, and a single-flight guard so N simultaneous misses of one package cause **one** upstream fetch. An upstream 404 neither evicts a snapshot we hold nor counts against the breaker.
- (server) **Resolution wiring** (decision 01, S-16): the proxy is reachable from exactly one expression — the `Resolution::Unclaimed` arm of `resolve_target`, whose `Target::Upstream` variant *carries* the service, so no handler can proxy a claimed name even by accident. Proxied listings re-emit upstream's flags, hashes, and pubspecs verbatim with `archive_url` rewritten under the requesting base ([sharp edge 3](docs/protocol.md#sharp-edges-violate--break-clients)); local and upstream versions of one name are never merged. `advisoriesUpdated` is stored but not advertised while `…/advisories` is unimplemented (sharp edge 11).
- (server) **Per-org upstream policy** (`orgs.upstream_policy`, `allow` | `block`, migration **0005** in both dialects): a blocked org answers the *same* 404 for an unclaimed name that an unknown name gets — a distinct status would confirm the package exists upstream (S-04). `delay`/`allowlist` are later variants of the same enum; `OrgRepo::set_upstream_policy` is their write path.
- (server) **`UpstreamRepo`** in `core` with implementations on both backends: snapshot upsert that **never deletes** a version upstream stopped listing (we may already hold its bytes), precedence-ordered `list_versions`, and `mark_cached` guarded by the content hash so a row whose hash moved under a concurrent snapshot cannot be marked cached for the wrong content.
- (server) **`[upstream]` config section**: `enabled` (default true), `base_url` (default `https://pub.dev`, https required in production — the listing carries the hash we verify against), `user_agent`, optional `auth_token` (a masked `Secret`), connect/listing/archive timeouts, retry count and backoff bounds, `max_archive_bytes`, `max_listing_bytes`, `listing_ttl_secs` (default 300), `max_concurrent_fetches`, and the circuit-breaker thresholds — validated at startup even when disabled, and shown in the effective-config summary with the token masked.
- (server) **67 tests**: a 21-test proxy conformance suite ([api/tests/proxy.rs](server/crates/api/tests/proxy.rs)) over a scripted upstream — cold miss caching and re-emitting under our own base, a warm cache proving upstream was not asked, TTL refresh, sha256-mismatch quarantine (refused, unstored, audited, and still ingestible once upstream is honest again), byte-drift keeping the pinned hash and the original bytes, stale serving and 404-not-5xx under an outage, the circuit breaker, single-flight collapsing eight concurrent misses into one fetch, oversized and hostile-pubspec refusals, the four resolution-order cases, per-org `block`, and verbatim flag re-emission; 23 registry unit/pipeline tests; an `upstream_repo` contract function running against **both** database backends; SSRF-guard, status-mapping, depth-check, and config tests.

### Changed

- (server) `Pubspec::parse` is now YAML decoding plus `Pubspec::from_json`, the shared rules half — so "an upstream pubspec clears the same bar as a local publish" is one implementation rather than two. The depth cap walks iteratively: a JSON document arrives already built, and recursing over an attacker-shaped tree is how a depth check becomes the overflow it was meant to prevent.
- (server) `Repositories` gained an `upstream` handle, `AppState` an `upstream: Option<Arc<UpstreamService>>` (absent = no upstream branch in the resolution path at all, which is what an air-gapped operator buys), `Org` an `upstream_policy` field, and `DomainEvent::org_id()` returns `Option<OrgId>` — proxy integrity alarms are instance-scoped, and silently attributing them to some org would show them to the wrong audience (S-32).
- (server) The archive response omits `Content-Length` rather than claiming zero when a size is unknown; proxied sizes are measured while caching and frozen with the hash.

## 2026-08-07 — registry conformance and security review

An adversarial pass over the registry slice, arbitrated by the **real `dart pub` client** (Dart SDK 3.12.2) driving a live `pubd` on SQLite + filesystem blobs: token add → publish → resolve in a consumer package → retraction visibility, plus the 401/403 credential-handling asymmetry that only exists in the client's source. Findings recorded in [docs/security.md](docs/security.md) (S-04.b, S-20.a, S-24.b/c) and [docs/protocol.md](docs/protocol.md).

### Fixed

- (server) **An archive could hide bytes from the validator** (S-20). A tar reader stops at the end-of-archive marker and a single-member gzip reader stops at the end of member one, so a second concatenated gzip member — which `tar -xzf` decodes — or a payload past the zero blocks passed ingest unseen and was then stored and served forever: the validated archive was a *prefix* of the published one. The stream is now decoded multi-member and drained to EOF, and everything after the marker must be NUL padding (`ArchiveError::TrailingData`). Verified not to reject archives produced by the real client, which pad with zeros.
- (server) **A duplicate-version conflict leaked version existence across orgs** (S-04, decision 01). Publishing into a name another org holds reported "version 1.0.0 already exists" when the version happened to exist — a version-existence oracle for somebody else's private package. Ownership is now decided before existence, and both routes to the denial emit the same sentence.
- (server) **A wrong method under a registry base answered a bodyless 405.** The router produced it before any handler, so the pub client — which parses the body of every failure — got unparseable bytes. It now carries the spec error shape, still as a permanent 4xx.
- (server) **The `Bearer` scheme was matched case-sensitively.** Auth schemes are case-insensitive (RFC 9110 §11.1), and on this plane a rejected credential is a 401 — which makes the client *delete the stored token*. Header casing must not cost a developer their credential.
- (server) **A rejected publish was audited without naming the package** (S-22): the pub protocol pins no name (step 1 carries none), so every failure landed in the log as an anonymous `package.publish` failure. The pipeline now reports the parsed name back, and rejections after the pubspec parses are audited as `name@version`.
- (server) Caller-supplied names and archive filenames are clipped before they are quoted back in a 404 message (the ingest path already did this for tar entry paths).

### Added

- (server) **S-24 publish rate limit** — `registry.rate_limit.publish_per_hour_org` (default 30), previously normative but unimplemented. It is spent by the upload step, which is the step that costs storage and is reachable directly; trips answer `429 + Retry-After` and are audit-logged as `package.publish.throttled`. A KV outage fails **open** here (an already-authorized write), the opposite of the auth-abuse buckets.
- (server) **Adversarial suite** ([api/tests/pub_attack.rs](server/crates/api/tests/pub_attack.rs), 9 tests): the publish authorization matrix (read-scoped token, foreign-org token, Read-role member, non-member — every cell a 403 that keeps the credential, at step 1 *and* at the byte sink), 13 hostile archives each required to answer a permanent 4xx (truncated gzip, gzip-in-gzip, tar garbage, traversal, absolute path, duplicate entries, missing/invalid pubspec, YAML anchor bomb, gzip bomb, 10 001 entries, smuggled second member), byte-identical responses for private-vs-unknown names, blob keys that no crafted name or version can steer, and a finalize session that cannot be redeemed from another org.
- (server) **Conformance re-derivations** in [api/tests/protocol.rs](server/crates/api/tests/protocol.rs): 405 responses speak the spec shape, the bearer scheme is case-insensitive, no valid credential is ever answered with 401 (a seven-case matrix over the read *and* publish paths), listing and error bodies carry exactly the documented field set read from the response bytes, and archives answer `HEAD` with the same metadata as `GET` (the client HEADs before it downloads).

## 2026-08-07 — pub protocol v2 HTTP surface

The registry becomes usable by `dart pub`: the Hosted Pub Repository Spec v2 endpoints on both virtual bases (`/o/{org}/pub` and the public root `/pub`), the CLI-token authentication plane, and the decision 05 status ladder — with a conformance suite that encodes [docs/protocol.md](docs/protocol.md) sharp edge by sharp edge. Design refinements recorded in [docs/decisions.md](docs/decisions.md) (decision 01, 05 and 13 addenda) and as amendment S-14.a in [docs/security.md](docs/security.md).

### Added

- (server) **Pub protocol routes** ([api/src/protocol/](server/crates/api/src/protocol/)), one handler set mounted on both bases (`nest` prefixes the OpenAPI paths too, so neither mount can drift): `GET B/api/packages/{name}` (version listing — `name`, `latest`, `versions[]` with `version`/`retracted`/`archive_url`/`archive_sha256`/`pubspec`, `isDiscontinued`/`replacedBy`, served as `application/vnd.pub.v2+json`); the three-step publish `GET B/api/packages/versions/new` → `POST B/api/packages/versions/newUpload` (multipart field `file`, `204` + `Location`) → `GET B/api/packages/versions/newUploadFinish/{session}` (`200 {"success":…}` / `400 {"error":…}`); `GET B/api/archives/{name}-{version}.tar.gz` honouring `DownloadPlan` (307 to a presigned URL, or the stored bytes streamed); and the legacy `GET B/api/packages/{name}/versions/{version}` and `GET B/packages/{name}/versions/{version}.tar.gz`. - (server) **CLI-token authentication plane for pub routes** (S-13/S-14): the `Principal` extractor takes the token from `Authorization: Bearer` **only** — the spec has no query-parameter credential, and `?token=` would put live secrets into access logs and `pubspec.lock` files. Offline CRC/prefix/charset validation runs before any database lookup, which is also what structurally excludes browser access JWTs from this plane (decision 03). Scopes, the org binding, and the org role are three independent checks; package patterns narrow reads of *private* packages and are enforced at publish finalize, where the package name first exists. `AuthService::authenticate_cli_token`/`token_actor`/`touch_cli_token` carry it, with the S-24 "30 failed token authentications per IP per minute" bucket answering 429 + `Retry-After` instead of a 401 that would delete a bystander's stored token.
- (server) **Status ladder** (decision 05, S-04/S-14) in one place ([protocol/error.rs](server/crates/api/src/protocol/error.rs)): unreadable-or-unknown → **404** with no challenge; missing/invalid credentials → **401**; valid-but-insufficient on a visible resource → **403**; both 401 and 403 carry `WWW-Authenticate: Bearer realm="pub", message="…"` with the message sanitized and capped at 1024 chars — the CLI's only messaging channel, so every denial names the fix (`dart pub token add <base>`, the missing scope, the missing role). Permanent failures are 4xx by construction, `Conflict` included (finalize answers 400, not 409, and a unit test asserts no permanent error can map to 5xx — the client retries those up to 7 times).
- (server) **Base-scoped resolution** (decision 01, S-16): `PackageRepo::resolve_in_base` — a provided method, so the policy exists once above both SQL dialects and runs through the `authorize()` chokepoint. Inside `/o/{org}/pub`: org-owned → instance-public → (upstream iff unclaimed); at `/pub`: public only. "Local always wins" is structural rather than conventional — `Resolution::Unclaimed`, the only value that may ever permit an upstream lookup, is produced on exactly one path, after `lookup_claim` came back empty. Handlers never call `get_by_name` on a read path.
- (server) `registry.require_auth_for_read` (decision 05): flips the protocol to token-only reads, where anonymous requests get the spec-mandated 401 + onboarding message instead of the anti-enumeration 404. `auth.rate_limit.token_auth_fail_per_ip_minute` (S-24, default 30). `BlobStore::get` — the in-process read path, distinct from `download`, which plans a *client* response and may answer with a redirect. `core::token::patterns_allow` shared by the read narrowing and the publish check.
- (server) 82 tests: a 42-test conformance suite ([api/tests/protocol.rs](server/crates/api/tests/protocol.rs)) named after the sharp edges it pins and driving the router exactly as the CLI does — the ladder (404-not-401, 403-with-challenge for scope *and* role, indistinguishable expired/revoked tokens, both credential planes rejecting each other's tokens), listing field types (`archive_sha256` exactly 64 lowercase hex, booleans, full pubspec), the publish flow following the advertised URLs (happy path, duplicate → 400, corrupt archive → 400, junk accepted at upload and refused at finalize, single-use sessions, finalize bound to its credential, pattern-scoped tokens passing step 1 and failing step 3), byte-stability across a restart on two blob backends, subpath bases, `Accept` negotiation and the 406, retraction/hard-delete visibility, resolution order across bases, legacy endpoints, and both mounts being present in the OpenAPI document; plus 39 unit tests and a `resolve_in_base` contract function running on **both** database backends.

### Changed

The pub protocol deliberately does **not** inherit the S-12 mutation guard or the app-API rate-limit layer — both scope themselves to `/api/…`, and the CLI can send neither a custom header nor a JSON body.

## 2026-08-06 — auth slice: adversarial security review

Findings from an attack-oriented review of the just-landed auth slice. Every fix ships with the attack that motivated it ([api/tests/attack.rs](server/crates/api/tests/attack.rs), 20 tests); the normative consequences are recorded as amendments S-03.a, S-04.a, S-12.a, S-24.a/b and S-25.a in [docs/security.md](docs/security.md).

### Security

- (server) **OTP attempt budget was not atomic.** The ≤5-wrong-attempts counter lived inside the pending-auth record and was read-modify-written per verification, so guesses fired in parallel shared a single increment and the budget bounded nothing. The counter moved to its own KV key behind a new atomic `Kv::incr` primitive (Redis `INCR`+`PEXPIRE`, moka per-key upsert), and the attempt is now spent **before** the code is compared (S-03/S-03.a).
- (server) **`X-Forwarded-For` was trusted unconditionally, leftmost hop first.** Every S-24 per-IP limit could be bypassed by rotating the header, and any address's bucket and audit trail could be poisoned by claiming to be it — including behind a correctly configured reverse proxy, where the leftmost entry is exactly the client-supplied one. New `server.trust_proxy_headers` (default **false**) ignores forwarding headers in favour of the socket peer; when enabled it reads the **rightmost** entry. `pubd` now serves with connect-info so a peer address exists (S-24.a/b).
- (server) **Credential redemption had no rate limit.** `POST /api/v1/auth/otp/verify` and `/auth/refresh` were unthrottled, so the per-code ≤5 budget was sidestepped by simply requesting fresh codes. Both now carry S-24's "login 10/min/IP" bucket (`auth.rate_limit.login_per_ip_minute`).
- (server) **Secrets were reachable through derived `Debug`.** The OTP pepper, JWT signing seeds, SMTP password, S3 keys, connection-URL passwords, minted token secrets and the access/refresh pair were all printable via a stray `{:?}`, `#[instrument]` field or panic message — S-25 masking covered only the startup summary. Configured secrets now use a `Secret` newtype (redacting `Debug`, no `Display`, explicit `.expose()`); `DatabaseConfig`/`KvConfig` mask their URLs; `AuthPolicy`, `LoginSuccess`, `MintedToken` and `SmtpSettings` hand-write redacting `Debug` (S-25.a).
- (server) **S-31 was enforced at registration but not at sign-in.** An account whose domain had since left the allowlist could still redeem a valid code; `verify_otp` now applies the domain gate to existing accounts too, with the same uniform `invalid_code` rejection (S-04).
- (server) **S-12's server-side `Origin`/`Sec-Fetch-Site` verification was missing** — only the custom header was checked, leaving CSRF defence entirely to the browser. `/api/` mutations now compare the parsed `Origin` triple against `server.public_url` and reject non-same-site `Sec-Fetch-Site`, while header-less CLI/CI clients keep working (S-12.a).
- (server) **Anti-enumeration timing.** `request_otp` no longer skips the account lookup and template render for policy-rejected addresses; all branches perform identical server-side work. The remaining SMTP-hand-off asymmetry is documented as an accepted, bounded risk with its planned mitigation (S-04.a).

### Added

- (server) `Kv::incr` — atomic counter with TTL on the KV seam, contracted as atomic because authentication budgets are decided by its return value.
- (server) `_FILE`-suffixed environment variables (S-25): secrets read from mounted files with trailing newlines trimmed; unreadable paths and the ambiguous "both `X` and `X_FILE` set" case are startup errors.
- (server) `RequestMeta` typed extractor replacing ad-hoc `HeaderMap` plumbing, so handlers cannot reach for a raw forwarding header instead of the resolved client identity.
- (server) 39 tests: the 20-test adversarial suite (JWT algorithm confusion with the Ed25519 public key as HMAC secret, `alg:none`, unknown `kid`; parallel OTP guessing; resend-rewind of the attempt budget; KV-outage fail-closed on both the access-token and OTP paths; concurrent refresh races; refresh-plaintext persistence; bundled `admin` scope escalation; forwarded-header spoofing and poisoning; cross-site mutations; post-policy domain sign-in) plus KV atomicity, config secret-redaction, `_FILE` handling, and JWT claim-set assertions.
